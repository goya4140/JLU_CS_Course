CHAPTER 6 · TRANSPORT LAYER

传输层：让两台主机上的
两个进程，像面对面一样对话

网络层能把一个包从这台主机送到那台主机，可一台主机上同时跑着浏览器、微信、下载工具……包到了之后该交给谁？传输层就是干这件事的——它把"主机之间的通信"，升级成"进程之间的通信"。这一层要么像 UDP 那样大大咧咧、发完就忘，要么像 TCP 那样面面俱到、把一条不可靠的网络改造成可靠的字节流。

先建立整体印象：这一层在忙什么

在 OSI 模型里，传输层夹在"通信子网"（下三层：物理、数据链路、网络）和"资源子网"（上三层：会话、表示、应用）之间，是整个协议层次中最核心的一层。为什么说它核心？因为下三层负责"把比特从这里送到那里"，而上层的应用程序根本不该关心网络是怎么铺的——传输层就站在这个分界线上，向上把通信细节藏起来。

用"打电话"来类比

网络层（IP）相当于总机把电话从你这栋楼接通到对方那栋楼——它只保证"主机到主机"。可对方那栋楼里有几百个分机，包到底找哪个分机？传输层的端口号就是分机号。于是传输层提供的是"进程到进程"的逻辑通信：IP 的作用范围是两台主机之间，TCP/UDP 的作用范围才是两台主机上具体应用进程之间。

它到底要做哪几件事

课件把传输层的功能归纳为四条：端到端的报文传递、服务点的寻址（端口）、拆分和组装（把大块数据切成小块、到对端再拼起来）、连接控制。围绕"要不要先把关系定下来"，它给上层提供两类截然不同的服务：

面向连接先握手建连、传数据、再挥手释放（TCP）
无连接每个包独立发，事先不打招呼（UDP）

端口号：这一层的"门牌号"

一台计算机发出的数据，不仅要被另一台计算机收到，还必须被那台计算机上正确的那个应用程序收到。一个应用程序要和远端程序通信，必须知道两个地址：NSAP 地址（网络服务访问点，也就是 IP 地址，找到是哪台主机）和 TSAP 地址（传输服务访问点，也就是端口号，找到是这台主机上的哪个程序）。

端口号是一个抽象的标识符，每台计算机内部再把它映射到操作系统里的具体程序编号。正因为有了端口，传输层才能做复用与分用：发送时多个应用进程共用一条网络连接发出去（向下复用），接收时再根据端口号把数据分发给对应的进程（向上分用）。

一句话主线：传输层 = 在主机之间加一道"进程级的门牌号"（端口），再决定要不要为这次对话建立一条"可信的专线"。后面 UDP 和 TCP，就是这道题的两种截然不同的解法。
模块 1 可靠传输与流量控制

怎么把一条"会出错、会堵车"的路修好

传输层运行在一个不可靠的网络之上：包可能丢、可能坏、可能乱序到、可能重复到。所谓"可靠传输"，并不是魔法，而是四件具体的事凑在一起——先看清单，后面 TCP 全是在实现这四件事。

要解决的问题靠什么手段类比
差错控制校验和，发现比特传错了挂号信拆开先检查信封有没有破损
次序控制给分段编号，到对端再按序拼回把长信拆成编号信页，收到后按页码装订
丢失控制超时没等到确认就重传快递丢了，过一阵没动静就再寄一份
重复控制靠序号识别重复包，丢掉副本同一封信收到两封，看页码发现是重号，扔一封

次序控制：先切，再拼

上层交下来的是一整块数据，网络层一次不一定装得下，传输层就把它分段，给每段编上序号，加上端口号 j、k 和网络地址 A、P，再交给网络层发出。到了接收端，再把这些分段按序号组合还原成原来那整块数据。还有另一种相反的情况：发送方应用一口气塞来好几小块（数据1、数据2），传输层可以把它们合并（分割）进同一批发送；本质都是"发送侧切块/拼接、接收侧反向操作"。

流量控制：别把对方噎着

传输层也要做流量控制，但和数据链路层有个关键区别：链路层的流量控制只管相邻这一段链路，传输层的流量控制是端到端的。它同样用滑动窗口，但窗口大小是可变的——接收方缓冲区紧张了就调小，空闲了就调大，以适应缓冲区的变化。

发送窗口用三个指针圈出三块区域：已经发送并被确认的、已发送但还没被确认的、还可以继续发送的，剩下的就是"暂时不能发"的。数据发出去，"可发送"指针右移；收到确认，"已确认"指针也右移，窗口整体向前滑动。

课件例题：请求 8 个缓冲只拿到 4 个（点开看完整过程）

A 向 B 请求分配 8 个缓冲区，B 只给了 4 个，于是 A 只能一边发一边等确认。过程：A 发 REQ（要 8 个缓冲）→ B 回 ACK0（只给 4 个）→ A 依次发 Seq0、Seq1、Seq2 → B 回 ACK2（缓冲剩 3）→ A 发 Seq3、Seq4 → 其中 ACK 丢失，A 超时重发 Seq2 → B 再回 ACK5（缓冲耗尽为 0）→ A 继续被 ACK5 带着往前走……整个过程里，B 的"buf."数字（剩余缓冲区）不断变化，A 发多快完全由 B 反馈的窗口大小决定——这就是端到端、可变窗口的流量控制。

面向连接的三步：建连、传数据、拆连

传输层端到端传送有面向连接和无连接两种模式。面向连接要走三步：连接建立 → 数据传输 → 连接终止。课件在通用模型里就已经画出了雏形：建立连接用三次握手（CR 连接请求，互相交换初始序号 x、y 并确认）；如果中途来了一个重复的、失效的连接请求（旧报文迟到），接收方会用 RJ（拒绝）来回绝，避免误建连接。这套思想后面 TCP 会用 SYN/ACK 完整重演一遍。

模块 2 轻装上阵的 UDP

用户数据报协议：发出去就当完事了

UDP（用户数据报协议）走的是另一个极端：它用无连接的方式做事务处理，不提供可靠性——没有端到端确认，没有重传，不保证包一定到得了。它会遭遇丢失、重复、延迟、乱序和损坏，所以叫"不可靠协议"。UDP 必须跑在 IP 之上，把 UDP 数据报整个塞进 IP 数据报里。

为什么还要有这么个"不靠谱"的协议

打视频电话、直播、在线游戏时，你真正怕的是"延迟太高"，而不是"丢了这一帧"。这种场景下，UDP 不握手、不排队重传、头部极小、开销极低，反而比面面俱到的 TCP 更合适——丢一两帧无所谓，卡成 PPT 才要命。UDP 的六个标签：端到端、无连接、面向报文、尽力而为、任意交互、操作系统无关。

面向报文：一个应用报文，一个 UDP 包

UDP 允许一对一、一对多两种通信方式。它"面向报文"意味着：应用进程交给它一个完整报文，UDP 就原封不动装进一个数据报发出去——既不拆，也不合并，到对端也是整包交给应用进程。这和 TCP 那个"字节流"形成鲜明对比（后面模块三会讲）。

UDP 报头：只有 8 个字节

源端口号16 位，可选，不用则填 0
目的端口号16 位，指明接收进程
报文长度16 位，首部+数据字节数，最小 8
校验和16 位，可选字段
  • 源端口号：作为接收进程回数据时的目的端口；是可选字段，不用就填 0。
  • 目的端口号：接收主机内与某个应用进程绑定的地址。
  • 长度：指 UDP 首部＋UDP 数据的总字节数（＝IP 全长减去 IP 首部长度），最小就是首部本身的 8 字节。
  • 校验和：可选，用来检测传输中是否出错。

校验和为什么要加一个"伪首部"

UDP 校验和不光算 UDP 首部和数据，还要在前面拼一个 12 字节的伪首部，里面包含源 IP 地址、目的 IP 地址、一个全 0 字节、协议号（UDP 是 17）和 UDP 长度。

源 IP 地址4B
目的 IP 地址4B
0 / 协议(17) / UDP长度4B（伪首部）
UDP 首部+数据真正发送的部分

伪首部并不真的发送，只是计算校验和时临时拼上去。它的妙处在于：把 IP 层的源/目的地址也纳入校验范围，这样万一 UDP 包被错误地送到了别的主机、或地址被改了，校验和就能对出来——相当于"顺便检查了一下这包是不是真的寄给对的人"。

课件算例：二进制反码求和怎么算出校验和

把伪首部（源 IP 153.19.8.104、目的 IP 171.3.14.11、0、协议17、长度15）、UDP 首部（长度15、校验和先填0）和数据逐段按 16 位一行展开，用二进制反码运算求和。数据是 7 个字节（"TESTING"），凑不满 16 位整数倍时末尾补一个全 0 字节对齐。把所有 16 位字加起来得到一串（如 10010110 11101101），再对这个和求反码，就得到校验和 01101001 00010010。接收方把校验和也算进总和，正确时结果应为全 1。

模块 3 TCP 报文段首部

TCP：可靠的、面向连接的字节流

和 UDP 相反，TCP 提供一种可靠的、面向连接的、全双工的字节流传输服务，并做端到端流量控制、强制校验和。它的特点：面向连接、点对点、完全可靠、全双工、流接口、可靠地建立连接、友好地关闭连接。虽然 TCP 和 UDP 都跑在同一个 IP 之上，给应用层的服务却完全不同。可以把 TCP 描述成一个没有选择确认、也没有否认的、窗口大小可变的滑动窗口协议。

把 TCP 想成"一条按顺序递挂号信的专线"

UDP 是把明信片扔进邮筒、不管对方收没收到；TCP 则是双方先打电话确认对方在家（握手），然后把你的文件拆成一页一页、每页编号，按编号送达、签收、丢了就补寄，最后再礼貌道别（挥手）。"字节流"意味着应用写到发送缓存里的是一串没有边界的字节，TCP 自己决定怎么切分成一个个报文段——它不保证你写一次、对面就收一次。

TCP 报文段的整体长相

TCP 首部固定 20 字节 ＋ 可变选项
TCP 数据部分应用数据

整个 TCP 报文段再装进 IP 数据报里（IP 首部在前）。固定首部 20 字节，后面还能跟长度可变的选项。下面逐个字段拆开看——这是本章的重头戏。

3.1 端口、序号、确认号

字段长度含义
源端口 / 目的端口各 2 字节传输层与应用层的服务接口，复用和分用都靠它
序号 seq4 字节本报文段所发数据第一个字节的编号
确认号 ack4 字节期望收到对方下一个字节的序号

TCP 把连接里传送的每一个字节都编上号。序号字段的值，指的是本报文段数据部分第一个字节的编号；确认号则是"我已经收到了你到 ack−1 为止的所有字节，下一次请从 ack 开始发"。注意：确认号总是上次成功收到的最后一个字节序号加 1。

因为确认号字段和 ACK 标志本来就是 TCP 首部的固定成员，所以一旦连接建立，ACK 标志就永远置 1，发确认几乎不花额外代价。

3.2 数据偏移、保留与六个控制标志

数据偏移占 4 位，它指出"数据起始处距离报文段开头有多远"，单位是 32 位字（即 4 字节）——也就是用它来算首部总长度（因为选项是变长的）。保留字段占 4 位，留作将来用，没用时填 0。

紧跟着是 6 个控制位（再加上 CWR、ECE 共 8 个标志位），每个都是开关：

标志名字为 1 时的含义
URG紧急紧急指针有效，这包有要尽快传送的高优先级数据
ACK确认确认号字段有效；连接建立后恒为 1
PSH推送收到就尽快上交应用进程，别等缓存填满
RST复位连接出严重差错（如主机崩溃），释放后重建
SYN同步这是连接请求或连接接受报文
FIN终止发送方数据发完了，请求释放连接
ECEECN 响应收到了 IP 头 ECN=1 的包，表示网络拥塞；握手时表示本机支持 ECN
CWR拥塞窗口减少已收到 ECE 包，发送方据此减小发送窗口、降低发送速率

3.3 窗口、校验和、紧急指针、选项

  • 窗口（2 字节）：告诉对方"我现在还能收多少字节"，是对方设置发送窗口的依据，单位是字节。
  • 校验和（2 字节）：校验范围包括首部＋数据；计算时也要在前面加 12 字节伪首部（和 UDP 同理）。
  • 紧急指针（16 位）：指出本报文段里紧急数据共有多少字节，与序号相加得到紧急数据最后一个字节的序号。
  • 选项（长度可变）：TCP 最初只规定一种——最大报文段长度 MSS，用来告诉对方"我缓存能接收的数据字段最大是 MSS 字节"。
  • 填充：因为选项长度不定，必要时补 0，保证首部长度是 4 字节的整数倍（对齐数据偏移的单位）。
TCP 选项 kind 速查（点开）
  • kind=0：选项表结束（EOP）；kind=1：空操作（NOP，用于对齐）；
  • kind=2：最大报文段长度 MSS；kind=3：窗口扩大因子；
  • kind=4：允许 SACK；kind=5：SACK 实际工作；kind=8：时间戳选项。

3.4 为什么 TCP 做不到"选择确认"

课件特意强调：TCP 的确认号表示"我已成功收到字节序号小于它的全部字节，但不包含它本身指向的那个字节"。举例：1～1024 字节已收到，接下来一个报文段送来的是 2049～3072 字节——中间 1025～2048 还缺着，接收端没法确认这个新报文段，它能做的只有回一个确认号 1025 的 ACK。这就是"没有选择确认/否定的滑动窗口"的含义。后面模块四会讲怎么用 SACK 选项补上这个能力。

模块 4 可靠怎么做到：重传与定时器

丢了怎么发现、多快重传才合适

模块一说过，TCP 靠四样技术对付四类问题：给每个分组附序号对付重复和乱序；用"带重传的正向确认"对付丢失；用序号防重复；用滑动窗口做流量控制。这一节聚焦最难的问题——超时重传时间到底该设多长。课件说：重传机制是 TCP 中最重要也最复杂的问题之一。

4.1 为什么 RTT 这么难测

TCP 每发一个报文段，就给它启动一次计时器；计时时间到了还没收到确认，就重发这一段。可麻烦在于：TCP 下面是互联网环境，IP 数据报走哪条路由变化很大，于是往返时间 RTT 的方差也很大。设短了——没丢包却误超时，白白重传；设长了——真丢包却干等半天。怎么取一个聪明的值？

4.2 平滑 RTT 与超时时间 RTO

TCP 保留一个"加权平均往返时间" RTTS（又叫平滑 RTT）。第一次测到 RTT 样本时，RTTS 就取这个样本值；以后每来一个新样本，按指数滑动平均更新：

新 RTTS = (1−α) × 旧 RTTS + α × 新 RTT 样本　（RFC 2988 推荐 α = 1/8 = 0.125）

α 接近 0 表示 RTT 更新慢、稳；接近 1 表示更新快、跟得紧。但只取平均值还不够——万一某次 RTT 突然变长，RTO 也该跟着放宽。所以再引入偏差的加权平均 RTTD：

RTO = RTTS + 4 × RTTD
新 RTTD = (1−β) × 旧 RTTD + β × |RTTS − 新 RTT 样本|　（β = 1/4 = 0.25）

第一次测量时 RTTD 取样本值的一半。直觉上：RTTS 是"正常大概要多久"，RTTD 是"波动有多大"，RTO 在平均时间之外再留 4 倍波动量的富余。

4.3 Karn 算法：重传过的包不再用来算 RTT

重传带来一个测不准的难题：一个报文段发出去、超时、重传，这时收到一个 ACK——它到底确认的是第一次发的，还是重传的那一次？分不清，RTT 就会测歪。Karn 算法的处理很干脆：重传报文的 RTT 不取样。但这样超时时间就没法更新了，于是补一条修正：报文段每重传一次，就把 RTO 放大一倍：

新 RTO = γ × 旧 RTO　（γ 典型值 = 2）

越重传越等得久，避免在已经拥塞的网络上反复火上浇油。

4.5 SACK：补上"选择确认"这块短板

模块三说过，普通 TCP 只能回一个累积确认号，中间缺块时新到的好数据也没法被确认。课件例子：收到 1025～2048 这段但校验和错了，接收端只能回确认号 1025。解决办法是 SACK（选择确认，RFC 2018）：在选项里额外报告"我这里连续收到了哪些字节块"。

例子：收到字节 1～1000 连续，然后缺了一段，接着 1501～3000、3501～4500 又各成一块到达。确认号仍填 1001（表示连续收到的上界），再在 SACK 里报告两个块的边界：第一块 L1=1501、R1=3001；第二块 L2=3501、R2=4501。

这样发送方就知道只缺 1001～1500，不必把后面好端端的 1501～4500 也一起重传。注意：建立连接时双方就要在选项里约定"允许 SACK"；确认号字段用法不变；每个边界 4 字节，选项最多 40 字节，所以最多报告 4 个字节块的边界。

4.6 什么时候发、发多大：发送时机与两个性能算法

TCP 决定"什么时候凑够一个报文段发出去"有三种机制：缓存攒到 MSS 就发；应用主动要求推送（push）；发送计时器到点，把现有缓存（不超 MSS）打包发出去。

Nagle 算法：别一个字节一个字节地发

如果应用把数据逐字节塞进发送缓存，TCP 会先把第一个字节发出去，后面的先攒着；收到第一个字节的确认后，再把攒下的数据打成一段发出去；一旦攒到发送窗口的一半或一个 MSS，也立刻发。这样避免在一条连接上塞满极小的报文段。

糊涂窗口综合症：别让对方一次只读一个字节

反过来的麻烦：接收缓存已满，应用却一次只从中读一个字节，然后通告"窗口开了 1 字节"——发送方就屁颠屁颠发个只装 1 字节的包，来回跑一趟却传 1 字节，这就是糊涂窗口综合症。对策：让接收方等一等，直到缓存能装下一个 MSS、或空出一半空间再通告窗口；发送方也别发太小的报文。

模块 5 三次握手与四次挥手

建立和拆除一条 TCP 连接

TCP 是面向连接的，双方发数据前必须先建好连接。建立连接要解决三件事：让每一方都确知对方存在；允许双方协商参数（MSS、最大窗口、服务质量等）；分配传输实体资源（缓存、连接表项），还要避免一个"已经失效的旧连接请求"突然冒出来把连接建错。这个过程就叫三次握手（3-way handshake）。

三次握手为什么像打电话确认

A 说："喂，能听到我吗？（SYN，seq=x）"；B 回："能听到，你能听到我吗？（SYN+ACK，seq=y，ack=x+1）"；A 再补一句："能听到你！（ACK，ack=y+1）"。为什么要第三句？因为 B 发出"我在"之后，并不知道 A 是否收到了这句——少了 A 的最后确认，B 可能对着空气白等。这正是"双方都要确知对方存在"。

5.1 三次握手的报文与状态

① A → BSYN=1, seq=x
② B → ASYN=1, ACK=1, seq=y, ack=x+1
③ A → BACK=1, seq=x+1, ack=y+1

A 主动打开，从 CLOSED 进入 SYN_SENT；B 被动打开（LISTEN），收到 SYN 后回 SYN+ACK，进入 SYN_RCVD；A 发完第三个 ACK 后双方都进入 ESTABLISHED，开始传数据。下面这个分步演示把整个过程和状态走一遍。

5.2 为什么释放连接要四次

建立连接三次就够，释放却要四次握手。原因是 TCP 全双工，两个方向要分别关闭。主动关闭方 A 说"我没数据要发了"（FIN），可这时 B 可能还有数据要继续发——B 先回一个 ACK 表示"知道了你发完了"，等 B 自己数据也发完了，才再发一个 FIN，A 再回 ACK。ACK 和 FIN 不能像建连那样合并，所以多了一次。

① A → BFIN=1, seq=u（A 主动关闭）
② B → AACK=1, seq=v, ack=u+1
③ B → AFIN=1, ACK=1, seq=w, ack=u+1
④ A → BACK=1, ack=w+1

状态跟着走：A 发 FIN 后是 FIN_WAIT_1，收到 B 的 ACK 后进入 FIN_WAIT_2；B 收到 A 的 FIN 后进入 CLOSE_WAIT，等自己发完数据、发 FIN 后进入 LAST_ACK；A 收到 B 的 FIN 后回 ACK，进入 TIME_WAIT，等 2MSL 后才 CLOSED；B 收到最后那个 ACK 就 CLOSED。

5.3 TIME_WAIT 为什么非要等 2MSL

MSL 是最长报文寿命（Maximum Segment Lifetime）。A 发完最后一个 ACK 后，要等足 2MSL，理由有二：

  • 保证最后那个 ACK 能到 B——万一它丢了，B 会重发 FIN，A 在 2MSL 内还能再补一个 ACK；要是 A 过早 CLOSED，就收不到这个重发的 FIN 了。
  • 防止"已失效的连接请求报文段"混进下一个新连接——等 2MSL，本连接持续时间内产生的所有报文段都会从网络中消失，新连接里就不会出现旧报文。
课件还列了断连的容错场景：DR（断连请求）/DC（断连证实）/ACK 在网络中会丢——发送方都启动计时器兜底，超时后重发 DR，或干脆超时删除连接。和建连时拒绝"重复 CR"用 RJ 一样，都是为了在不可靠网络上把连接的生杀做得稳当。
模块 6 拥塞控制四算法

网络堵不堵，发送方自己心里要有数

流量控制照顾的是接收方收不收得下；拥塞控制照顾的是整个网络扛不扛得住。如果大家一个劲往网络里塞包，路由器和链路过载，就会恶性循环——丢包 → 重传 → 更堵。拥塞控制的目标是：网络空闲时尽量多塞、物尽其用；网络一拥塞就立刻降速，别火上浇油。这背后是"报文段守恒"原则：每个发送方都要清楚网络里还能容纳多少。

把网络想成一条高速公路

刚上高速时空着，你可以从 1 辆车开始、每过一会儿就翻倍往上加（慢启动）；看到车流渐密，就改成稳稳地一辆一辆加（拥塞避免/加法增大）；一旦追尾（超时），说明路堵了，立刻把目标车速砍一半（乘法减小），从头缓加速。这就是 TCP 拥塞控制 AIMD（加法增大、乘法减小）的直觉——它能把各条流的速率收敛到一个相对公平、有效的分配。

6.1 先分清四个术语

术语含义
cwnd 拥塞窗口发送方根据网络拥塞情况，自己允许发的最大数据量
rwnd 接收窗口接收方通告的、它还能收的字节数（流量控制）
SMSS 最大数据段一个报文段里数据的最大长度
ssthresh 慢启动阈值慢启动和拥塞避免之间的切换开关
发送窗口上限 = min(rwnd, cwnd)
rwnd < cwnd：接收能力卡住；cwnd < rwnd：网络拥塞卡住

6.2 慢启动：指数爬升

连接刚开始，发送方把 cwnd 设成 1 个 SMSS。只要一个往返时间内没有丢包，cwnd 就翻倍：第 1 轮后 2、第 2 轮后 4、第 3 轮后 8……按指数增长，直到 cwnd 达到 ssthresh，才转入拥塞避免。起步虽叫"慢启动"，其实指数涨得很快，所以涨到阈值就得刹车。

6.3 拥塞避免：线性爬升（加法增大）

cwnd 达到 ssthresh 后进入拥塞避免：每个往返时间（收到一轮全部确认）cwnd 只增加 1 个 MSS，改成线性缓慢增长，防止网络过早再次拥塞。一旦检测到丢包（超时），就把 ssthresh 设成当前 cwnd 的一半，cwnd 重置回 1，重新慢启动。

口诀动作触发
加法增大每 RTT，cwnd +1 MSS（线性）拥塞避免阶段、一切正常
乘法减小ssthresh = 当前 cwnd × 1/2只要超时（一次拥塞）就减半
"拥塞避免"不是说真能完全避免拥塞——它只是把窗口控制成线性增长，让网络更不容易拥塞而已。网络频繁拥塞时 ssthresh 掉得很快，注入网络的包数随之大减。

6.4 课件例题：超时后 4 轮，窗口多大？

题目：MSS = 1KB，发生超时前拥塞窗口 cwnd = 16KB，现在发生超时。若接着 4 个轮次传输都成功，窗口多大？

解题：超时 → 乘法减小，ssthresh = 16/2 = 8KB，cwnd 重置为 1KB，重新慢启动。

第 1 轮成功 → cwnd=2；第 2 轮 → 4；第 3 轮 → 8（正好等于 ssthresh，切换到拥塞避免）；第 4 轮 → 拥塞避免加法增大，cwnd = 8+1 = 9KB。

课件答案正是 9KB。追问"若接着 6 轮都成功呢？"——第 5 轮 10、第 6 轮 11，即 11KB。下面分步演示把这条曲线走一遍。

6.5 快重传与快恢复：别干等超时

超时往往意味着网络已经很堵了。可有时只是某一个包丢了，后面的包都好好的——这时干等超时就太亏了。快重传的规则：接收方每收到一个失序的报文段，就立刻发一个重复确认（确认那个还没收到的序号）；发送方一旦一连收到 3 个重复确认，就立刻重传那个丢失的报文段，不必等计时器超时。

快重传例子（课件 M1~M7）

发送方依次发 M1、M2、M3、M4、M5、M6，其中 M3 丢了。接收方收到 M4 时发现序号不连续，就回一个"确认 M2"（表示我只收到 M2）；收到 M5、M6 又各回一个"确认 M2"。发送方连收 3 个对 M2 的重复确认，立刻重传 M3——这比干等超时快得多。注意快重传并没有取消重传计时器，只是让它在"只是丢了一个包"的情况下更早重传。

快恢复：既然是"3 个重复确认"才触发，说明后面还有包在正常到达，网络很可能并没有真的拥塞。于是发送方执行乘法减小（把 ssthresh 减半），但不执行慢启动——cwnd 不重置为 1，而是直接设成减半后的 ssthresh，然后进入拥塞避免（加法增大），让窗口缓慢线性回升。这就是 TCP Reno 的做法；而老的 Tahoe 版本无论超时还是 3 个重复确认，都把 cwnd 置 1 重走慢启动，已废弃。

一句话对比：超时＝网络真堵了 → 乘法减小＋慢启动（cwnd=1）；3 个重复确认＝大概只丢了一个包 → 乘法减小＋快恢复（cwnd 不回 1，直接拥塞避免）。
模块 7 QUIC 与 socket 程序设计

新一代传输协议 QUIC，以及怎么调用传输层

7.1 QUIC：为了解决"HTTP over TCP"的痛点而生

QUIC 是 Google 为解决 HTTPS over TCP 性能不佳而研究的、基于 UDP 的传输层协议。在协议栈里它主要替代的是 HTTP/2 + TCP + TLS 这一摞，核心解决两件事：低时延建立连接、多路复用避免 TCP 队头阻塞。随着在 IETF 标准化，QUIC 已从 HTTP 专用变成通用传输协议。

为什么需要 QUIC

打开一个网页要同时加载几十张图。HTTP/1.1 每个 HTTP 消息建一条 TCP 连接，握手开销大；HTTP/2 改成一条 TCP 连接复用多个消息，省了连接，但只要一个包丢了，这条 TCP 上所有后续消息都得等它重传——这就是 TCP 队头阻塞。QUIC 在一条 UDP 连接上开多条独立的"子流（stream）"，某条子流丢包只等它自己重传，不拖累别的流。

QUIC 的几个关键特性

  • 低时延建连：把传输层握手和加密握手合二为一，首次连接只需 1 RTT（TCP+TLS 要 2~3 个 RTT）；复用连接时本地缓存了密钥等参数，可做到 0 RTT 直接发数据。
  • 连接迁移：连接用连接 ID 标识，而不是"IP+端口"四元组。比如客户端从 Wi-Fi（IP1）切到手机网络（IP2），服务器靠包首部的 SCID 仍认出是同一个连接——这之所以可行，根本原因是底层 UDP 本来就是无连接的。
  • 无队头阻塞的多路复用：一个 Connection 可复用多个 Stream，各 Stream 互相独立；单条 Stream 内部仍存在队头阻塞。
  • 应用层拥塞/流量控制：QUIC 不再依赖内核算法，而是在应用层实现；流量控制基于"限制（limit）"——接收方通告对单条流和整个连接可接收的总字节数，发送方不得超过（分流控制和连接控制两级）。
  • 可靠传输：每条流有唯一 Stream ID，客户主动发起的流 ID 为奇数、服务器为偶数；包大小要满足 MTU（IPv6 下 ≤1350 字节、IPv4 下 ≤1370 字节）；靠单调递增的包号 PKN 加 SACK 保证完整性和有效性，还能精确估算 RTT、解决 TCP 的重传歧义。

QUIC 报文格式速览

部分要点
两种首部长首部（建连之前用）：Header Form=1，含 Fixed Bit、长包类型（0 Initial / 1 0-RTT / 2 handshake / 3 Retry）、Version ID、DCID/SCID 及其长度；短首部（建连之后用）：Header Form=0，含 Spin Bit、Key Phase、DCID、包号、包载荷
流帧类型1 字节，格式 1 f d ooo ss：最高位 1 表示流类型帧；f 是 Fin（半关闭）；d 表示是否带数据长度；ooo 编码偏移量长度；ss 编码流 ID 长度
帧内容Stream ID（哪个资源请求）、Offset（在本流中的字节偏移）、Length、Stream Data（真正的应用数据）

7.2 socket：应用程序调用传输层的接口

传输层提供两种服务，对应两类 socket：面向连接的用 TCP，无连接的用 UDP。课件给了两套编程流程：

服务器：socket() → bind() → listen() → accept()（阻塞等客户连接）→ read()/write() 收发数据。

客户：socket() → connect()（主动连服务器）→ write() 发请求 / read() 读回答。

特点：先 connect/accept 把连接建好，再像读写文件一样 read/write。

服务器：socket() → bind() → recvfrom()（阻塞等客户数据）。

客户：socket() → bind() → sendto() 发请求 → recvfrom() 收回答。

特点：没有 connect/accept，每个包都用 sendto/recvfrom，连对方地址一起带上。

最后：把整张知识地图收进脑子里

一层定位：传输层在通信子网与资源子网之间，把"主机到主机"升级成"进程到进程"，靠端口号（TSAP）寻址，提供面向连接 / 无连接两类服务。

两个协议：UDP 无连接、面向报文、不可靠、8 字节首部（源/目的端口、长度、校验和，校验加 12 字节伪首部）；TCP 面向连接、可靠、全双工、字节流，首部 20 字节起（端口、序号、确认号、数据偏移、6 标志、窗口、校验和、紧急指针、选项）。

可靠四件套：差错控制（校验和）、次序控制（序号分段拼接）、丢失控制（超时重传）、重复控制（序号去重）；重传时间靠 RTTS（α=1/8）+ RTTD（β=1/4）算 RTO=RTTS+4·RTTD，Karn 算法重传包不取样、RTO 翻倍。

连接管理：三次握手（SYN seq=x → SYN+ACK seq=y ack=x+1 → ACK ack=y+1）；四次挥手（FIN→ACK→FIN→ACK），主动方 TIME_WAIT 等 2MSL。

拥塞控制 AIMD：慢启动指数涨、拥塞避免线性涨（加法增大）、超时则 ssthresh 减半（乘法减小）cwnd 回 1；快重传收 3 个重复确认立即重传、快恢复不回 1 直接拥塞避免；发送窗口上限 = min(rwnd, cwnd)。

新协议与接口：QUIC 跑在 UDP 上，多路子流避免队头阻塞、1RTT/0RTT 建连、连接迁移；应用层通过 socket 调用——TCP 用 connect/accept/read/write，UDP 用 sendto/recvfrom。
