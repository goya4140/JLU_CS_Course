CHAPTER 7 · APPLICATION LAYER

应用层：真正为你所用的
那些网络服务，都长在这一层

前面几层都是"铺路"，到了应用层才是你每天真正在用的东西——上网查域名、收发邮件、浏览网页、下载文件、看视频。这一层不再讲底层怎么传比特，而是规定"两个应用进程之间该按什么规矩对话"。这一版我们把 DNS、邮件、HTTP、FTP、流媒体、CDN/P2P 一条线串起来，看每种服务到底在解决什么问题。

先建立整体印象：应用程序怎么对话

在 TCP/IP 分层模型里，应用层在传输层之上，是最高层——再往上就是某个具体应用了。它要做的事很朴素：规定不同主机上的应用进程通信时该遵循的协议和约定。那两个进程到底怎么分工？课件给出三种模式。

C/S 客户/服务器主从式，服务器一直等着服务
B/S 浏览器/服务器C/S 的特例，客户端就是浏览器
P2P 对等每个节点既服务别人，也请求服务

C/S：服务与被服务的关系

C/S 是主从架构：服务器是"主"，一直运行着、被动等待请求；客户是"从"，主动发起请求。客户必须知道服务器的 IP 地址才能发请求；服务器却不需要事先知道客户在哪，谁来都接。服务器以多进程方式同时服务多个客户，是个可缩放的架构。传统的文件传输、电子邮件、远程登录大多基于 C/S。

B/S：把客户端换成浏览器

B/S 就是 C/S 的特例——客户端软件换成了浏览器，采取"浏览器请求、服务器响应"。通常是三层架构：展现层（浏览器只管显示网页）、处理层（Web 服务器跑业务逻辑）、数据层（数据库服务器管数据）。好处是界面统一、升级只需改服务器端、用标准 TCP/IP+HTTP 易扩展。

P2P：人人都是客户，人人也是服务器

P2P 是分布式对等模型：任意两个运行 P2P 软件的主机都能直接通信，不区分谁是请求方、谁是提供方。从本质看它仍用了 C/S，但强调"对等"——每个进程既当客户又当服务器。音视频流量推动了 P2P 的发展，它把网络流量从"垂直方向（都找中心服务器）"变成"水平方向（节点之间互传）"。

用"餐厅"来类比三种模式

C/S 是你（客户）主动去餐厅（服务器）点餐，餐厅一直开门等着；B/S 是你不用装专门的点餐 App，直接用浏览器这个"万能客户端"下单；P2P 则像一个聚餐群，群里每个人既可以把自己家的菜分享给别人，也能从别人那里夹菜——没有一个固定的"大厨中心"。

服务器怎么同时伺候很多人：循环 vs 并发

工作方式典型协议做法
循环方式 iterative无连接 UDP一次只服务一个客户，请求在队列里排队，按先后顺序处理（阻塞）
并发方式 concurrent面向连接 TCP主进程在熟知端口等连接，每来一个客户就 fork 一个从属进程用临时套接字专门伺候，主进程继续等下一个
记住：UDP 简单、常配循环服务；TCP 连接多、常配并发服务（主进程＋从属进程）。后面每个应用协议，你都可以带着"它是 C/S 还是 P2P、用 TCP 还是 UDP、端口是几号"这三个问题去看。
模块 1 DNS 域名系统

把好记的名字，翻译成机器用的 IP 地址

计算机之间通信靠的是 IP 地址，可 IP 地址又长又没语义、谁也记不住。于是人们给机器取了有意义的名字（域名），但通信时还得用 IP。DNS 域名系统就是来解决这个矛盾的：把域名映射成 IP 地址。

DNS 就像 114 查号台

你想给"吉林大学官网"打电话，可你只记得名字、不记得号码。你拨 114 查号台（本地域名服务器），查号台要么自己查到号码告诉你（递归），要么说"这个我得帮你问总台、总台告诉你问哪个分台"（迭代）。DNS 是一个联机的、分布式数据库系统，不是哪一台机器单打独斗。

1.1 域名是一棵倒过来的树

早期 ARPANET 靠一个 hosts.txt 文件列出所有主机名和 IP，主机都去一个站点下载。互联网一变大，这文件就臃肿到没法管了。1987 年 RFC 1034/1035 发布 DNS，改用层次化、基于域的命名树加分布式数据库。域名从右往左、从大到小：

根（.）树根
顶级域.com .cn .edu …
二级域名.jlu .tsinghua …
三级/四级www mail cs …

域名各分量用小数点 "." 隔开，总长不超过 255 个字符，每个分量不超过 63 字符，合法域名至少含一个点。例如 www.jlu.edu.cn：cn 是国家顶级域、edu 是二级域、jlu 是三级、www 是四级。

顶级域名分三类

类别例子说明
国家顶级域 ccTLD.cn 中国 / .us 美国 / .uk 英国目前 300 多个
基础设施域 .arpain-addr.arpa、ip6.arpa专用于互联网基础设施（如反向解析）
通用顶级域 gTLD.com .net .org .edu .gov .mil .info …早期 20 个，2012 年起公司名也可做顶级域，截至 2020 已 1200 多个

我国 .cn 下的二级域名分三类：类别域名 7 个（.edu.cn 教育、.gov.cn 政府、.org.cn 非营利、.net.cn 网络、.com.cn 工商金融、.ac.cn 科研、.mil.cn 国防）；行政区域名 34 个（bj 北京、he 河北……每个两个字母）；以及无类别域名。域名由 ICANN 统一管理，.edu.cn 下三级域名归 CERNET 管，其余归 CNNIC 管。

1.2 四类域名服务器

类型管什么
根域名服务器知道所有顶级域服务器的地址；全球共 13 套（a~m.rootservers.net），靠任播部署成 1700 多个节点。它不直接给 IP，而是告诉你下一步去找哪个顶级域服务器

本地域名服务器每个 ISP 至少一个，离用户最近；主机发查询先交给它，也叫递归解析器

1.3 递归查询 vs 迭代查询

主机向本地域名服务器查，一般用递归查询（你就帮我查到到底，别让我来回跑）；本地服务器向根服务器查，一般用迭代查询（你告诉我下一步找谁，我自己再去）。DNS 查询用 UDP 数据报，目的端口 53（用 UDP 是为了省开销）。

课件实例：查 www.jlu.edu.cn → 客户机先问本地服务器（递归）→ 本地服务器迭代地问根 → .cn → .edu.cn → 权限服务器，最终拿到 IP 202.198.16.80，客户再用这个 IP 去发 HTTP 请求。

1.4 DNS 报文长什么样

DNS 报文分三部分：首部（基础结构）＋问题部分＋资源记录。查询和响应结构基本相同。首部 6 个字段各 2 字节：

标识 ID2B，请求与响应相同
标志 Flags2B
问题数2B
资源记录数2B
授权数2B
附加数2B

标志字段按位分：QR（0 请求 / 1 响应）、Opcode（0 标准查询 / 1 反向 / 2 服务器状态）、AA（授权应答）、TC（响应超 512 字节被截断）、RD（期望递归）、RA（服务器支持递归）、Z（保留必须为 0）、Rcode（返回码：0 无错 / 1 格式错 / 2 服务器失败 / 3 域名不存在 / 4 不支持查询类型 / 5 拒绝）。

问题部分：查询名（要查的域名）＋查询类型＋查询类（通常 1=IN 互联网地址）。资源记录只有响应里才有，格式是：域名、类型、类、生存时间 TTL、资源数据长度、资源数据。

高速缓存：每个域名服务器都缓存最近用过的名字映射，靠 TTL 决定缓存多久（课件举例每项约存两天），大大减轻根服务器负担、减少网络往返。DNSSEC 则用私钥签名、公钥验证（RRSIG/DNSKEY/DS），保证应答真实完整、防篡改。
模块 2 电子邮件：SMTP / POP3 / IMAP / MIME

异步通信的鼻祖：把信写好，慢慢送到

电子邮件是互联网上最广泛的应用之一，是一种异步通信——你发完不用等对方立刻看。它有三个主要构件：用户代理（邮件客户端，写/发/读邮件）、邮件服务器（保存和转发邮件）、邮件传输协议。

寄信的类比

你写好信（用户代理），先丢进自己这边邮局的邮筒（发件方邮件服务器的缓存队列）；邮局之间按 SMTP 把信一站站转到对方城市的邮局（收件方邮件服务器），存进你朋友的邮箱；朋友再用 POP3/IMAP 从自己邮局把信取回家看。注意：送信（SMTP）和取信（POP3/IMAP）是两套完全不同的协议。

2.1 一封邮件是怎么跑完的（六步）

  1. 发件人在用户代理里撰写、编辑邮件；
  2. 用户代理用 SMTP 把邮件发给发件方邮件服务器；
  3. SMTP 服务器把邮件临时存进邮件缓存队列等待发送；
  4. 发件方 SMTP 客户与收件方 SMTP 服务器建立 TCP 连接，把队列里邮件依次发出；
  5. 收件方 SMTP 服务器收到后，放进收件人的用户邮箱等待读取；
  6. 收件人用用户代理、通过 POP3 或 IMAP 把邮件从服务器取回。

2.2 邮件的组成：信封＋内容

信封MAIL FROM / RCPT TO（传输靠它）
首部 headerFrom/To/Date/Subject/Cc…
空行分隔首部与主体
主体 body邮件正文

信封上最重要的是收件人地址，传输全靠它；用户打开邮箱后才看到内容。邮件地址格式是 邮箱名@邮箱所在主机域名（@读"at"），如 jcst@jlu.edu.cn——主机域名在全球唯一，用户名在该域内唯一。RFC 5322 规定首部格式（From、To 必选，Subject、Cc、Date、Reply-To 可选），正文自由写。

2.3 SMTP：送信协议，端口 25

SMTP（简单邮件传送协议）基于 TCP，熟知端口 25，是基于 ASCII 文本的"命令—响应"协议。它分三个阶段：连接建立 → 邮件传送 → 连接释放。一个邮件服务器既能当客户（往外发）也能当服务器（收别人的）。下面分步看一次完整对话。

S: 220 Service Ready
C: HELO abc.edu.cn
S: 250 OK
C: MAIL FROM: Ling@jlu.edu.cn
S: 250 OK
C: RCPT TO: Wang@abc.com
S: 250 OK
C: DATA
S: 354 Start mail input; end with <CRLF>.<CRLF>
C: From/To/Date/Subject/正文… .
S: 250 OK
C: QUIT
S: 221 Service closed

应答是三位数代码：2xx 成功（220 服务就绪、250 操作完成、221 关闭信道）、3xx 中间（354 开始输入、以 "." 结束）、4xx 临时失败、5xx 永久失败（550 邮箱不可用等）。

2.4 取信协议：POP3 vs IMAP

POP3（邮局协议 v3）IMAP（网际报文存取协议）
端口110（RFC 1939）143（RFC 2060）
工作方式客户/服务器，基于 TCP客户/服务器，基于 TCP，联机协议，要先联网
邮件存哪一般下载到本地后服务器可删除留在服务器上，用户在服务器上建/管文件夹
特点三阶段：认证（user/pass）→ 事务（list/retr/dele）→ 更新（quit）；响应 +OK / -ERR只下载邮件首部（部分下载）、可按条件搜索、可只取 MIME 的一部分、维护会话状态

2.5 MIME：让邮件能发图片和附件

原始 SMTP 只能传 7 位 ASCII 文本。MIME（多用途互联网邮件扩展）沿用 RFC 822 格式，加上消息体结构和非 ASCII 编码规则，就能传多媒体、二进制文件了，还用原来的邮件程序和协议传送。

  • Quoted-Printable：可打印 ASCII 不动；等号和 >127 的字节，用两个十六进制数字前加 "=" 表示。如"系统"的 GB 码 CFB5CDB3 编码为 =CF=B5=CD=B3，等号本身编码为 =3D。
  • Base64：把 24 位二进制分成 4 个 6 位组（0~63），依次用 A~Z、a~z、0~9、+、/ 表示，末尾不足补 =。如 01001001 00110001 01111001 分成 010010 010011 000101 111001，编码为 STE5。

Content-Type 由类型/子类型组成：独立媒体五大类——text、image、audio、video、application；复合类型 multipart（mixed 混合 / alternative 选择 / parallel 并行 / digest 摘要）和 message。

模块 3 文件传输：FTP 与 TFTP

跨不同系统传文件：FTP 的两条连接

不同计算机存储格式、目录结构、命令、访问控制都不一样，直接传文件很麻烦。FTP（文件传输协议，RFC 959）就是为屏蔽这些系统细节而生，让异构网络中任意计算机之间都能传文件，基于 TCP 提供可靠传输。

FTP 的巧妙之处：用两条连接，而不是一条

你去邮局寄大包裹：一条专线（控制连接，端口 21）一直开着，专门用来"对话"——你发什么命令、我回什么话；真正搬包裹时，另开一条临时的数据连接（端口 20），搬完就拆。这样"说事儿"和"干活"互不干扰。控制连接在整个会话期间保持，数据连接传完文件就关闭。

控制连接TCP 21 端口，全程保持，传命令不传输文件
数据连接TCP 20 端口，传完即关，真正传文件

服务器主进程打开 21 端口等连接，客户用任意本地端口连上来；主进程收到请求后启动从属进程处理，处理完就结束，主进程回去继续等下一个客户（和前面"并发服务"一致）。

两种工作模式：谁主动发起数据连接

模式数据连接谁发起做法
主动模式 PORT服务器发起服务器用 20 端口去连客户用 PORT 命令告诉它的端口 Y
被动模式 PASV客户端发起服务器被动监听一个端口 Z，客户主动连 Z（常用于客户在防火墙/NAT 后）

常用命令速查

命令作用
USER / PASS发用户名 / 口令登录
LIST列目录文件清单（经数据端口返回）
RETR file从服务器取回文件（get）
STOR file把文件上传到服务器（put）
TYPE A / I文件类型：A=ASCII 码，I=图像（二进制）
PORT / QUIT / ABOR / SYST告知客户地址端口 / 注销 / 放弃当前传输 / 返回系统类型

应答码和 SMTP 类似按位：1yz 肯定预备、2yz 完成、3yz 中间、4yz 暂时否定、5yz 永久否定。

TFTP：极简的 UDP 文件传输

TFTP（简单文件传输协议）很小、易实现，用 C/S ＋ UDP（服务器端口 69），因为 UDP 不可靠所以它自己要做差错控制。它没有命令集、不能列目录、不做身份鉴别，只支持文件读写；每传一个 512 字节的"块（block）"就等确认（类似停止等待），块从 1 编号；最后一个不足 512 字节的块天然标志文件结束——若文件正好是 512 的整数倍，还要补发一个空数据块表示结束。

模块 4 万维网 WWW 与 HTTP

你每天在浏览器里做的事，就是这一层

Web 应用由三部分组成：Web 服务器（存着所有资源）、浏览器（在客户机上请求、解释并显示页面）、HTTP（客户浏览网页资源用的协议）。浏览器点一个链接后发生的事：分析 URL → 让 DNS 解析出 IP → 建立 TCP 连接 → 发 HTTP 请求 → 服务器返回 HTML 响应 → 浏览器解释显示 → 释放 TCP 连接。

HTTP 就像"按固定格式点菜"

你（浏览器）走进餐厅（服务器），不能随便说"给我来点吃的"，得照格式报：方法＋菜名（URL）＋协议版本；后厨回你也照格式：状态码＋说明＋菜（内容）。一来一回就是一次 HTTP 事务。这套规矩就是 HTTP。

4.1 URL：互联网资源的唯一地址

<协议>://<主机>:<端口>/<路径>

例如 http://www.XXXXX.com:8000/comics.php：协议是 http，主机是 www.XXXXX.com，端口 8000，路径是 /comics.php。确定主机后端口和路径可省略。浏览器还常帮你自动补全省略的 http:// 和 www。

4.2 HTTP 是什么：无状态、面向事务、跑在 TCP 上

HTTP 在传输层用 TCP，默认 80 端口，是面向事务的客户/服务器协议，能可靠交换文本、声音、图像等各类多媒体。两个关键性质：无状态——服务器不保留之前请求的状态；HTTP 本身"无连接"，虽然它用的 TCP 是面向连接的。

版本标准特点
HTTP/1.0RFC 1945（1996）无状态，默认非持久连接
HTTP/1.1RFC 2616（1999）默认持久连接＋流水线，缓存优化、断点续传
HTTPSHTTP＋TLS在 TCP 之上加 TLS 层提供安全
HTTP/2RFC 7540（2015）二进制格式、多路复用、头压缩、服务端推送，降延迟提带宽利用率

4.3 非持久连接 vs 持久连接

非持久连接（HTTP/1.0 默认）持久连接（HTTP/1.1 默认）
一个对象两阶段：建 TCP 连接 → 请求/传对象 → 关闭同一 TCP 连接上反复请求/响应，传完保持连接
慢启动每个对象都要经历一次 TCP 慢启动经历较少慢启动，省往返时间
流水线不支持支持流水线，但响应要按序
课件算例：一个页面含 index.html 加 2 幅 jpg 图像——HTTP/1.0 非持久要三次完整的 TCP 连接（三次握手＋三次 HTTP）。若一页有 100 张图呢？这就是非持久连接的痛点，也是 1.1 持久连接要解决的问题。

4.4 HTTP 报文：三部分结构

请求报文和响应报文都由开始行＋首部行＋实体主体三部分组成，各部分之间用空行（CRLF）分隔。

请求报文的开始行 = 请求行：方法 URL 版本

方法含义
GET请求读取由 URL 标识的信息（最常用）
HEAD只读取该信息的首部
POST给服务器添加信息（如提交表单、注释）
PUT在指定 URL 下存储一个文档
DELETE删除指定 URL 标识的资源
OPTIONS / TRACE / CONNECT请求选项信息 / 环回测试 / 用于代理服务器

响应报文的开始行 = 状态行：版本 状态码 短语

状态码类别含义典型例子
1xx通知信息：请求收到/正在处理—
2xx成功200 OK：请求成功，对象在响应数据里
3xx重定向，需进一步动作301 Moved Permanently：对象永久移走，新地址在 Location
4xx客户差错400 Bad Request：服务器看不懂；404 Not Found：找不到文档
5xx服务器差错505 HTTP Version Not Supported：不支持该 HTTP 版本

4.5 无状态带来的两件事：认证与 Cookie

HTTP 无状态，服务器默认记不住你是谁。要保护页面，常用 HTTP 认证：请求里不带凭证，服务器回 401 + WWW-authenticate，浏览器下次在请求头带上 Authorization: <凭证>。

但光认证还不够——你登录淘宝后一连点好几个页面，服务器怎么知道还是同一个人？这就靠 Cookie：服务器在响应首部用 Set-Cookie 发一个唯一编号给浏览器；之后浏览器每次请求都在请求头里带上这个 Cookie；Cookie 存在用户主机上，由浏览器管理，服务器后端数据库把它当关键字记录用户。

Cookie 一般 5 个字段：域（来自何方）、路径（服务器文件树中哪些部分可用）、内容（"名字=值"，最多 4K，只是字符串、不是可执行程序）、安全（只向安全连接返回）等。

Cookie 是把双刃剑：能做个性化推荐、记录购物车、保持登录；也能跨站跟踪用户浏览痕迹、泄露隐私。用户可以在浏览器里限制 Cookie。（注意：Cookie 里存的只是文本串，不是病毒，"Cookie 能嵌间谍程序"是误区。）

4.6 代理服务器 / Web 缓存

代理服务器又叫万维网高速缓存（Web cache），代理浏览器向源服务器发请求，把最近请求过的响应暂存在本地。新请求来时，若缓存里已有该对象就直接返回，不必再绕远路去互联网找——减少访问互联网服务器的时延、节省出口带宽。课件用校园网出口举例：所有流量本来都挤在一条 2 Mbit/s 的大链路上，放了缓存后，很多重复对象根本不用出校园。

附带一提：网页本身分静态文档（存好就不变）和动态/活动文档（服务器或浏览器端实时生成，典型技术 AJAX＝HTML+CSS＋DOM＋XML＋异步＋JavaScript）；浏览器架构则含用户界面、浏览器引擎、渲染引擎、网络、JS 解析器、数据存储（Cookie）等部件。
模块 5 流媒体应用

边下边播：为什么能不下载完就开始看

你在线看视频时，不用把整集下载完就能从头播——这就是流式存储媒体。课件把三种流媒体应用按延迟分了档：点播（<10 秒延迟，从任一点开始播）、直播（几秒延迟，像电视）、实时交互式会议（<400 ms，VR 要求 <25 ms，差一点就听着别扭）。

和"整集下载"对比

整集下载像先把整本书买回来才开始读；流式媒体像"读到第 1 页、同时后台在送第 2 页"。它在播放端设一个缓存：先攒一小段再播，网络偶尔抖一下，缓存里的余量就能顶住——把网络抖动抹平。代价是多了一点播放延迟。

5.1 视频怎么压：MPEG 的帧间编码

原始视频太大（一张 1024×768×24bit 图片 ≈ 2.4 MB，每秒 30 帧就是约 72 MB/s）。MPEG 视频压缩利用了相邻帧大同小异的特点，三种帧：

帧名字怎么编
I 帧帧内编码单独压缩成完整静态图像；必须周期性插入，是随机存取的入口
P 帧前向预测只记录和前一个 I/P 帧相比的变化
B 帧双向预测参考前后两个帧

一组连续帧叫 GOP（图像组）：1 个 I 帧后跟一串 P/B 帧，循环往复。I 帧是"完整锚点"，P/B 帧都依赖它——这就是为什么流里必须周期性插入 I 帧，否则一旦丢个关键帧后面就花了。

5.2 流式媒体的协议栈

层协议干什么
信令/播放控制RTSP / SIP / H.323控制播放、录制、暂停
实时数据传输RTP（在 UDP 上）端到端实时多媒体数据，不带 QoS 保证
QoS 监控RTCP监视服务质量、反馈、多流同步
媒体描述SDP描述会话信息

RTSP：互联网录像机的遥控器

RTSP（实时流协议）用一组方法控制播放（播放/录制/暂停），但它本身不传送媒体数据——数据走 RTP/RTCP。它是一个有状态的协议，会记录"这个用户现在在播第几秒"；而 HTTP 默认无状态。可以把 RTSP 想成"互联网录像机遥控器"。

RTP 与 RTCP：一对搭档

RTP 在端到端之间传输实时多媒体数据，不提供服务质量保证（没有重传）；RTCP 在 RTP 传数据的同时做 QoS 监视、反馈和多流（比如视频流＋音频流）同步。RTP 和 RTCP 配合使用，RTP 数据端口和 RTCP 控制端口紧挨。

WebRTC：浏览器里直接 P2P 通话

WebRTC（Google 捐出）让浏览器之间直接通音视频（实时交互式应用），用 SRTP/SRTCP 加密；还解决了"两边都在内网，怎么直接连"的问题：用 ICE 框架＋STUN（穿透 NAT 拿外网地址）＋TURN（实在打不通就中继）做内网穿透。

5.3 自适应码率：根据网速动态调清晰度

DASH 把一个视频编码成多个版本，切成 2~10 秒的片段，放在 HTTP 服务器上；客户端根据网络情况自动切换版本码率，就是 ABR（自适应码率流）。

  • 基于吞吐量：吞吐量变了，就切到更高/更低码率的版本。
  • 基于缓冲：靠播放缓冲区填得快不快判断——攒得快就切高码率（看着清晰），攒得慢就切低码率（不卡顿）。

SVC（可伸缩视频编码）是另一条路：把视频分成"一个基础层＋多个增强层"，解码端只收自己收得动的层数——这样同一份编码就能适应不同带宽，不用为每种码率单独编码。

模块 6 CDN 与 P2P

让内容离你更近，让节点互相帮忙

6.1 CDN：把内容搬到离用户最近的地方

假设你在长春看一个架在广州的视频源，光把数据搬过来就慢。CDN（内容分发网络）在全国各城市部署一堆边缘服务器（CDN 节点），把热门内容缓存到边缘；用户就近访问，时延大降，还能分担源服务器压力、防 DDoS。

它怎么把用户"引导"到最近节点？靠 GSLB（全局服务器负载均衡）＋CNAME 解析：网站把自己的域名 CNAME 到 CDN 域名，用户向 DNS 查询时，GSLB 根据用户位置返回最近的 CDN 边缘服务器地址，于是流量就被吸引到就近节点，减轻原始服务器负担。

6.2 P2P：节点之间互相传

互联网上的计算机本来都是独立的，P2P 应用把它们的虚拟连接组织成一张"覆盖网络（overlay network）"——逻辑上互联，物理上可能隔着千山万水。任意两个节点都能直接通信，不区分客户/服务器，每个节点既下载又上传。按结构分三类：

结构特点例子
集中式目录有个中心服务器记录"谁在哪、有什么资源"（但数据传输不经过它）早期 Napster
非集中式（洪泛）没有中心，请求在覆盖网络里逐跳广播，靠带宽大的超级节点Gnutella 早期
混合式超级节点＋集中目录＋洪泛结合Skype

BitTorrent：把文件切块，人人互传

下载者拿到一个小的种子文件 torrent，先找 tracker（跟踪服务器），它记录当前有哪些节点有这个文件。整个大文件被切成固定大小的块（block，通常 256 KB）；每个节点只持有部分块，大家互相交换自己缺的块——你上传的同时也在下载。

DHT：连 tracker 都不要

DHT（分布式哈希表）用 Kademlia 算法，给每个节点一个 160 位的节点 ID；文件也用哈希算出一个 160 位的"info hash"，谁存这个文件就把自己的节点 ID 和这个 hash 关联起来。查资源时，用"后继节点 successor"的思路，一步步把请求送到 ID 最接近该 hash 的节点，就能在一张巨大的 P2P 网络里找到谁有这个文件——完全不需要中心 tracker。

一句话收束：CDN 是"中心化地把内容推到边缘"，P2P 是"去中心化地让节点互传"；前者靠 GSLB/CNAME 就近引流，后者靠覆盖网络、分块和 DHT 自组织。两者都是为了把内容更快地送到用户手里。

最后：把整张知识地图收进脑子里

模式与端口：C/S（服务器一直等、客户主动发）/ B/S（客户端是浏览器）/ P2P（对等互传）；服务器可循环（UDP）或并发（TCP 主进程＋从属进程）。

DNS：域名→IP 的分布式数据库；层次命名树（根→顶级域→二级→…），四类服务器（根/TLD/权限/本地）；主机→本地用递归、本地→根用迭代，UDP 端口 53；报文＝首部(标识/标志/计数)＋问题＋资源记录；RR 类型 A/AAAA/CNAME/NS/MX/PTR/SOA；缓存靠 TTL。

电子邮件：用户代理＋邮件服务器＋协议；信封(MAIL FROM/RCPT TO)＋内容(首部/空行/主体)；SMTP 端口25 送信（连接建立/传送/释放，命令 HELO/MAIL/RCPT/DATA/QUIT，应答 2xx/3xx/4xx/5xx）；POP3 端口110 下载、IMAP 端口143 服务器上管理；MIME 用 Quoted-Printable/Base64 编码多媒体。

FTP/TFTP：FTP 两条 TCP 连接——控制连接 21 端口全程保持、数据连接 20 端口传完即关；主动 PORT/被动 PASV；RETR=get、STOR=put；TFTP 用 UDP 69 端口、512 字节块、停止等待。

WWW/HTTP：URL＝协议://主机:端口/路径；HTTP 跑 TCP 80、无状态、面向事务；1.0 非持久、1.1 持久＋流水线；报文＝开始行＋首部行＋实体主体；方法 GET/POST/PUT/DELETE…；状态码 2xx 成功/3xx 重定向/4xx 客户错/5xx 服务器错（200/301/400/404/505）；Cookie 维持状态，代理/Web 缓存就近服务。

流媒体与分发：MPEG 用 I/P/B 帧、GOP 里周期插 I 帧；RTSP 只控播放不传数据、有状态，RTP 传实时数据、RTCP 管 QoS 同步，WebRTC 浏览器 P2P 通话；DASH/ABR 自适应码率、SVC 分层；CDN 边缘节点＋GSLB/CNAME 就近引流，P2P 覆盖网络、BitTorrent 分块(256KB)、DHT(Kademlia 160 位) 去中心化查找。
