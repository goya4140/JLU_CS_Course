## 7.1 应用层概述

### 7.1.1 应用与协议：做什么、怎样说

**应用**是用户要完成的任务，例如收邮件；**应用层协议**是程序之间的交流规则，例如先发送哪条命令、回答用什么格式、失败后怎样处理。相同的业务可以采用不同协议，相同协议也能支撑多种产品。

**客户端/服务器（C/S）**是一种分工：客户端主动请求，服务器接收请求并提供服务。“服务器”首先是角色，可以是普通计算机上的程序，也可以是集群。某程序在一次通信中是服务器，在另一次通信中也可以成为客户端。

**浏览器/服务器（B/S）**把浏览器作为主要客户端。例如查成绩时，浏览器发送查询，业务服务检查身份并查询数据库，再把结果返回。浏览器、业务服务、数据库是应用的组织方式，不能当作 OSI 的三层。

**P2P（对等方式）**让参与者同时贡献资源：下载文件时也能把已收到的部分上传给别人。它分散了提供数据的工作，但查找伙伴、处理离线和核对数据也需要额外机制。

### 7.1.2 一个服务器怎样处理多人请求

**循环服务器**处理完一个请求再接下一个，容易理解；一个请求等待很久时，其他请求也可能被拖住。**并发服务器**通过多个执行任务或事件处理，让若干请求在重叠的时间内推进。

并发不等于多个 CPU 在同一瞬间执行；后者叫**并行**。程序等待网络数据时能否继续做别的工作，则涉及**阻塞/非阻塞**。这两组概念描述不同问题，不能把“并发”直接等同于“非阻塞”。

采用 TCP 时，服务器通常先监听，再接受连接；采用 UDP 时，可以接收数据报后回复。TCP/UDP 决定传输服务，并不直接决定服务器采用循环还是并发处理。

## 7.2 DNS：把域名解析为所需信息

### 7.2.1 为什么需要 DNS

人容易记住 `www.example.com`，网络转发主要使用 IP 地址。**DNS（域名系统）**是一套分布式查询系统，能够查出域名对应的地址、邮件服务器等信息。**解析**就是按名字和查询类型取得这些信息。

早期可以维护一份主机名与地址的 `Hosts.txt`；主机变多、地址频繁变化后，集中更新和分发越来越困难。DNS 把不同范围交给不同管理者，同时用缓存减少重复查询。

域名与物理主机并非一一对应：一个域名可以对应多个地址，多个域名也可以指向同一服务。

### 7.2.2 域名的层次与服务器角色

域名从右往左看，由大范围逐步缩小。例如 `www.example.edu.` 中，最后的点表示根，`edu` 是顶级域，`example` 是其下的名字，`www` 又是下一层。日常输入往往省略最后的点。

顶级域有国家或地区类，如 `cn`；有通用类，如 `com`；`arpa` 用于基础设施。ICANN、CNNIC 等涉及名字资源的协调或管理，不能直接当作每次查询都要访问的服务器。

| 角色 | 通俗理解 | 主要工作 |
|---|---|---|
| 根服务器 | 知道各顶级域去哪里问 | 返回相应顶级域的服务器线索 |
| 顶级域服务器 | 知道该顶级域下谁负责某个域 | 返回下一层的服务器线索 |
| 权威服务器 | 管理某个区域的正式记录 | 给出它所负责记录的答案 |
| 递归解析器 | 帮用户查完整答案的人 | 查询、跟随线索、缓存并返回结果 |

前三者解释命名层次；递归解析器是查询中的角色，不是域名树的“第四层”。

**域（domain）**是树中的一片名字范围；**区（zone）**是一次权威管理所负责的范围。若把一个子域交给另一组服务器管理，原区便不再直接保存该子域的全部记录，而通过 NS 记录说明应该去哪里问。这种交接叫**委派**。

课件中的“13 台根服务器”应理解为 13 个逻辑标识 `a.root-servers.net`～`m.root-servers.net`。**任播（anycast）**允许不同地点的服务器使用同一服务地址，由路由把请求送到其中一个，因此物理实例不止 13 台。参见 [IANA 根服务器资料](https://www.iana.org/domains/root/servers)。

DNS 的线缆格式把每一段名字称为**标签**。单标签最多 63 字节；完整未压缩名字连同长度字节和结尾根标签，最多 255 字节。这是字节限制，不能说成“最多 255 个汉字”；也不能要求任何域名都必须包含一个点。参见 [RFC 1035 的长度限制](https://www.rfc-editor.org/rfc/rfc1035.html#section-2.3.4)。

### 7.2.3 递归与迭代：谁继续查

**递归查询**相当于“请你替我查出最后答案”；**迭代查询**相当于“如果你不知道，请告诉我下一步去问谁”。典型过程如下，假设缓存中没有可用记录：

```text
电脑 → 递归解析器：请查 www.example.com 的地址
解析器 → 根服务器：得到 com 的服务器线索
解析器 → com 服务器：得到 example.com 的权威服务器线索
解析器 → 权威服务器：得到地址，或继续跟随别名
解析器 → 电脑：返回结果
```

电脑通常向解析器提出递归请求，解析器再向各级服务器迭代查询。不是每次访问都要完整走一遍：浏览器、操作系统或解析器已有缓存时，步骤可以减少。

**TTL（生存时间）**说明记录可以在缓存中保留多长时间，单位为秒，由记录设置。它不是统一的“两天”，也不是一个分组最多能跳多少次；这里只是与 IP 的 TTL 使用了相同缩写。

传统 DNS 使用 UDP 或 TCP 的 53 端口。UDP 回复被截断时，可以转用 TCP，不能记成“DNS 只使用 UDP”。

### 7.2.4 DNS 报文：先辨认四个区域

报文由 **12 字节首部**和四个数量可变的部分构成：问题、回答、权威信息、附加信息。首部中的四个计数分别说明这些部分包含多少条项目，每个计数占 16 位。

| 首部内容 | 含义 |
|---|---|
| ID | 匹配查询与响应的标识 |
| QR | 这是查询还是响应 |
| AA | 响应是否具有相应权威性 |
| TC | 响应是否被截断 |
| RD / RA | 请求是否希望递归 / 服务器是否支持递归 |
| RCODE | 处理结果，例如成功、域名不存在 |

常见 RCODE：0 成功，2 服务器失败，3 名字不存在，5 拒绝处理。不要把“名字不存在”与“暂时查询失败”混为一谈。

**问题项**包含 QNAME（问哪个名字）、QTYPE（问哪种记录）、QCLASS（哪种类别，互联网通常为 IN）。回答等部分使用**资源记录 RR**：

```text
NAME | TYPE | CLASS | TTL | RDLENGTH | RDATA
名字   类型   类别    缓存时间  数据长度    具体数据
```

TYPE、CLASS、RDLENGTH 各占 16 位，TTL 占 32 位；RDATA 的解释由 TYPE 决定。因此看见一串数据时，先看记录类型，再判断是地址、域名还是其他信息。

“UDP DNS 最多 512 字节”指没有扩展机制时的经典限制。**EDNS**用 OPT 伪资源记录等机制扩展 DNS，允许说明可接收的 UDP 载荷大小；仍会受到网络与实现条件限制。参见 [RFC 6891](https://www.rfc-editor.org/rfc/rfc6891.html)。

### 7.2.5 常见记录与别名过程

| 记录 | 回答什么 |
|---|---|
| A / AAAA | IPv4 地址 / IPv6 地址 |
| CNAME | 这个名字的规范名字，即别名最终指向的名字 |
| NS | 哪个名字服务器负责相应区域 |
| MX | 邮件服务器名字及其优先级数值 |
| SOA | 区域的管理和更新信息 |
| TXT | 文本信息 |
| PTR | 常用于由地址反查名字 |

例如记录为：

```text
www.example.com  CNAME  web.example.com
web.example.com A      192.0.2.10
```

查 `www.example.com` 的 A 记录时，可能先得到 CNAME，再得到规范名字的地址。**CNAME 存放的是名字，不是 IP 地址。**附加部分可以提供继续处理所需的信息，并不只能放名字服务器地址。

反向查询 IPv4 地址 `192.0.2.10` 时，按字节逆序组织名字 `10.2.0.192.in-addr.arpa`，查询其 PTR 记录。这里逆序的是四个十进制字节，不是把整个字符串逐字符倒过来。

### 7.2.6 DNSSEC：验证答案是否可信

普通 DNS 查询得到一个答案，仍要面对“记录是否由对应管理者提供、传途中有没有被改动”的问题。**DNSSEC**用数字签名验证记录来源与完整性。

**数字签名**可理解为：管理者用私钥生成证明，验证者用公开的公钥检查证明。RRSIG 保存签名，DNSKEY 保存公钥，父区的 DS 记录把信任关系连接到子区；从预先信任的起点向下验证，形成信任链。

它还需要检查签名有效期和信任配置。DNSSEC 本身不负责加密查询内容，也不保证网站内容安全；如果要隐藏查询内容，需要其他机制。

## 7.3 电子邮件：发信、取信、表示内容

### 7.3.1 一封邮件经过哪里

**用户代理 UA**是用户操作的邮件程序；**邮件服务器**负责接收、暂存和转交邮件。收发双方不必同时在线：服务器可先保存，再等待取信或重试转交。

```text
发件人的邮件程序
    ↓ SMTP 提交
发件邮件服务器
    ↓ 查收件域的 MX，使用 SMTP 转交
收件邮件服务器
    ↓ POP3 / IMAP 获取或同步
收件人的邮件程序
```

SMTP 负责提交、转交；POP3 和 IMAP 主要解决用户怎样访问已到达邮箱的邮件。邮件服务器之间的经典 SMTP 端口为 TCP 25；不能由此推断所有用户发信连接都使用 25 端口。

### 7.3.2 信封与正文首部：两套地址各有用途

SMTP 的 `MAIL FROM`、`RCPT TO` 构成投递所用的**信封**；消息内部的 `From:`、`To:` 等属于**邮件首部**，用于向用户描述这封信。就像快递外包装的收件信息与盒子里信纸上的称呼，不必完全相同。

| 邮件首部 | 用途 |
|---|---|
| From / Sender | 内容所标明的作者 / 发送者 |
| To / Cc / Bcc | 主要收件、抄送、密送信息；密送地址通常不会展示给其他收件人 |
| Date / Subject | 日期 / 主题 |
| Reply-To | 希望接收回复的地址 |
| Message-ID | 标识这条消息 |
| In-Reply-To / References | 关联回复链 |
| Received | 记录邮件经过的处理节点 |
| Return-Path | 记录返回路径，供退信等处理 |

这些字段并非都必须出现，字段文本本身也不能单独证明发件人身份。首部之后有一个空行，再开始消息正文。

### 7.3.3 SMTP：命令、响应、结束标记

SMTP 使用 TCP，一般由客户端发命令、服务器回状态码。下面省略具体域名和地址，展示一次投递的主要过程：

```text
服务器：220   服务就绪
客户端：EHLO  报告身份并询问扩展能力
服务器：250   可以继续
客户端：MAIL FROM:<发件地址>
服务器：250
客户端：RCPT TO:<收件地址>
服务器：250
客户端：DATA
服务器：354   开始发送邮件内容
客户端：邮件首部、空行、正文
客户端：.     单独一行，表示内容结束
服务器：250   已接受这封邮件
客户端：QUIT
服务器：221   结束会话
```

HELO 是基本问候，EHLO 用于扩展 SMTP。多个收件人可以重复发送 `RCPT TO`，不需要把整个正文重复提交多次。

状态码首位有规律：2 表示成功；3 表示需要继续输入；4 表示暂时失败，可按策略重试；5 表示永久失败。收到最终 250，表示服务器接受处理，**不等于收件人已经阅读**。

协议中的行结束符是 CRLF，即回车与换行两个字符。正文中若某行以点开头，发送方在前面再加一个点，接收方移除加上的点；这样正文中的点不会被误认成结束标记。这叫**点透明处理**。

### 7.3.4 POP3 与 IMAP：下载和同步

**POP3**偏重从邮箱取信，经典端口为 TCP 110。会话经历认证、事务、更新三个阶段。主要命令如下：

| 命令 | 做什么 |
|---|---|
| USER / PASS | 提供用户名与密码进行认证 |
| STAT / LIST | 获取邮件数量、总大小或各邮件大小 |
| RETR | 取回某封邮件 |
| DELE / RSET | 标记邮件待删除 / 撤销本次删除标记 |
| UIDL | 获取可用于识别邮件的唯一标识 |
| TOP | 获取首部与部分正文，是可选命令 |
| QUIT | 正常退出，在相应阶段提交更新 |

取回邮件不必然删除邮件。DELE 先做标记，正常进入更新阶段后才执行相应移除；客户端也可以配置保留服务器副本。

**IMAP**偏重“服务器上的邮箱与多个设备保持一致”，经典端口为 TCP 143。它支持文件夹、已读标记、搜索以及只取所需部分；本地缓存仍可支持离线阅读。

可按功能记命令：CAPABILITY 查能力，LOGIN/AUTHENTICATE 做认证，SELECT/EXAMINE 选择邮箱，LIST/SEARCH 查目录或邮件，FETCH 取内容，STORE 改标记，COPY/APPEND 复制或追加消息，EXPUNGE 清除已标记删除的消息，LOGOUT 退出。先理解这些操作，不必把所有命令一次背完。

### 7.3.5 MIME：正文和附件怎样装在一封信里

早期邮件主要处理文本；图片、音频、附件需要说明数据类型和表示方法。**MIME**是一组扩展规则，让同一消息可以容纳不同内容。

- `Content-Type`：这是哪种内容；可附带字符集 charset 或分隔符 boundary。
- `Content-Transfer-Encoding`：这些字节怎样表示，便于传输。
- `multipart`：消息由多个部分组成，以 boundary 划分；各部分又有自己的首部。

常见顶级类型有 text、image、audio、video、application、multipart。`multipart/mixed` 用于组合正文与附件；`multipart/alternative` 的不同部分是同一内容的不同表示，例如纯文本版和 HTML 版。课件中的 parallel、digest 也属于多部分组织方式，不是新的传输协议。

**字符编码**先把文字变成字节，**传输编码**再把字节变成适于传输的字符。两者不能混用。

**Quoted-Printable**可以用 `=十六进制字节` 表示字节，等号自身写作 `=3D`。例如“系统”采用 GBK 时：

```text
字节：CF B5 CD B3
二进制：11001111 10110101 11001101 10110011
表示：=CF=B5=CD=B3
```

采用 UTF-8 时原始字节不同，结果也会不同。以上更正了课件第 86 页原例的二进制表示。

**Base64**把三个字节的 24 位分成四组，每组 6 位，查表得到四个字符。表依次使用 `A～Z`、`a～z`、`0～9`、`+`、`/`。

```text
原字节：49 31 79（十六进制，对应文本 I1y）
位分组：010010 010011 000101 111001
索引：  18     19     5      57
字符：  S      T      F      5
结果：STF5
```

课件原例的 `STE5` 应改为 `STF5`。剩一个原始字节时补两个 `=`，剩两个时补一个 `=`。不计换行，n 字节编码后长度为 `4 × ⌈n/3⌉`，通常增加约三分之一。**编码不等于加密**，知道编码规则就能还原字节。参见 [RFC 4648 的 Base64 规则](https://www.rfc-editor.org/rfc/rfc4648.html#section-4)。

## 7.4 FTP 与 TFTP：传输文件

### 7.4.1 FTP 为什么有两种连接

**FTP**把发命令和传数据分开：**控制连接**使用 TCP，服务器经典监听端口为 21；**数据连接**传文件内容或目录列表。控制连接可持续存在，数据连接按操作建立和结束。

因此 `LIST` 虽然是在控制连接上发出的命令，目录列表仍通过数据连接传输。RETR 表示下载，STOR 表示上传；USER/PASS 做登录，TYPE I 选择二进制传输类型，QUIT 退出。

### 7.4.2 主动与被动：谁发起数据连接

| 模式 | 客户端告诉服务器什么 | 数据 TCP 连接由谁发起 |
|---|---|---|
| 主动 | PORT 提供客户端接收地址与端口 | 服务器连接客户端；经典服务器数据端口为 20 |
| 被动 | PASV 请求服务器给出监听地址与端口 | 客户端连接服务器给出的地址与端口 |

PORT/PASV 的端口由两个字节 p1、p2 表示，实际端口为 `256p1+p2`。例如 p1=195、p2=80，则端口为 `195×256+80=50000`。

主动模式需要服务器能够连接客户端给出的端点，因此 NAT、入站过滤等可能带来困难；被动模式由客户端发起。这里是机制区别，不能记成“FTP 的数据一定走 20 端口”。

### 7.4.3 TFTP：在 UDP 上做简单确认

**TFTP**是更简单的文件传输协议，初始请求发往 UDP 69；后续传输使用双方为此次会话选定的传输标识端口，并非所有数据都经过 69。它没有 FTP 那套登录和目录操作。

主要报文是读请求 RRQ、写请求 WRQ、数据 DATA、确认 ACK、错误 ERROR。基本方式接近停等：发送一个编号数据块，收到相应 ACK，再发下一个；超时则重传。UDP 自身不提供可靠交付，应用协议仍能添加确认和重传。

基本 TFTP 的每个数据块最多 512 字节；**最后一个数据块不足 512 字节**表示结束。如果文件恰好有 1024 字节：

```text
DATA 1：512 字节 → ACK 1
DATA 2：512 字节 → ACK 2
DATA 3：  0 字节 → ACK 3，结束
```

不能仅因“前两块已经有 1024 字节”就省略结束块。扩展选项可以协商其他块大小，做题先看是否采用基本协议。参见 [RFC 1350 的传输结束规则](https://www.rfc-editor.org/rfc/rfc1350.html#section-6)。

## 7.5 Web 与 HTTP：网页怎样到达浏览器

### 7.5.1 Internet、Web、URL 各是什么

**Internet**是互连网络基础设施；**Web**是在其上使用网页和链接组织信息的应用体系；**浏览器**是访问和呈现这些内容的程序。网络还承载邮件、文件传输等，不能把 Internet 与 Web 完全画等号。

**URL**说明要以什么方式访问哪个资源。例如：

```text
https://www.example.com:8443/course?id=7#section2
协议     主机名          端口 路径   查询     片段
```

`https` 表示采用受 TLS 保护的 HTTP；8443 是显式端口；`/course` 是路径；`id=7` 是查询部分；`section2` 是片段，通常由浏览器在得到资源后处理，不作为 HTTP 请求目标发送给服务器。主机名大小写通常不敏感，路径是否区分大小写取决于服务规则。

### 7.5.2 网页内容与生成方式

**HTML**描述内容结构，例如标题和段落；**CSS**控制呈现方式，例如颜色和排版；**JavaScript**在浏览器中执行行为，例如点击后请求新数据。

**静态页面**的主要内容预先保存；**动态页面**由服务器根据查询、用户身份或数据生成；课件所说的**活动页面**强调客户端执行程序。这些能力可以同时存在于一个网站中。

**XML**用于表示有结构的数据；**AJAX**强调浏览器异步取数据并局部更新页面。它不要求数据一定是 XML，也不需要每次整页刷新。

浏览器包含网络、页面解析、渲染、脚本执行与存储等功能。服务器可能经 CGI 或其他接口把请求交给业务程序，再查询数据库。CGI 是服务器与程序的接口机制，不是网络协议层。HTTP 的 Content-Type 帮接收方判断正文类型。

### 7.5.3 无状态、Cookie、会话

**HTTP 无状态**指协议本身不会自动把连续请求关联成同一用户的交互过程。两次请求即使复用一个 TCP 连接，也不会仅因此完成用户身份管理。

网站可以用 **Cookie**保存一个会话标识，再让服务器关联状态：

```text
第一次请求 → 服务器返回 Set-Cookie: sid=某个标识
浏览器保存 → 后续符合条件的请求携带 Cookie: sid=某个标识
服务器查 sid → 找到对应会话，例如登录状态或购物车
```

**会话（session）**是应用对一段交互的管理，不等于一条 TCP 连接。一个会话可能跨多条连接，一条连接也能承载多个请求。

Cookie 的 Domain、Path 限定适用范围，过期时间决定保存期限；Secure 限制在安全连接上发送，HttpOnly 限制普通脚本接口访问。理解它们各自约束什么即可，任何单个属性都不能保证整体安全；Cookie 值也不必然是加密数据。

### 7.5.4 HTTP 连接与 RTT：先画请求顺序

**非持续连接**在经典模型中为每个对象重新建立连接；**持续连接**让多个请求复用连接。**流水线**允许前一个响应未收到时就发出后续请求，HTTP/1.1 的响应仍按请求顺序交付。

**多路复用**进一步让多个请求对应的流交错传输。HTTP/2 在同一 TCP 连接上多路复用，但 TCP 丢失某些字节仍可能使其他流等待，称为传输层的**队头阻塞**。HTTP/3 使用 QUIC 的多个流，减少不同流因同一 TCP 字节序列而相互等待；仍可能受到拥塞控制等共同条件影响。参见 [HTTP/3 标准](https://datatracker.ietf.org/doc/html/rfc9114)。

做课件的 RTT 题时，必须先列模型：**忽略 DNS、TLS、服务器计算和排队，数据传输时间可忽略；TCP 建连计 1 RTT，请求到响应计 1 RTT。**RTT 是往返时间。如果对象有 L bit、有效传输率为 R bit/s，简单单对象模型还需加上 L/R。

**例：同一服务器上的 1 个 HTML 加 2 个小图片。**先得到 HTML，才知道图片地址；所有对象按题设安排获取。

| 方式 | 时间线 | 总计 |
|---|---|---:|
| 非持续，三个对象串行 | 每个对象各建连与请求一次 | 6 RTT |
| 持续，无流水线 | 建连 1 + HTML 1 + 图片各 1 | 4 RTT |
| 持续，图片流水线 | 建连 1 + HTML 1 + 两图片请求共同计 1 | 3 RTT |

如果允许并行连接、已有缓存、TLS 握手或对象传输时间不可忽略，结果就会变化。这三个数字不能脱离题设套用。

### 7.5.5 HTTP/1.x 报文：起始行、首部、空行、正文

请求的起始行写方法、请求目标和版本；响应的起始行写版本、状态码和简短说明。首部之后的空行把元信息与正文分开。

```http
GET /hello HTTP/1.1
Host: www.example.com
Accept: text/plain

```

一个简化响应可以是：

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 5

hello
```

这里正文假定仅含 `hello` 的 5 个字节，代码块的排版换行不算额外正文。Content-Length 计的是字节，不是汉字个数。HTTP/2、HTTP/3 使用其他帧结构，不能把以上文本格式原样当作所有版本的线上格式。

| 方法 | 通常表达的意图 |
|---|---|
| GET | 获取资源的表示 |
| HEAD | 类似 GET，但响应不带该资源正文 |
| POST | 提交内容，让目标资源按其规则处理 |
| PUT | 创建或替换指定目标的表示 |
| DELETE | 请求移除目标资源的关联 |
| OPTIONS | 询问通信选项；拼写带 S |
| TRACE | 用于诊断请求经过的处理 |
| CONNECT | 建立隧道，例如经代理转发连接 |

具体业务结果由服务器实现与权限决定。方法名字说明语义，不能把所有操作都简化成“网页增删改查”。

状态码首位：1 信息响应，2 成功，3 重定向或缓存相关处理，4 客户端请求相关错误，5 服务器处理错误。常见值包括 200 成功、301/302 重定向、304 无需重传表示、400 请求有问题、403 拒绝访问、404 目标未找到、500 服务器内部错误。收到 404 说明收到了一条 HTTP 响应，不等于网络完全不通。

### 7.5.6 缓存与代理：少传一次相同内容

**代理**替请求方或服务方中转请求；**缓存**保存可复用的响应。代理可以带缓存，但两者不是同义词。

缓存先根据新鲜度规则判断能否直接复用；需要确认内容是否变化时，可以带上旧内容的验证标识。**ETag**是服务器给某个表示的标识，例如浏览器把先前的 ETag 放入 `If-None-Match`：

```text
内容没变 → 服务器返回 304 → 浏览器复用已有正文
内容已变 → 服务器返回新正文与新的缓存信息
```

304 本身不重新携带完整资源正文。缓存能否共享还取决于响应规则、授权、Cookie 以及 Vary 等字段；Vary 指出哪些请求首部影响响应的选择。因此“URL 相同”不必然意味着所有用户都能复用相同内容。

## 7.6 网络流媒体：边收边播

### 7.6.1 吞吐、时延、抖动与缓冲

**流媒体**不必等整个文件下载完成才播放。点播内容预先存在；直播边产生边发布；交互式音视频还要求双方尽快听到、看到彼此。

- **吞吐量**：每秒实际收到多少数据，影响能否维持播放。
- **时延**：从产生到播放要等多久，交互通信对它更敏感。
- **抖动**：到达间隔忽快忽慢，即时延的波动。
- **缓冲**：先存一段待播内容，用来吸收到达不均匀或短暂变慢。

缓冲多可以抵御短暂波动，但增加起播等待或直播延迟；缓冲不能让长期不足的带宽凭空变大。

**例：视频码率为 2 Mb/s，一个 2 秒片段有 4 Mb。**如果下载速率为 4 Mb/s，1 秒下载完，期间播放消耗 1 秒内容，新片段增加 2 秒内容，缓冲净增 1 秒。若下载速率降到 1 Mb/s，则需 4 秒，缓冲净减 2 秒；原缓冲不够就可能卡顿。这里忽略协议开销并假定持续播放。

**码率**是每秒编码数据量，**分辨率**是画面像素尺寸。分辨率相同也可能有不同码率，不能直接互换。

### 7.6.2 I、P、B 帧与 GOP

视频编码常利用相邻画面的相似部分来减少数据。**I 帧**主要在本帧内编码；**P 帧**利用先前参考画面；**B 帧**可利用前后参考画面。**GOP（图像组）**把一段相关帧组织在一起。

解码一帧可能需要先得到参考帧，因此传输或解码顺序可以与显示顺序不同。某帧丢失会影响哪些后续画面，要看实际依赖关系；不能说“任意 B 帧一丢，整段视频一定全坏”。

### 7.6.3 信令、媒体与反馈：三件不同的事

**信令**处理“邀请谁、协商什么格式、何时开始”等控制信息；**媒体数据**是音视频内容；**反馈**报告接收效果。课件涉及的协议各有分工：

| 协议或格式 | 主要作用 |
|---|---|
| SIP、H.323 | 会话建立、能力协商等信令体系 |
| SDP | 描述媒体类型、地址、端口、编码等会话参数 |
| RTSP | 对媒体会话进行建立、播放、暂停、结束等控制 |
| RTP | 传送带序号、时间信息的实时媒体 |
| RTCP | 报告接收质量、同步等信息 |

它们不必在每个流媒体应用中全部出现，也不能仅因用途相近就互换名称。

RTSP 的 SETUP 建立传输相关安排，PLAY 开始播放，PAUSE 暂停，TEARDOWN 结束。RTSP 控制与实际媒体传送可以采用不同通道。防火墙是否允许流量取决于配置和策略，不能把课件“允许 TCP”表述当作普遍保证。

### 7.6.4 RTP：序号管顺序，时间戳管播放时刻

RTP 基本首部最少 12 字节。主要字段包括：V 版本（2 位）、P 填充标志、X 扩展标志、CC 源列表数量（4 位）、M 标记、PT 载荷类型（7 位）、序号（16 位）、时间戳（32 位）、SSRC 同步源标识（32 位）。源列表和扩展会增加首部长度。

**序号**通常每发送一个 RTP 分组加 1，帮助发现丢包、重排；**时间戳**按媒体时钟计数，帮助确定相对播放时刻。时间戳不是统一的“毫秒数”。SSRC 区分参与会话的媒体来源；CSRC 列表可说明混合内容的贡献来源。

**例：8 kHz 音频，每个分组装 20 ms 采样。**一个分组对应 `8000×0.020=160` 个采样时刻，连续分组的序号加 1，时间戳通常加 160。数据包因为网络抖动晚到，不改变这段音频本来的采样间隔。

RTCP 可报告丢失比例、抖动等，帮助发送方调整。RTP/RTCP 本身不保证每个包都得到重传或按时到达。

### 7.6.5 WebRTC：浏览器怎样实时通信

**WebRTC**让浏览器等端点建立实时音视频或数据通信。PeerConnection 管理对等连接，DataChannel 提供数据通道；仍需要应用安排信令，交换建立连接所需的信息。

难点之一是双方处于 NAT 或过滤设备后面。**ICE**收集并测试候选路径；**STUN**帮助了解对外映射等信息；直接连接不可用时，**TURN**可提供中继。不是使用 STUN 就必然能让任意两端直连。

媒体通常用 SRTP 保护，连接安全协商涉及 DTLS。SRTP 可理解为在 RTP 基础上添加安全保护，DTLS 则提供适用于数据报通信的安全机制。这里掌握分工即可，不必把所有握手细节混入媒体播放过程。

### 7.6.6 DASH、自适应码率与 SVC

**DASH**把视频切成小段，并准备多种质量版本。描述文件告诉客户端有哪些片段、版本和访问地址；客户端通过 HTTP 下载，结合近期吞吐与缓冲，选择下一段的版本。

例如可选码率为 1、2、4 Mb/s，近期估计下载能力约 3 Mb/s。选 2 Mb/s 留有余量；持续选 4 Mb/s 会消耗缓冲。真实选择还考虑估计误差、切换成本和当前缓冲，不是只比较两个数字。

HLS 也采用描述文件和片段进行 HTTP 分发，但具体格式与规则不同。它们可借助既有 Web 缓存与 CDN，并不需要把每次播放都组织成 RTP 会话。

**SVC（可伸缩视频编码）**把内容分成基础层和增强层：基础层即可得到基本画面，收到增强层可提高质量。它与“各码率各存一个完整版本”是不同组织方式；增强层可能依赖基础层。此处 SVC 与前面交换技术中的缩写含义不同。

## 7.7 CDN 与 P2P：让内容分散提供

### 7.7.1 CDN：把副本放到多个位置

**CDN（内容分发网络）**通过分散部署的边缘节点，把常用内容副本放到离请求者较合适的位置。保存原始内容的服务叫**源站**；边缘没找到可用副本时，从源站获取，叫**回源**。

**推送式**由源站主动分发；**拉取式**在用户请求造成缓存未命中时获取。缓存过期、版本更新和失效处理决定用户看到哪份内容，不能保证所有节点瞬间同步。

“就近”不只按地图距离判断，还可能考虑网络路径、节点负载、可用性与运营策略。

课件中的 DNS 调度可理解为：

```text
用户查询网站名字
    ↓ CNAME 指向 CDN 管理的名字
CDN 的 DNS / 调度系统选择节点
    ↓ 返回节点地址
用户连接节点 → 命中缓存则返回，否则回源
```

**GSLB（全局服务器负载均衡）**就是在多个服务位置之间安排请求。DNS 是一种调度手段；缓存 TTL 和解析器位置可能影响选择，不是每次请求都立即重新选择同一个地理最近节点。

动态、按用户授权的响应能否缓存，需要遵循应用与 HTTP 规则。CDN 本身也不保证内容真实性或安全。课件“2022 年视频流量占 82%”属于历史预测材料，不能作为当前流量统计背诵。

### 7.7.2 P2P 的覆盖网络与查找方式

P2P 中参与者互相建立逻辑连接，形成**覆盖网络（overlay）**。两个逻辑邻居在物理网络中可能隔着许多路由器，逻辑边不等于一根直接连接的网线。

| 组织方式 | 怎样查内容 | 主要代价 |
|---|---|---|
| 集中式索引 | 向中心问提供者，再与对等方传数据 | 依赖中心可用性与容量 |
| 非结构化网络 | 向邻居传播查询等 | 查询消息可能很多，也可能找不到 |
| 结构化网络 | 按约定的编号规则逐步找到负责者 | 需要维护编号、路由与节点变化 |

树状分发路径清晰，但父节点离开会影响子节点；网状分发可从多个伙伴取数据，但选择伙伴与维护连接更复杂。

### 7.7.3 BitTorrent：分片、交换、核对

**BitTorrent**把文件分成 pieces，用户从多个伙伴获取不同片，同时上传自己已有的片。拥有完整内容的参与者叫 **seed（种子）**；其他参与者可持有部分内容。

**Tracker**帮助发现伙伴；也可以通过 DHT 等方式发现伙伴。发现谁有内容与实际传输文件是两项工作。piece 内还可划分更小的请求块，不能把 piece 与每条数据报的大小画等号；课件的 256 KB 只是示例或常见设置，不是所有文件都固定使用的片长，更不是 256 Kb。

**最稀缺优先（rarest first）**倾向先获取伙伴中副本最少的片。例如 A、B、C 有多个副本，D 只有一个伙伴持有，先补充 D 能减少唯一提供者离线后无法完成下载的风险。

片下载完成后，可用元数据中的哈希检查内容。**哈希**把数据算成固定长度的摘要，帮助判断片是否与预期一致；摘要匹配不自动证明元数据来源可信。

### 7.7.4 DHT：把索引责任分给节点

**DHT（分布式哈希表）**把“某个键由谁负责”分布到许多节点上。键可以来自内容标识的哈希；查到的值可以是提供者信息，不意味着整部视频必然保存在负责节点上。

先用一个**教学用环模型**理解：编号空间 0～15，节点编号为 1、5、9、14，约定键归顺时针遇到的第一个节点。键 7 归节点 9；键 15 绕回节点 1。这是某类环式 DHT 的简化，不是所有 DHT 的通用查找规则。

BitTorrent 的 DHT 使用 Kademlia 思路，以 **XOR 距离**比较编号：把两编号按位异或，将结果作为距离。例如 `7 XOR 5=2`，`7 XOR 9=14`，所以按这种距离 5 比 9 更接近 7。不能拿上面的环上顺时针规则直接推导 Kademlia。参见 [BitTorrent DHT 协议 BEP 5](https://www.bittorrent.org/beps/bep_0005.html)。

结构化查找常见的 `O(log N)` 表示：在相应设计与假设下，所需步骤随节点数大致按对数增长，规模扩大时步骤增加相对缓慢。它不是任何 P2P 网络在任意故障下都成立的保证。

## 7.8 把一次视频访问串起来

```text
输入视频 URL
    ↓ DNS：找服务地址，可能经 CDN 调度
建立传输与安全连接
    ↓ HTTP：取得网页、描述文件和视频片段
CDN 节点返回内容，必要时回源
    ↓ 客户端按吞吐和缓冲选择质量
缓冲 → 解码 → 按媒体时间播放
```

这条路线适合 HTTP 分段视频。实时通话可以采用信令、WebRTC、RTP 等另一条路线，不应要求所有网络视频都同时经过 SMTP、FTP、RTSP 和 RTP。

### 分工速查

| 问题 | 主要机制 |
|---|---|
| 名字对应什么地址或服务 | DNS |
| 邮件怎样提交、转交 | SMTP |
| 怎样访问邮箱 | POP3 / IMAP |
| 附件与多种正文怎样表示 | MIME |
| 文件怎样上传、下载 | FTP / TFTP |
| Web 资源怎样请求、响应 | HTTP |
| 实时媒体怎样标顺序与播放时间 | RTP |
| 接收效果怎样反馈 | RTCP |
| 如何适应带宽变化 | 缓冲、自适应码率等 |
| 怎样减少源站重复发送 | CDN |
| 怎样利用参与者资源 | P2P、BitTorrent、DHT 等 |

### 计算前先检查条件

| 计算 | 公式或规则 | 条件 |
|---|---|---|
| Base64 长度 | `4 × ⌈n/3⌉` 字符 | n 为原始字节数，不含额外换行 |
| FTP PORT/PASV 端口 | `256p1+p2` | 两个字节采用十进制给出 |
| HTTP RTT | 按建连与请求依赖逐步相加 | 是否并行、持久、流水线以及 TLS 必须明确 |
| 片段数据量 | 码率 × 播放时长 | 统一 bit、B 与时间单位 |
| RTP 时间戳增量 | 媒体时钟频率 × 对应媒体时长 | 使用对应载荷的时钟频率 |
| 基本 TFTP 结束 | 最后 DATA 的数据少于 512 字节 | 未协商其他块大小 |

### 自测

1. 根服务器为什么不必保存每个网站的 IP？递归解析器处在域名树的哪一层？
2. 查询 A 记录时得到 CNAME，下一步应理解或查询什么？
3. SMTP 返回接受邮件的 250，能否证明对方已经读信？
4. 为什么 Base64 会变长，却不能当作加密？5 个字节编码后多长？
5. FTP 的 LIST 命令与它的目录内容是否使用同一连接？
6. 基本 TFTP 传 1024 字节文件，为什么还要一个零数据字节的 DATA？
7. HTTP 无状态与 TCP 持续连接是否矛盾？
8. 在本章简化题设中，一个 HTML 加两个图片采用持续、非流水线方式需多少 RTT？
9. 8 kHz 音频每包 20 ms，相邻 RTP 包的序号与时间戳分别怎样变化？
10. CDN 节点缓存未命中怎么办？DHT 查找负责节点是否等于从该节点下载完整文件？

<details>
<summary>参考答案</summary>

1. 根主要提供下一层线索，由不同权威区分担记录；递归解析器是查询角色，不是独立的域名树层次。
2. CNAME 给的是规范名字；需要沿名字继续取得相应 A 记录，响应也可能已包含它。
3. 不能，只说明相应服务器接受处理。
4. 三个字节转成四个字符，编码可逆且不依赖保密密钥；5 字节得到 `4×⌈5/3⌉=8` 个字符。
5. 命令走控制连接，目录内容走数据连接。
6. 前两个满块不能表明结束，需要不足 512 字节的最后块。
7. 不矛盾：协议是否自动关联应用状态与传输连接是否复用是不同问题。
8. 4 RTT：建连 1、HTML 1、两个图片各 1。
9. 序号加 1，时间戳通常加 160。
10. 可回源获取；DHT 可能只保存提供者信息，之后还需联系实际提供者。

</details>
