## 二、逐节详细讲解

### 1. 多态性是什么

**官方定义**：相同的消息请求（即调用同一个函数名/同一段代码），执行不同的代码体，从而产生不同的行为后果。

**用大白话理解**：你对不同的对象说同一句话"叫一声"，猫会"喵"，狗会"汪"——发出的"指令"（消息）是一样的，但具体谁来执行、执行成什么样，是不确定的，要看"听话的对象是谁"。这就是多态。

多态分两大类，区分标准是：**代码体是在编译期确定，还是运行期确定**。

| 分类 | 确定时机 | 依据 | 实现方式 |
|---|---|---|---|
| 静态多态 | 编译期 | 目标对象的**静态类型** + 参数的**静态类型** | 模板、函数重载 |
| 动态多态 | 运行期 | 目标对象的**动态类型** + 参数的**静态类型** | 虚函数（虚机制） |

> "静态类型"是变量声明时的类型（写在代码里、编译器一看就知道）；"动态类型"是变量实际指向/绑定的对象的真实类型（运行时才能确定）。这一组概念是理解本章的钥匙，后面会反复用到。

### 2. 静态多态

#### 2.1 模板实现的静态多态

模板本身不是"重载"，但从效果上看，不同的模板参数会在编译期生成不同的代码体，这也算一种多态——"同一段模板代码，参数不同，行为不同"。

```cpp
template <typename T>
class My {
public:
    void f(const T& t)
    { cout << typeid(t).name() << endl; }
};

int main() {
    My<int>   obj1;
    My<float> obj2;
    obj1.f(2);   // 输出 i  （T 被实例化为 int）
    obj2.f(2);   // 输出 f  （T 被实例化为 float）
}
```

关键点：`obj1` 和 `obj2` 调用的都叫 `f`，但因为模板参数 `T` 不同，编译器实际生成了两份不同的函数代码——`My<int>::f` 和 `My<float>::f`，这一切在**编译时**就已经决定好了。

#### 2.2 函数重载实现的静态多态

函数重载指同一个类里可以有多个同名函数，只要**参数列表**不同（类型、个数），编译器就能在编译期根据传入实参的静态类型，唯一确定调用哪一个。

```cpp
class A {
public:
    void f(int a)  { cout << "Int"  << endl; }
    void f(char c) { cout << "Char" << endl; }
};

int main() {
    A obj;
    obj.f(2);    // 输出 Int   （2 的静态类型是 int）
    obj.f('c');  // 输出 Char  （'c' 的静态类型是 char）
}
```

**为什么叫"静态"**：编译器仅凭 `2` 和 `'c'` 这两个字面量的**类型**，在编译阶段就已经把调用锁定到具体的函数地址上了，运行时不需要再做任何判断。

> 类比：快递分拣按"包裹上写的地址"分拣——地址（类型）在包裹打包（编译）那一刻就写好了，分拣员（编译器）照着地址直接送，不需要临时判断。

### 3. 动态多态性

#### 3.1 定义辨析

动态多态：**目标对象的动态类型** + **参数表中参数的静态类型**，共同确定目标代码体，这种机制叫"虚机制"（virtual mechanism）。

需要特别注意 PPT 里强调的一条边界：C++ **不支持**"根据目标对象的动态类型和参数的动态类型"来确定代码体（也就是不支持真正的"多重派发/multiple dispatch"）。也就是说：

- 谁去调用（this 指针指向谁）——看**动态类型**（运行时决定）✅
- 传进来的参数是什么类型——看**静态类型**（编译时决定），哪怕参数本身也是多态的对象，也只按它声明的类型去匹配重载版本 ❌（这点最容易考、也最容易错）

#### 3.2 经典例子拆解

```cpp
class B;
class A {
public:
    virtual ~A() {}
    virtual void f(A *) { cout << 1 << endl; }
    virtual void f(B *) { cout << 2 << endl; }
};

class B : public A {
public:
    virtual ~B() {}
    virtual void f(A *) { cout << 3 << endl; }
    virtual void f(B *) { cout << 4 << endl; }
};

int main() {
    B b;
    A* pa = &b;
    pa->f(&b);   // ?
    pa->f(pa);   // ?
    b.f(pa);     // ?
}
```

逐句分析（表格对照，帮助理解"两次决议"的过程）：

| 调用语句 | 第一步：确定"谁执行"（动态类型） | 第二步：确定"调用哪个重载版本"（参数的静态类型） | 输出 |
|---|---|---|---|
| `pa->f(&b);` | `pa` 动态指向 `B` 对象 → 用 `B` 的虚表 | `&b` 的静态类型是 `B*` → 匹配 `f(B*)` | **4** |
| `pa->f(pa);` | `pa` 动态指向 `B` 对象 → 用 `B` 的虚表 | `pa` 的静态类型是 `A*`（声明为 `A* pa`）→ 匹配 `f(A*)` | **3** |
| `b.f(pa);` | `b` 本身就是 `B` 对象 → 用 `B` 的虚表 | `pa` 的静态类型仍是 `A*` → 匹配 `f(A*)` | **3** |

**这道例题是本章最容易考的坑**：`pa` 实际指向的是 `B` 对象，很多初学者会想当然地认为传 `pa` 进去应该匹配 `f(B*)`，但规则是"参数只看静态类型"，`pa` 声明为 `A*`，所以永远匹配 `f(A*)` 版本，这就是"C++ 不支持参数的动态类型参与决议"的直接体现。

### 4. 虚机制的作用

**核心意义**：在保持客户端访问接口不变的前提下，可以变更类的实现。

```cpp
class A {
public:
    virtual ~A() {}
    virtual void func() { /* 实现1 */ }
};
class B : public A {
public:
    virtual ~B() {}
    virtual void func() { /* 实现2 */ }
};
class C : public A {
public:
    virtual ~C() {}
    void func() { /* 实现3 */ }
};
```

三个类都有 `func()`，但各自实现不同。因为 `func` 是虚函数，客户端只要拿着 `A*` 或 `A&`，调用 `func()` 时就会自动跳到"实际对象"所属类的那个实现——客户端代码完全不需要知道也不需要修改。

#### 4.1 子类型化（Subtyping）与适应变化

```cpp
Parent * p = new Child1;
p->func();      // 实际调用 Child1::func
delete p;

Child2 myObj;
Parent& obj = myObj;
obj.func();      // 实际调用 Child2::func

void Proc(Parent * p) { p->func(); }  // 通用函数，接受任何子类对象
```

理解这一段的关键：`Parent*`/`Parent&` 是"接口"，`Child1`、`Child2` 是"具体实现"。`Proc` 函数只依赖 `Parent` 这个接口写代码，将来无论新增多少种子类，`Proc` 都不用改一行代码——这正是虚机制带来的"开闭原则"式好处（对扩展开放，对修改关闭）。

> 类比：家里的插座是统一标准（接口），你可以插电灯、插风扇、插手机充电器（不同子类实现），插座本身（客户端代码）不需要为了适配新电器而重新设计。

### 5. 虚机制的应用（三个例子）

#### 例1：父类提供接口，子类提供具体实现

```cpp
class Mouse {  // 部分代码
public:
    void eat(Fruit & fruit)
    { weight += fruit.energy() * 0.1; }
private:
    int weight;
};
```

这里 `Fruit` 是父类（提供 `energy()` 这个虚函数接口），`Apple`、`StrawBerry` 是子类，各自的 `energy()` 返回值不同。`Mouse::eat` 只依赖 `Fruit` 接口，不管传进来的是苹果还是草莓，调用 `fruit.energy()` 都会自动调到具体子类的实现——这是"依赖接口而非具体实现"思想的体现。

#### 例2：父类提供框架，子类提供细节（模板方法模式）

```cpp
class Software {
public:
    virtual ~Software();
    void develop() {          // 非虚，固定流程（框架）
        design();
        coding();
        test();
        maintain();
    }
protected:
    virtual void design()   = 0;   // 纯虚，交给子类实现细节
    virtual void coding()   = 0;
    virtual void test()     = 0;
    virtual void maintain() = 0;
};

class AppSoftware : public Software { /* 实现 design/coding/test/maintain */ };
class WebSoftware : public Software { /* 实现 design/coding/test/maintain */ };
```

这是经典的**模板方法模式**：`develop()` 这个"骨架流程"在父类中写死、不能改，但每一步的具体做法（`design`、`coding` 等）是纯虚函数，留给子类去填空。

```cpp
void use(Software & sw) { sw.develop(); sale(sw); }

Software* sw1 = new AppSoftware("微信");
Software* sw2 = new WebSoftware("人人网");
```

客户端 `use` 函数完全不关心具体是哪种软件，调用 `develop()` 就能自动跑对应子类的整个开发流程。

**"父类提供接口"（例1）与"父类提供框架"（例2）的区别**：

| 对比维度 | 例1：接口式 | 例2：框架式（模板方法） |
|---|---|---|
| 父类中的函数 | 全是虚函数，各自独立 | 有一个非虚的"总控函数"（如 develop），调用内部若干虚函数 |
| 子类要做的事 | 实现某个虚函数即可 | 实现若干个步骤细节，但不能改变整体调用顺序 |
| 典型场景 | 简单的"一个动作，多种实现" | 固定流程、可变步骤的场景（如软件开发四步走） |

#### 例3：虚拟的拷贝构造（clone 模式）

**先说问题**：假设你有一个 `A*` 指针，实际指向的是某个子类对象（`B` 或 `C`），你想"复制出一个和它完全一样的新对象"，但你不知道它具体是哪个子类。直接用拷贝构造行不行？

**不行，原因有两条**：
1. 拷贝构造函数不能被声明为虚函数（C++ 语言规定，构造函数本身不能是虚函数）；
2. 即使能虚，各个类的拷贝构造函数名字（跟类名一致）也不可能相同，无法在基类里统一调用。

**常规笨办法**（PPT中展示的反例）：

```cpp
A * copy(A & a) {
    if (a是B型对象)
        return new B(*(B*)(&a));
    else if (a是C型对象)
        return new C(*(C*)(&a));
    else ....
}
```

这种写法需要手动判断类型，每加一个新子类都要改这个函数，完全违背了"用虚机制适应变化"的初衷。

**正确写法**：新增一个虚函数 `clone()`，让每个类自己知道"如何复制自己"：

| 反例：手工判断类型 | 正确写法：虚函数 clone() |
|---|---|
| `if (a是B型) return new B(*(B*)&a);`<br>`else if (a是C型) return new C(*(C*)&a);`<br>`else ...` | `virtual A* clone() { return new A(*this); }`<br>（每个子类各自重写一份，返回自身副本） |
| 每新增子类要改这个判断函数 | 每新增子类只需重写自己的 `clone()`，`copy` 函数完全不用动 |

```cpp
class A {
public:
    A() {}
    virtual ~A();
    virtual A * clone() { return new A(*this); }
protected:
    A(const A &) {}   // 拷贝构造设为 protected，禁止外部直接拷贝
};

class B : public A {
public:
    B() {}
    virtual B * clone() { return new B(*this); }
protected:
    B(const B & b) = default;
};

class C : public A {
public:
    C() {}
    virtual C * clone() { return new C(*this); }
protected:
    C(const C & c) = default;
};
```

调用时只需要 `a.clone()`，不管 `a` 实际是 `A`、`B` 还是 `C`，都会自动调到自己的 `clone()`，返回正确类型的副本。这就是设计模式中的 **Prototype（原型模式）**。

> 小知识点：这里子类 `clone()` 返回类型是 `B*`/`C*` 而不是 `A*`，这在 C++ 中是允许的，叫做**协变返回类型**（covariant return type），只要返回类型是原虚函数返回类型的派生类指针/引用即可。

### 6. 虚机制的意义（进一步深化）

```cpp
class XXX {
public:
    void Do1(Parent & obj) { obj.func(); }
    void Do2() { pObj->func(); }
    XXX() : pObj(new Child1) {}
    void SetParent(Parent * p) { pObj = p; }
private:
    Parent * pObj;
};
```

这里 `XXX` 类内部持有一个 `Parent*` 成员 `pObj`，并提供了 `SetParent` 方法允许外部随时替换成不同的子类对象。这体现了：**变更子类的具体实现时，完全不用修改客户端类 `XXX` 的定义和实现**——只需要在外部 new 一个新的子类对象传进来即可。

### 6.1 用子类适应变化——变化的两个层面

```cpp
class A {
public:
    // 1. 参数表可能变化
    // 2. f 的具体实现可能变化
    // 3. 增加新的成员 g()
    // 4. 删除成员 f(int,int)
    // 5. 更改 f(int,int) 的返回类型
    // 6. 更改成员的访问控制
    void f(int n, int m);
private:
    // 7. 数据类型可能变化
    // 8. 数据组织可能变化
    int nums[50];
};
```

PPT 在这里区分了两类"变化"：

| 变化类型 | 含义 | 例子（对应上面注释编号） |
|---|---|---|
| **接口变化** | 变更外部访问的约定（函数原型） | 1、3、4、5、6（参数表、增删成员、返回类型、访问权限） |
| **实现变化** | 变更类的内部组织或实现细节 | 2、7、8（函数具体怎么实现、数据类型和组织方式） |

虚机制主要解决的是"**实现变化**"——只要接口（虚函数签名）不变，内部怎么实现随便换，客户端不受影响。如果是"**接口变化**"，那客户端代码通常也得跟着改，这不是虚机制能单独解决的问题。

### 7. 使用继承和虚机制的不足

**核心问题**：如果一个类里有多个虚函数，每个虚函数又各自独立地有多种实现方式，那么用"继承+重写"的方式会导致子类数量按**乘法**爆炸增长。

```cpp
class Parent {
public:
    virtual ~Parent();
    virtual void f();
    virtual void g();
    virtual void h();
};
```

举例：若 `f()` 有 2 种实现，`g()` 有 3 种实现，`h()` 有 4 种实现，且这三者可以任意组合，那么理论上需要派生 **2×3×4 = 24** 个子类，才能覆盖所有组合情况。这显然是不可维护的。

**解决思路**：不要把所有变化都塞进一条继承链，而是**"水平方向的关联/依赖" + "垂直方向的继承"结合使用**——通俗说就是"组合优于继承"。

#### 7.1 用关联+依赖+继承 解决子类爆炸（示例）

```cpp
class Parent {
public:
    Parent(ImpF *, ImpG*, ImpH*);
    virtual ~Parent();
    void f() { pF->f(); }
    void g() { pG->g(); }
    void h() { pH->h(); }
private:
    ImpF * pF;
    ImpG * pG;
    ImpH * pH;
};

class ImpF {
public:
    virtual ~ImpF() {}
    virtual void f() { .... }
};
// ImpG、ImpH 同理，各自可以有多个子类实现不同版本
```

**思路解读**：`Parent` 不再自己实现 `f/g/h` 的具体逻辑，而是把这三个"职责"分别委托给三个独立的辅助类 `ImpF`、`ImpG`、`ImpH`（它们各自可以有自己的继承体系，各自扩展互不影响）。这样一来：

- `f` 有 2 种实现 → 只需要 `ImpF` 派生 2 个子类；
- `g` 有 3 种实现 → 只需要 `ImpG` 派生 3 个子类；
- `h` 有 4 种实现 → 只需要 `ImpH` 派生 4 个子类；
- 总共只需要 2+3+4=9 个子类，而不是 24 个（**加法代替乘法**）。

`Parent` 在运行时通过构造函数或 setter 接收不同的 `ImpF/ImpG/ImpH` 组合对象，自由拼装出任意组合的行为，这正是**策略模式（Strategy Pattern）**的雏形。

#### 7.2 例2：用动态多态改造大量 if-else（策略模式实战）

**反例（未使用多态，条件判断写死在函数里）**：

```cpp
class Some {
public:
    void func(int cond) {
        if (cond == 1) {
            代码块01
        } else if (cond == 2) {
            代码块02
        } else {
            ...
        }
    }
};
```

**问题**：已知代码块之间互斥、以后会不断新增条件、各代码块自身也会经常修改。如果继续用 if-else，每次新增/修改都要动这个 `func` 函数本身，违反"对扩展开放、对修改关闭"的原则。

**正确写法（用虚函数取代条件分支）**：

| 反例：if-else 硬编码 | 正确写法：多态 execute() |
|---|---|
| `if(cond==1){代码块01}`<br>`else if(cond==2){代码块02}`<br>`else {...}` | 定义抽象基类 `Code`，纯虚函数 `execute()`；<br>`Code01`、`Code02` 各自实现自己的 `execute()` |
| 新增条件 = 修改 `func` 函数 | 新增条件 = 新增一个 `CodeXX` 子类，`func` 不用动 |

```cpp
class Code {
public:
    virtual ~Code() = default;
    virtual void execute() = 0;
};
class Code01 : public Code {
public:
    void execute() override { 代码块01 }
};
class Code02 : public Code {
public:
    void execute() override { 代码块02 }
};

class Some {
public:
    void func(Code & code) { code.execute(); }
};
```

这样 `Some::func` 永远只有一行 `code.execute()`，无论以后新增多少种 `CodeXX`，`func` 本身完全不需要改动，改动被"局部化"到了新的子类中。这正是"用动态多态替代条件分支"的标准套路，也是设计模式中**策略模式**的核心思想。

## 三、本章小结

1. **多态的本质**：相同的调用形式，产生不同的执行结果，核心目的是让客户端代码与具体实现解耦。
2. **静态多态**在编译期确定代码体，依据是"目标对象的静态类型 + 参数的静态类型"，实现手段是**模板**和**函数重载**。
3. **动态多态**在运行期确定代码体，依据是"目标对象的动态类型 + 参数的静态类型"，实现手段是**虚函数（虚机制）**；C++ 明确不支持参数的动态类型也参与决议（不支持多重派发），这是最容易考错的知识点。
4. **虚机制的作用**是"保持客户端接口不变的前提下更换实现"，其基础是**子类型化**（父类指针/引用可指向/绑定子类对象）。
5. 虚机制有三大典型应用套路：**①父类提供接口、子类提供实现**；**②父类提供框架（模板方法）、子类提供步骤细节**；**③虚拟拷贝构造（clone / 原型模式）**，因为拷贝构造函数本身不能是虚函数。
6. 类的变化分两种：**接口变化**（函数原型层面）和**实现变化**（内部逻辑/数据层面）；虚机制主要用来吸收"实现变化"。
7. 单纯依靠"继承+虚函数"应对**多个独立变化维度**时，子类数量会呈**乘法级**爆炸增长（如 2×3×4=24）；解决办法是**"关联/依赖 + 继承"结合使用**（组合优于继承），把每个变化维度拆分到独立的辅助类继承体系中，变乘法为加法。
8. 用**虚函数替代大量 if-else 条件分支**（策略模式思路），可以把"新增/修改一种情况"的改动局部化为"新增/修改一个子类"，不用触碰主流程代码。
