## 一、面向对象的三大基本特征

面向对象编程有三大基石：**封装、继承、多态**。本章聚焦"封装"，为后续继承、多态打基础。

### 1.1 封装（Encapsulation）

**是什么**：封装是"从现实世界抽象出类"的过程——观察一个客观事物，提炼出它有哪些**行为**（能做什么）、有哪些**属性**（有什么特征数据），然后用"类"这种语言结构把它们包在一起，形成一个"对象"的蓝图。

**为什么**：现实世界的事物是杂乱、连续的，程序需要用离散的、结构化的方式去描述它们。封装就是"造模型"的过程：把无关的细节舍弃，只保留对当前问题有意义的行为和属性。

**怎么用**：在 C++ 中，封装的语法载体就是 `class`。举例：

```cpp
class Dog {
public:
    void bark();      // 行为
private:
    int age;          // 属性
};
```

这里我们把"狗会叫、狗有年龄"这两个认知封装进了一个 `Dog` 类里。

### 1.2 信息隐蔽（Information Hiding）

**是什么**：封装解决了"提炼行为和属性"的问题，但更进一步的问题是——这些行为和属性，是不是都要让外部随便访问？信息隐蔽的答案是：**不是**。只暴露"可信的外部事物"需要用的部分，其余的实现细节要藏起来。

**为什么**：如果一个类的所有细节都暴露给外部，会导致：
- 外部代码可能绕过正确的调用顺序，直接改坏内部数据；
- 类内部想改进实现方式时，外部代码可能因为"看到了不该看的东西"而被牵连修改。

**怎么用**：C++ 用 `public` / `private`（还有 `protected`，本章暂不展开）来控制可见性。这是下文"信息隐蔽"一节的核心，稍后详细讲解。

> 一句话记忆：**封装 = 把行为和数据打包成类；信息隐蔽 = 决定包里哪些东西露在外面，哪些藏起来。**

## 二、抽象与封装

### 2.1 抽象 → 表示：两步走的思维过程

面向对象设计从来不是"上来就写代码"，而是先做**抽象**（想清楚"这是什么、它能干什么、它有什么数据"），再做**表示**（把抽象的结果落地成具体的类语法）。

```
抽象（想）                      表示（写）
────────────                   ────────────
类型的抽象  ──────────────►    类型的表示（class 名字）
行为的抽象  ──────────────►    行为的表示（成员函数）
数据的抽象  ──────────────►    数据的表示（成员变量）
```

### 2.2 例1：小球碰撞问题

**问题描述**：屏幕上有小球在边界墙内运动、碰撞、反弹。

**抽象过程**：

| 抽象类别 | 内容 |
|---|---|
| 类型的抽象 | 小球（Ball）、边界墙（Border） |
| 行为的抽象（小球） | 移动、设置速度、设置位置、检测是否碰撞、反弹、设置能量系数 |
| 行为的抽象（边界墙） | 设置位置、改变能量系数、检测是否碰撞、反弹 |
| 数据的抽象 | 位移、速度、能量系数 |

**表示（落地为代码）**：

```cpp
class Ball {
public:
    void setPosition(int x, int y);
    void setSpeed(int speed);
    void stepMove();
    void setScale();
    void rebound();
private:
    int mx, my;
    int mspeed;
    float mscale;
    Border* mborder;
};

class Border {
public:
    void setPosition(int x, int y);
    void setScale();
    void rebound();
private:
    int mx, my;
    float mscale;
};
```

**行为的内部实现示例**（`stepMove` 依赖了内部的碰撞检测）：

```cpp
void Ball::stepMove() {
    if (HitBorder()) {          // 碰到边界，改变速度和位置
        SetSpeed(...);
        mx = ...; my = ...;
    } else {                    // 未碰到，正常移动
        mx = ...; my = ...;
    }
    setPosition(mx, my);
}
```

这个例子体现了抽象设计的完整闭环：**从现实问题（小球碰撞）→ 抽象出类型/行为/数据 → 用 class 语法表示 → 实现具体逻辑。**

### 2.3 例2：怪物战斗系统

**题目**：多个怪物（Monster）互相 `fight`，每个怪物有生命值 `hitpoint`、攻击力 `damage`、防御力 `defense`，各自有特有的 `attack` 攻击方式；战斗时双方轮流攻击，直到一方生命值为 0。

**抽象**：
- 类型的抽象：怪物类 Monster
- 行为的抽象：战斗（fight）、设置属性
- 数据的抽象：hitpoint、damage、defense

**表示**：

```cpp
class Monster {
public:
    // ... 设置属性等方法
    bool fight(Monster& other) {
        while (true) {
            if (attack(other)) return WIN;          // 我方先攻击
            if (other.attack(*this)) return LOSE;   // 对方还击
        }
    }
};
```

**理解要点**：`fight` 函数体现了题目描述的"轮流攻击直到一方死亡"的逻辑，用一个 `while(true)` 循环 + 双向 `attack` 调用即可清晰表达。这是一个典型的"把自然语言描述直接翻译为类行为"的练习，考试中常考。

### 2.4 抽象无处不在：五种抽象对象

PPT 强调"有意义的事物都可以抽象"，抽象不仅限于"类型"，还包括：

- **类型的抽象**
- **数据的抽象**
- **参数的抽象**
- **代码的抽象**
- **行为的抽象**

下面逐一讲解。

#### 2.4.1 类型的抽象

类型抽象是一种"层次化归类"的思维：同一批具体事物，可以按不同粒度归纳出上位概念。例如"人物"这个概念，可以按照虚构/历史分类，再往下细分小说人物、历史人物，再往下是具体的西游人物、四大美人等。

```
人物
├── 虚构人物 → 小说人物 → 西游人物 / 红楼人物 / 四大美人
└── 历史人物 → 200年前人物 / 近代人物 → 周文王 / 陈庆之
```

**类比理解**：这就像我们给文件分文件夹——先分大类，再分子类，越往下越具体。在设计类时，我们要思考"当前问题需要抽象到哪一层"，抽象层级选得太粗会丢失细节，太细会导致类爆炸。

#### 2.4.2 数据的抽象

同一个类的数据成员，可以有不同粒度的组织方式。以 `Person` 类为例：

```cpp
// 粒度1：完全打散
class Person {
private:
    string 姓名, 性别;
    vector<string> 爱好列表;
    string 职业;
    vector<Order> 网购历史;
    Preference 购物偏好;
};

// 粒度2：初步归类
class Person {
private:
    BasicInfo 基本信息;      // 姓名、性别、爱好、职业 打包
    History   网购历史;
    Preference 购物偏好;
};

// 粒度3：再归类
class Person {
private:
    BasicInfo 基本信息;
    ShoppingInfo 购物信息;   // 网购历史 + 购物偏好 打包
};

// 粒度4：完全打包
class Person {
private:
    PersonalInfo 个人信息;   // 所有信息打包成一个复合对象
};
```

**为什么要这样做**：数据抽象的粒度决定了类的"粗细"。数据项太多太散，类会显得臃肿难维护；适度打包成子对象（如 `BasicInfo`），能让主类更清晰，也方便复用（比如 `BasicInfo` 可能在别的类里也用得到）。**这是一种渐进式重构的思路**，实际开发中经常按此方式演化设计。

#### 2.4.3 参数的抽象

**是什么**：当一个函数的参数越来越多时，把相关参数打包成一个结构体/类作为单一参数传入。

**反例（参数堆砌）**

```cpp
void login(const char* username,
           const char* password,
           const char* validCode,
           DateTime dt,
           int clientID,
           const char* IP);
```

**正例（参数打包）**

```cpp
void login(LoginInfo& info);

void login(UserInfo& user,
           Address& client);
```

**为什么**：参数太多会导致：
- 调用者容易记错参数顺序（例如把 `username` 和 `password` 位置搞反，编译器还不会报错）；
- 后续新增一个参数（比如增加"设备指纹"字段）需要改所有调用点的函数签名。

打包成 `LoginInfo` 结构体后，新增字段只需给 `LoginInfo` 加成员，调用点代码不用变。**这就是"参数抽象"带来的可扩展性优势。**

#### 2.4.4 代码的抽象

**是什么**：把函数体内的"代码块"逐步提炼、参数化，最终变成可替换、可配置的对象成员。

```
阶段1：全部硬编码在一个函数里
class Flight {
public:
    void fly(...) {
        起飞代码块;
        飞行代码块;
        降落代码块;
    }
};

阶段2：把"起飞"部分抽成参数传入（体现可替换性）
class Flight {
public:
    void fly(..., TakeOff& takeOff) {
        takeOff.excute();
        飞行代码块;
        降落代码块;
    }
};

阶段3：把整个流程抽成参数传入
class Flight {
public:
    void fly(..., FlyProcess& proc) {
        proc.excute();
    }
};

阶段4：把流程做成成员变量，成为类的内部依赖
class Flight {
public:
    void fly(...) { proc->excute(); }
private:
    FlyProcess* proc;
};
```

**为什么**：代码抽象的核心目的是"把易变的部分挪出去"。起飞、飞行、降落的具体动作可能因飞机型号不同而不同，把这部分抽象成一个可传入/可替换的对象（`TakeOff`、`FlyProcess`），`Flight` 类本身就不用因为"某种飞机的起飞方式变了"而被迫修改。这正是设计模式中"策略模式"的雏形。

#### 2.4.5 行为的抽象

**是什么**：把一组"名字不同但本质相同"的行为，归纳成一个更通用的行为。

**抽象前（每种交通工具一个方法）**

```cpp
class Traver {
public:
    void walk();
    void ride(Bike&);
    void ride(Camel&);
    void drive(Car&);
};
```

**抽象后（统一为"移动方式"）**

```cpp
class Traver {
public:
    void walk();
    void moveBy(Vehicle&);
};
```

**为什么**：`ride(Bike&)`、`ride(Camel&)`、`drive(Car&)` 本质上都是"借助某种交通工具移动"，只是交通工具种类不同。把它们统一抽象为 `moveBy(Vehicle&)`，以后新增一种交通工具（如 `Boat`），只要 `Boat` 满足 `Vehicle` 的约定，`Traver` 类完全不用改动。**这体现了"面向接口/基类编程"的思想，是后续学习继承与多态的重要铺垫。**

## 三、信息隐蔽

### 3.1 隐藏行为、操作

**是什么**：一个"行为特征"往往由多个内部操作步骤组成，在 C++ 中每个操作步骤通常是一个成员函数。设计时，可以把这些"步骤性"的成员函数设为 `private`，只暴露最终对外有意义的那个操作。

**为什么**：外部使用者只关心"能不能让球移动一步（`stepMove`）"，并不关心"球是怎么判断自己撞没撞墙的（`hitBorder`）"。把 `hitBorder` 隐藏起来，可以防止外部代码乱调用这个内部辅助函数，也让类的"对外接口"更简洁。

**代码示例**：

```cpp
class Ball {
public:
    void setPosition(int x, int y);
    void setSpeed(int speed);
    void stepMove();          // 对外暴露：移动一步
private:
    bool hitBorder();         // 对内隐藏：碰撞检测细节
private:
    int mx, my;
    int mspeed;
    float mscale;
    Border* mborder;
};

bool Ball::hitBorder() {
    bool hitLeft  = distance <= radius;
    bool hitRight = (distance + radius >= RIGHT);
    return (hitLeft || hitRight);
}

void Ball::stepMove() {
    if (hitBorder()) {        // 内部调用私有函数完全没问题
        setSpeed(...);
        mx = ...; my = ...;
    } else {
        mx = ...; my = ...;
    }
    setPosition(mx, my);
}
```

**注意**：私有成员函数**只是对类外部不可见**，类自己的其他成员函数（如 `stepMove`）依然可以正常调用它。这是初学者常见的误区——以为 `private` 会让函数"完全不能用"，其实只是"外部不能直接调"。

### 3.2 隐藏数据

道理与隐藏行为完全一致：把成员变量设为 `private`，外部不能直接读写，只能通过公开的成员函数（如 `setSpeed`、`setPosition`）间接访问。这样做的好处是：类内部可以在 setter 里加校验逻辑（比如速度不能为负），而外部无法绕过校验直接改数据。

> **小结记忆点**：信息隐蔽不是"藏起来不让用"，而是"只允许通过规定的入口用"。

## 四、分离使用和实现

### 4.1 两种角色：使用者 vs 实现者

一个类天然存在两类"读者"：

- **类的使用者（调用方）**：只需要知道"这个类能做什么（public 接口）"，不需要知道"它是怎么做到的"。
- **类的实现者**：负责成员函数的具体实现、数据的组织方式等内部细节。

```cpp
class Imp {
public:
    void pubFunc() { ... }     // 使用者可以调用
private:
    void priFunc() { ... }     // 使用者不能调用
private:
    int fields;                 // 使用者不能直接访问
};

class Client {
public:
    void useImp(Imp& imp) {
        imp.pubFunc();          // ✅ 正确
        imp.priFunc();          // ❌ 编译错误：外部不可访问私有成员
        imp.fields = 100;       // ❌ 编译错误：外部不可访问私有成员
    }
};
```

**为什么这样设计**：这是信息隐蔽在"角色划分"层面的自然延伸——使用者只面对 `public` 接口，实现细节的变化不会波及使用者的代码，这就是"接口稳定、实现可变"的工程原则。

### 4.2 实践对比：把"使用逻辑"从类中剥离出去

下面这个例子非常关键，展示了"类的实现里不应该混入调用者的业务逻辑（如用户交互）"：

**反例：把"读取用户输入"写死在类方法里**

```cpp
// student.h
#include <iostream>
class Student {
public:
    void input() {
        int a;
        std::cout << "请输入年龄:";
        std::cin >> a;
        age = a;
    }
private:
    void f();
    int age;
};
```

**正例：类只负责数据，输入交给调用方（MainApp）**

```cpp
// student.h
class Student {
public:
    Student(int theAge) { age = theAge; }
private:
    void f();
    int age;
};

// MainApp.cpp
#include <iostream>
#include "student.h"
void main() {
    int a;
    std::cout << "请输入年龄:";
    std::cin >> a;
    Student stu(a);
    stu.f();
}
```

**为什么正例更好**：
1. 反例里 `Student` 类耦合了控制台输入输出（`std::cin`/`std::cout`），如果以后这个程序要改成图形界面或从文件读年龄，`Student` 类本身要被迫修改——这违反了"类不应该关心自己的数据从哪来"的原则。
2. 正例把"如何获取年龄"这件事交给调用方（`MainApp.cpp`）决定，`Student` 只管接收一个已经准备好的 `int` 值。这样 `Student` 类可以被任何输入来源复用。

> **一句话记忆**：类应该只关心"我是什么、我能做什么"，不应该关心"外部世界怎么把数据喂给我"。

## 五、类的设计

本节是全章的核心方法论，分为"多个类之间怎么设计"和"单个类内部怎么设计"两个层面。

### 5.1 多个类的设计

在设计一个较大的系统时，通常需要考虑四个方面：

- **类的拆分**：一个类功能太多、太复杂，拆成几个协作的类。
- **类的合并**：几个类职责太细碎，合并成一个类更清晰。
- **数据关系**：类与类之间通过"持有指针/引用"建立关联。
- **行为关系**：类的方法内部调用其它类的方法来完成任务。

**示例：Application 类的拆分**

```cpp
// application.h
class Application {
public:
    Application();
    void Init();
    void run(Argument& arg);
    void term();
private:
    Input*  in;
    Output* out;
    Config* cfg;
};

class Argument {};
class Input {};
class Output {};
class Config {};
```

`Application` 不是一个"大而全"的类，而是把"输入""输出""配置"这三个关注点拆分成独立的类（`Input`、`Output`、`Config`），`Application` 通过持有它们的指针来"组合"出完整功能。这正是**组合优于继承**思想的一个体现（虽然本章还没讲继承）。

**示例：行为关系——多个类互相调用**

```cpp
class A {
public:
    void fA(B& b, C& c) {
        b.fB(*this, c);   // A 调用 B 的方法，并把自己传进去
        c.fC(*this, b);   // A 调用 C 的方法
    }
};
class B {
public:
    void fB(A& a, C& c);
};
class C {
public:
    void fC(A& a, B& b);
};
```

**理解要点**：`*this` 代表"当前这个 A 对象自己"，把自己作为参数传给别的类的方法，是对象之间"互相认识、互相协作"的常见写法。这体现了"行为关系"——A 的行为需要依赖 B 和 C 才能完成。

### 5.2 单个类的设计：六个关注点

设计单个类时，PPT 给出了六个需要思考的维度，我们逐一拆解。

#### 5.2.1 行为的可见性

即前面讲过的"信息隐蔽"思路在单个类设计中的具体应用——哪些成员函数该 `public`，哪些该 `private`。例如 `Application` 类里，`loadFile`、`saveFile` 属于内部实现细节，设为 `private`；`init`、`run`、`term` 是对外提供的生命周期方法，设为 `public`。

```cpp
class Application {
public:
    Application();
    void init();
    void run(Argument& arg);
    void term();
private:
    bool loadFile(string&);
    bool saveFile(string&);
private:
    Input*  in;
    Output* out;
    Config* cfg;
};
```

#### 5.2.2 行为参数的抽象与封装

这是"参数的抽象"思想在单个类里的应用：当一个类的方法有很多重载版本，且参数种类繁多时，考虑用一个更通用的参数类型来统一它们。

**抽象前：为每种"叫的对象"重载方法**

```cpp
class Dog {
public:
    void bark(Human& human);
    void bark(Humen& humen);
    void bark(Door& door);
    void bark(Door& door, int db);
    void bark(int db);
};
```

**抽象后：统一成一个通用参数类型**

```cpp
class Dog {
public:
    void bark(Dest& aDest);
};
```

**为什么**：反例里，`Dog` 每遇到一种新的"叫的对象"，就要新增一个重载方法，方法数量会随场景数量线性增长，难以维护。正例把"叫的对象"抽象为一个统一的 `Dest`（Destination，目标）类型，`Dog` 只需要一个 `bark` 方法，新增场景只需要扩展 `Dest` 体系（这一点在后续学到继承/多态后会更清楚）。

#### 5.2.3 依赖与关联

这一小节展示了"参数传入"和"成员持有"两种设计方式之间的取舍与转换：

```cpp
// 方式1：依赖——每次调用都传入
class Dog {
public:
    void bark(Dest& aDest);
};

// 方式2：关联——先设置好，之后直接用
class Dog {
public:
    void setDest(Dest*);
    void bark();
private:
    Dest* aDest;
};
```

**怎么选**：
- 如果"目标"每次调用都可能不同（一次性使用），用**依赖**（参数传入）更合适；
- 如果"目标"是这个 `Dog` 对象长期关联的（比如狗一直对着同一个门叫），用**关联**（成员变量持有）更合适，调用方式也更简洁（`dog.bark()` 而不用每次都传参）。

**委托（Delegate）**：当一个类的方法把自己的实现完全委托给内部持有的另一个对象时，这种设计叫"委托"：

```cpp
class Dog {
public:
    void func() {
        pobj->func1();
        do1();
        pobj->func2();
    }
private:
    MyObj* pobj;
};

// 极端情况：整个函数体都委托出去
void func() {
    pobj->somefunc();
}
```

**类比理解**：委托就像"外包"——`Dog` 自己不干活，把活分给内部持有的 `MyObj` 对象去干，自己只负责"调度"。

#### 5.2.4 实现的抽象与封装

与"依赖与关联"的思路一致，只是应用在"函数实现细节"上：把函数体里散落的逻辑（如局部变量计算）委托给别的对象处理，让当前类更专注于"做什么"而不是"怎么做"。（PPT 中此部分与上一部分紧密关联，核心手法相同：**从"内联实现"逐步过渡到"委托给协作对象"**。）

#### 5.2.5 数据的抽象与封装

这一节展示了"把散乱的数据成员打包成一个数据类"的重构过程：

```cpp
// 重构前：Dog 直接持有一堆数据
class Dog {
public:
    void func() {
        age = 8;
        ...
    }
private:
    int age;
    int color;
    History hist;
};

// 重构后：数据被抽出到独立的 DogData 类
class Dog {
public:
    void func() {
        data->setAge(8);
    }
private:
    DogData* data;
};

class DogData {
public:
    void setAge(int a) { age = a; }
private:
    int age;
    int color;
    History hist;
};
```

**为什么**：这与前面"数据的抽象"讲的 `Person` 例子逻辑一致——把数据独立打包成 `DogData`，`Dog` 类只需要持有一个指针，既减轻了 `Dog` 类本身的复杂度，也让 `DogData` 具备了独立复用、独立测试的可能性。

#### 5.2.6 类方法与实例方法

C++ 中，`static` 成员函数属于**类方法**（不依赖具体对象即可调用），普通成员函数是**实例方法**（必须依附于一个具体对象）。这一区分会在下一节"类的设计（例）"中的工厂方法、单件模式里具体展开。

## 六、类的设计（例）

本节通过两个综合案例，把前面讲的方法论落地。

### 6.1 分页器（Paginate）设计

**场景**：设计一个网页常见的分页控件，支持"上一页、下一页、跳页"等交互（如下图所示的 `« 1 ... 6 7 8 9 10 ... 22 »` 分页条）。

**设计思路（对应前文六个维度的综合应用）**：

**第一步：行为设计**——先想清楚这个类要对外提供什么操作：

```cpp
class Paginate {
public:
    void go(int page);   // 跳转到指定页
    void prev();         // 上一页
    void next();         // 下一页
    void prevN();        // 向前跳 N 页（如显示的 "..." 快速跳转）
    void nextN();         // 向后跳 N 页
};
```

**第二步：数据设计**——想清楚支撑这些行为需要哪些内部状态：

```cpp
class Paginate {
private:
    int num;         // 当前页码
    int total;       // 总页数
    int rangeStart;  // 显示范围起始页（比如 6）
    int rangeEnd;    // 显示范围结束页（比如 10）
};
```

**第三步：其他配套方法的取舍**——这是本例给出的一条重要经验规则：

| 方法类型 | 是否需要自定义 | 原因 |
|---|---|---|
| 构造函数 | **需要**自定义 | 需要按传入的总数据量等信息初始化 `total`、`num` 等状态 |
| 拷贝构造函数 | **不需要**自定义 | 类内全是简单的 `int` 数据，编译器生成的默认拷贝（逐成员复制）已经足够正确 |
| 赋值函数 | **不需要**自定义 | 同上，默认赋值行为已经满足需求 |
| getter 函数 / `show()` | 视需要而定 | 取决于外部是否需要读取分页器的内部状态用于界面渲染 |

**这个判断规则很重要**：不是所有类都必须手写"三大函数"（构造/拷贝构造/赋值），**只有当类持有需要深拷贝的资源（如指针、动态内存）时，才必须自定义拷贝构造和赋值函数**；纯数据成员（如全是 `int`）时，编译器默认生成的版本就是安全的。

### 6.2 创建方法与构造函数：工厂方法

**问题**：当一个类有多个重载构造函数时，会带来两个问题：

```cpp
class Balloon {
public:
    Balloon() {}
    Balloon(int color) {}
    Balloon(Gas& gas) {}
};
```

- **语义不清楚**：`Balloon(色)` 和 `Balloon(气体)` 单看构造函数签名，不容易一眼看出这是"创建一个彩色气球"还是"创建一个充气气球"。
- **不易扩展**：以后如果想加"用彩色+充气两种方式一起创建"，构造函数重载会越堆越多，容易冲突混乱。

**解决方案：静态工厂方法**——把构造函数设为 `private`（外部不能直接 `new`），改用**有名字的静态方法**来创建对象：

```cpp
class Balloon {
public:
    static Balloon createNormalBalloon()
        { return Balloon(); }
    static Balloon createColorBalloon(int c)
        { return Balloon(c); }
    static Balloon createGasBalloon(Gas& g)
        { return Balloon(g); }
private:
    Balloon() {}
    Balloon(int color) {}
    Balloon(Gas& gas) {}
};
```

**为什么这样更好**：`createColorBalloon(5)` 比 `Balloon(5)` 的语义清晰得多——调用者一眼就知道这是"创建一个彩色气球"，而不用去猜 `5` 到底是颜色编号还是别的什么参数。这正是**类方法（静态方法）**的典型应用场景之一：用"有意义的方法名"替代"暧昧的构造函数重载"。

### 6.3 单件（Singleton）模式的两种实现

**需求**：希望某个类在整个程序运行期间，最多只能存在**一个实例**（比如全局唯一的配置管理器、日志记录器）。

**实现方式一：局部静态变量（推荐、简洁、线程安全性较好）**

```cpp
class Ball {
public:
    static Ball& getInstance() {
        static Ball aBall;   // 只在第一次调用时创建，之后一直复用
        return aBall;
    }
private:
    // 阻止外部创建、拷贝、赋值
    Ball() = default;
    Ball(const Ball&) = delete;
    Ball& operator=(const Ball&) = delete;
public:
    void func();
};
```

**实现方式二：堆上动态分配（手动管理生命周期）**

```cpp
class Ball {
public:
    static Ball* getInstance() {
        if (spBall == nullptr) spBall = new Ball;
        return spBall;
    }
    static void releaseInstance() {
        delete spBall;
        spBall = nullptr;
    }
private:
    static Ball* spBall;               // 类外还需分配存储空间！
    Ball() {}
    Ball(const Ball&);                 // 只声明，不实现（老式写法，禁止拷贝）
    Ball& operator=(const Ball&);      // 只声明，不实现
public:
    void func();
};
```

**两种方式对比**：

| 对比点 | 方式一（局部静态变量） | 方式二（堆上 new） |
|---|---|---|
| 创建时机 | 第一次调用 `getInstance()` 时自动创建 | 第一次调用 `getInstance()` 时手动 `new` |
| 释放方式 | 程序结束时自动析构，无需手动管理 | 需要显式调用 `releaseInstance()` 释放，容易忘记 |
| 返回类型 | 引用 `Ball&` | 指针 `Ball*` |
| 额外代码 | 无需类外初始化 | 需要在类外写 `Ball* Ball::spBall = nullptr;` |
| 现代 C++ 推荐度 | ✅ 更推荐（C++11 起局部静态变量初始化是线程安全的） | 传统写法，仍常见于较老代码库 |

**共同点（也是单件模式的核心手法）**：无论哪种方式，都必须做到：
1. 把构造函数设为 `private`（阻止外部 `new` 或直接创建对象）；
2. 禁用拷贝构造函数和赋值运算符（阻止通过拷贝产生第二个实例）；
3. 提供一个 `public static` 方法（如 `getInstance`）作为获取唯一实例的**唯一合法入口**。

这正是本章"类方法与实例方法"这一知识点的实战应用：`getInstance` 是一个不依赖具体对象、可以直接通过类名调用的**类方法（静态方法）**。

## 本章小结

1. **面向对象三大特征**是封装、继承、多态；本章专注封装，封装 = 从事物中提炼行为和属性，用类表示；信息隐蔽 = 决定这些行为和属性中哪些对外可见。
2. 类的设计遵循"**抽象 → 表示**"两步走：先想清楚类型、行为、数据是什么，再落地为 `class`、成员函数、成员变量。
3. **五种抽象对象**：类型的抽象、数据的抽象、参数的抽象、代码的抽象、行为的抽象——本质都是"把易变或冗余的部分提炼、打包、统一"，从而提高代码的清晰度和可扩展性。
4. **信息隐蔽**通过 `public`/`private` 实现：只暴露外部真正需要的接口，内部实现细节（辅助函数、内部数据）一律隐藏。
5. **分离使用和实现**：类应该只关心"自己是什么、能做什么"，不应该关心"外部世界怎么使用自己"（如避免把用户输入逻辑写死在类内部）。
6. **多个类的设计**要考虑拆分/合并、数据关系、行为关系；**单个类的设计**要考虑行为可见性、参数抽象、依赖与关联（含委托）、实现抽象、数据抽象、类方法与实例方法六个维度。
7. 只有当类持有需要深拷贝的资源时，才必须手写拷贝构造函数和赋值函数；纯数据类通常可以依赖编译器生成的默认版本（分页器例）。
8. **静态工厂方法**能让对象创建的语义比"重载构造函数"更清晰、更易扩展。
9. **单件模式**的核心是：私有化构造函数 + 禁用拷贝/赋值 + 提供唯一的静态获取入口；局部静态变量实现更现代、更安全，手动 `new`/`delete` 实现需要额外管理释放。
