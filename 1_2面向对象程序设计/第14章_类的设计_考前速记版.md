## 一、三大特征 & 封装/信息隐蔽 ★★★

| 概念 | 一句话结论 |
|---|---|
| 封装 | 从事物中提炼**行为+属性**，用 class 表示 |
| 信息隐蔽 | 决定哪些行为/属性对外暴露，哪些隐藏 |
| 三大特征 | 封装、继承、多态（本章只讲封装） |

**易混点**：封装≠信息隐蔽。封装是"打包"，信息隐蔽是"打包后决定露不露"。

## 二、抽象与封装

### 抽象→表示 两步走

```
抽象（想清楚是什么） → 表示（写成class/成员函数/成员变量）
```

小球碰撞例、Monster 战斗例：**类型的抽象→类名，行为的抽象→成员函数，数据的抽象→成员变量**。

`Monster::fight` 套路 ★★：
```cpp
bool fight(Monster& other) {
    while (true) {
        if (attack(other)) return WIN;
        if (other.attack(*this)) return LOSE;
    }
}
```
判断依据：**双方轮流攻击直到一方死亡** → `while(true)` + 双向调用。

### 五种抽象对象对照表 ★★★

| 抽象类型 | 反例特征 | 正例做法 | 好处 |
|---|---|---|---|
| 类型的抽象 | — | 按上位概念层次归类（人物→历史人物→周文王） | 明确抽象粒度 |
| 数据的抽象 | 成员变量堆砌 | 打包成子对象（BasicInfo等） | 类更清晰、可复用 |
| 参数的抽象 | 参数表过长，顺序易错 | 打包成结构体/类（LoginInfo） | 加字段不改签名 |
| 代码的抽象 | 代码块写死在函数体内 | 把易变部分抽成参数/成员（TakeOff→FlyProcess→proc指针） | 易变部分可替换，不改主类 |
| 行为的抽象 | 同类行为重载多个方法（ride/drive） | 统一为通用方法（moveBy(Vehicle&)） | 新增场景不改类 |

**判断口诀**：看到"函数参数一堆"→参数抽象；看到"函数体里一堆步骤"→代码抽象；看到"一堆同名不同参重载"→行为抽象。

## 三、信息隐蔽 ★★★

| 要点 | 结论 |
|---|---|
| 隐藏行为 | 内部辅助步骤设 `private`（如 `hitBorder`），只暴露对外有意义的操作（如 `stepMove`） |
| 隐藏数据 | 成员变量设 `private`，靠 public 的 setter/getter 间接访问 |
| **易错点** | `private` 只是**对外部不可见**，类自己的其他成员函数仍可正常调用 |

## 四、分离使用和实现 ★★

| 角色 | 只关心 |
|---|---|
| 使用者（调用方） | public 接口能做什么 |
| 实现者 | 成员函数怎么实现、数据怎么组织 |

**核心结论**：类不应该耦合"数据从哪来"的逻辑（如 `cin>>` 不该写在类方法里），应该由外部（调用方）准备好数据再传入构造函数/方法。

## 五、类的设计

### 多个类的设计（4个维度）

| 维度 | 说明 |
|---|---|
| 类的拆分 | 一个类太复杂 → 拆成协作的多个类（Application 持有 Input/Output/Config 指针） |
| 类的合并 | 太碎 → 合并 |
| 数据关系 | 类之间持有指针/引用 |
| 行为关系 | 方法内部调用别的类方法，常用 `*this` 把自己传出去 |

### 单个类的设计（6个维度）★★

| 维度 | 关键代码特征 |
|---|---|
| 行为的可见性 | public/private 划分接口与内部方法 |
| 行为参数的抽象与封装 | 多个重载 bark(A)/bark(B)/... → 统一 bark(Dest&) |
| 依赖与关联 | 依赖=每次传参；关联=成员持有(setDest+私有指针)；委托=函数体转发给内部对象 |
| 实现的抽象与封装 | 与依赖关联手法一致，应用于函数体内部逻辑 |
| 数据的抽象与封装 | 散乱成员变量 → 打包成独立数据类（Dog持有DogData*指针） |
| 类方法与实例方法 | `static` 成员函数=类方法(不依赖对象)；普通成员函数=实例方法 |

**依赖 vs 关联判断依据**：
- 目标每次可能变 → 参数传入（依赖）
- 目标长期不变、反复使用 → 成员变量持有（关联），调用更简洁

**委托代码特征**：函数体只是 `pobj->func()` 转发，自己不干活。

## 六、例题 —— 高频考点区

### 6.1 分页器：三大函数是否需要自定义 ★★★

| 方法 | 是否自定义 | 判断依据 |
|---|---|---|
| 构造函数 | **需要** | 要按传入信息初始化 num/total 等状态 |
| 拷贝构造函数 | **不需要** | 成员全是简单值类型(int)，默认逐成员拷贝已正确 |
| 赋值函数 | **不需要** | 同上 |
| getter/show() | 视需要 | 看外部是否要读取内部状态 |

**★★★核心判断规则（必考）**：
> 类持有**需要深拷贝的资源**（指针、动态内存）→ 必须自定义拷贝构造+赋值函数
> 类只有**纯值类型成员**（int/float等）→ 用编译器默认版本即可，不用自己写

### 6.2 工厂方法 ★★★

**问题触发条件**：类有多个重载构造函数 → ① 语义不清楚 ② 不易扩展

**解法模板**：
```cpp
class X {
public:
    static X createXxx(参数) { return X(参数); }  // 有名字的静态方法
private:
    X(参数) {}   // 构造函数私有化
};
```

**判断依据**：调用方需要"见名知意"地创建对象时用工厂方法；构造函数本身私有，只能通过静态方法创建。

### 6.3 单件（Singleton）模式 ★★★ 最高频考点

**必备三要素（缺一不可）**：
1. 构造函数 `private`
2. 拷贝构造函数、赋值运算符禁用（`= delete` 或只声明不实现）
3. 提供 `public static` 的唯一获取入口（如 `getInstance`）

**两种实现对比表（必考对比）**：

| 对比点 | 局部静态变量法 | 堆上 new 法 |
|---|---|---|
| 核心代码 | `static Ball& getInstance(){ static Ball aBall; return aBall; }` | `static Ball* getInstance(){ if(spBall==nullptr) spBall=new Ball; return spBall; }` |
| 返回类型 | 引用 `Ball&` | 指针 `Ball*` |
| 释放 | 程序结束自动析构 | 需手动调用 `releaseInstance()` 释放，易忘 |
| 类外代码 | 不需要 | 需要 `Ball* Ball::spBall = nullptr;` 类外初始化静态成员 |
| 现代写法推荐 | ✅ 推荐 | 传统写法 |

**易错点**：
- 忘记类外初始化 `static` 成员变量指针（方式二必须写 `Ball* Ball::spBall = nullptr;`）
- 忘记禁用拷贝构造和赋值运算符，导致可以通过拷贝产生第二个实例
- 混淆返回类型：方式一返回引用，方式二返回指针
