# 第13章 类间关系 —— 考前速记版

## 知识结构导览（精简版）

```
类间关系
├── 垂直：泛化 / 实现（本章不展开）
├── 水平
│   ├── 关联 ★★★（长期持有对方）
│   │   ├── 一般关联（单/双向，1-1、1-N、N-N）
│   │   ├── 自关联（关联同类对象）
│   │   ├── 关联类（关系本身有数据 → 独立成类）
│   │   └── 聚集关联 ★★★
│   │       ├── 聚合 has-a：不管生死
│   │       └── 组合 contain-a：管生死
│   └── 依赖 ★★★（临时用一下）
│       参数 / 返回值 / 函数体内局部创建销毁
└── 编译期依赖强度（工程角度）★★★
    继承 > 硬关联 > 强关联 > 弱关联 > 软关联
```

---

## 一、联系方向

| 单向 | 双向 |
|---|---|
| 只有一方持有对方，另一方不知情 | 双方互相持有，需 `class B;` 前置声明破循环 |

**判断依据**：看是否两个类都出现了对方的指针/引用成员。

---

## 二、关系强弱四级（★★★高频考点：判断某段代码属于哪一级）

| 级别 | 触发条件 | 依赖发生位置 | 强度 |
|---|---|---|---|
| 硬关联 | 双向关系 + 一方对另一方是强关联 | .h 互相 include，用对象成员 | 最强，应避免 |
| 强关联 | 对象成员 / 内联函数中直接调用对方成员 | .h 中 include | 强 |
| 弱关联 | 只在 .cpp 实现中用到对方（返回值等） | .cpp 中 include | 较弱，**最常见/推荐** |
| 软关联 | 只用指针或引用，不调用成员 | .h 中只需前置声明 | 最弱，最理想 |

**易混点**：
- "强关联"看**是否用对象成员或内联函数**；"硬关联"必须同时满足**双向 + 强关联**，二者不能混淆。
- "弱关联"和"软关联"都不需要在 .h 里 include，区别在于：弱关联是"只在 .cpp 里才需要包含"（.h 只需前置声明或不涉及），软关联是"只用指针/引用，连 .cpp 里可能都不需要调用对方成员"。

**判断口诀**：
1. B.h 必须 include A.h → 强关联（对象成员 / 内联函数）
2. 双向 + 强关联 → 硬关联
3. 只有 A.cpp 需要 include B.h → 弱关联
4. 只用指针/引用，A.h 里只需前置声明 → 软关联

**降低耦合的通用手段 ★★★**：
- 数据成员：指针 > 引用 ≈ 对象（能不用对象就不用对象）
- 函数参数：用指针/引用传递
- 函数返回值：尽量不直接返回对象
- 配合：前置声明 + 类外实现（外联）

**对象/引用/指针作为成员的优缺点对比**：

| 形式 | 缺点 | 优点 |
|---|---|---|
| 引用 | 必须用初始化列表；对象禁止赋值；被引用对象生存期须更长 | — |
| 对象 | 定义前必须看到完整定义（强关联） | 编译器自动处理构造/复制/赋值 |
| 指针 | 可能需自己写构造/复制/赋值/析构 | 最灵活，程序员完全控制 |

## 三、关联 vs 依赖（★★★核心判断题）

| 判断标准 | 关联 | 依赖 |
|---|---|---|
| 语义 | 长期持有，"一直知道" | 临时使用，用完即分开 |
| 代码位置 | 数据成员 | 函数参数 / 返回值 / 函数体内局部变量 |

| 代码形式 | 归类 |
|---|---|
| `class B { A* mpA; };` | 关联（数据成员） |
| `void Func(A* pa);` | 依赖（参数） |
| `A* Func01();` | 依赖（返回值） |
| 函数体内 `new A` 用完 `delete` | 依赖（局部临时） |

UML符号：关联=**实线**，依赖=**带箭头虚线**。

---

## 四、关联关系的四个子类型

| 子类型 | 关键词 | 例子 |
|---|---|---|
| 一般关联 | 非偶然性"知道"；可单/双向；可1-1/1-N/N-N | Student ↔ University / Course |
| 自关联 | 关联**同一个类**的对象 | Student 有 mates[]、super（都是 Student*） |
| 关联类 | 关系本身携带数据 → 独立建模 | Student *-* Course *-* Teacher |
| 聚集关联 | 强调"整体-部分" | 见下节聚合/组合 |

---

## 五、聚合 vs 组合（★★★高频考点）

| | 聚合 Aggregation | 组合 Composition |
|---|---|---|
| 语义 | has-a | contain-a |
| 生死控制权 | B **不**负责 A 的创建/销毁 | B **负责** A 的创建/销毁 |
| UML符号 | 空心菱形 ◇ | 实心菱形 ◆ |
| 代码特征 | 构造函数**外部传入**指针，析构**不 delete** | 构造函数内部 **new**，析构 **delete** |

```cpp
// 聚合：外部传入，不负责生死
class B { public: B(A* pa): mpA(pa) {} private: A* mpA; };

// 组合：内部创建，负责生死
class B { public: B(int n){mpA=new A(n);} ~B(){delete mpA;} private: A* mpA; };
```

**★★★易错点**：聚合/组合是**程序设计逻辑关系**，不能照搬现实世界直觉。
- 例：计算机有无网卡都叫计算机 → 聚合；汽车没轮子不算汽车 → 组合。
- 判断标准只有一个：**部分对象的生命周期是否由整体对象来管理**，不是"是不是整体的一部分"的生活常识。

## 六、经典案例速记

### 老鼠吃苹果（依赖关系设计）

- 老鼠不"一直知道"某个苹果，苹果也不"一直知道"某只老鼠 → **依赖**，不是关联。
- 吃的行为放哪个类？**放在主动、多变的一方**（老鼠是主动方）→ `Mouse::eat(Apple&)`。
- 也可以双向都写：`Mouse::eat()` 调用 `Apple::eatenBy()`，二者互相依赖。

### 学生与宿舍（同一问题，不同关注点 → 不同关系）★★★

| 方向：学生→宿舍 | 是否可为空 | 生死控制 |
|---|---|---|
| 一般关联 | 可以没有宿舍 | 外部创建，Student 不销毁 |
| 聚合 | 可以没有宿舍 | 外部创建，Student 不销毁 |
| 组合 | 必须有宿舍 | Student 自己 new/delete |

| 方向：宿舍→学生 | 生死控制 |
|---|---|
| 普通关联 | 只是知道住了哪些学生（查询用） |
| 组合 | 宿舍 new/delete 学生对象 |
| 聚合 | 宿舍只收纳已存在的学生指针，AddStudent/RemoveStudent 只操作指针，不 delete |

**结论**：关系怎么选，取决于**问题域和程序关注点**（以学生为中心 or 以宿舍为中心），没有唯一标准答案。

### Hero 与 Map / Goods / NPCs（开放练习，供参考）

| 关系对象 | 常见判断方向 |
|---|---|
| Hero - Map | 聚合（Hero 知道地图，但不负责创建/销毁地图） |
| Hero - Goods | 组合（背包物品随英雄创建/销毁而管理） |
| Hero - NPCs | 依赖（临时交互，非长期持有） |
