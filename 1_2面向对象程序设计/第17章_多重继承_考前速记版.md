# 第十七章 多重继承 —— 考前速记版

## 知识结构导览（精简版）

```
多重继承
├── 语法与顺序：class D: public B1, protected B2；构造按顺序，析构相反
├── 命名冲突：同名成员 → 模棱两可 ★★★
│   ├── 解法1：作用域限定 B::f()
│   └── 解法2：using A::f;（只能选一个做默认）
├── 菱形结构 ★★★：B、C 同继承 A，D 继承 B、C → A 被复制两份
│   └── 名字不重复也照样二义（本质是子对象重复，不是名字问题）
├── 虚基类 ★★★：virtual public A → D 中 A 只保留一份
│   └── 缺点：需基类提前配合 + 向上转型难 + 多一层间接寻址
└── 其它方案（绕开菱形，不用virtual）
    ├── 限定单继承：多余基类改为组合（成员变量）
    ├── 接口继承：至多1个普通类 + 其余全是接口类（无实例变量）
    └── Mixin：多基类叠加，但带数据的基类间不能有公共祖先
```

---

## 本章核心问题 ★★★（全章基调，必须掌握）

| 层次 | 问题 | 解法 |
|---|---|---|
| 第一层：命名冲突 | 两基类同名成员 → 模棱两可 | 作用域限定 / using（较表面） |
| 第二层：菱形结构（**真正核心**） | B、C 同继承 A，D 继承 B、C → D 中 **A 被复制两份** | 虚基类 / 单继承+组合 / 接口继承 / Mixin |

**核心结论 ★★★：问题的本质不是"名字重复"，而是"同一个基类子对象被沿不同路径复制了多份"。** 即使名字都不重复，菱形结构依然二义（如 `d.fA()`）。

**记忆锚点**：后面所有解决方案，本质都在回答同一个问题——
- **虚基类** = 技术手段：让共享祖先只保留一份存储
- **单继承+组合 / 接口继承 / Mixin** = 设计手段：从源头避免"带状态的基类"被多条路径重复继承

---

## 一、语法与构造析构顺序

| 要点 | 结论 |
|---|---|
| 语法 | `class D: public B1, protected B2 { };`，逗号分隔，各基类继承方式可不同 |
| 构造顺序 ★★★ | 严格按**继承列表声明顺序**（不是初始化列表书写顺序） |
| 析构顺序 ★★★ | 与构造**完全相反** |
| 存储格式 | 各基类子对象依次拼接存放 + 派生类自身成员 |

---

## 二、命名冲突

| 现象 | 结论 |
|---|---|
| 两个基类有同名成员，派生类直接用 | 编译错误：**模棱两可（ambiguous）** ★★★ |
| 解法1：作用域限定 | `B::f()`、`A::mNum`，每次都要写全 |
| 解法2：using 声明 ★★★ | `using A::f;` 后，`f()` 默认指向 `A::f`；另一个仍需 `B::f()` 显式访问 |
| 易错点 | using **不是合并**，是"选定一个做默认"，另一份依然存在 |

**判断依据**：只要两个基类有相同名字（无论函数还是变量），只要没有限定/using，一律判"错误：二义"。

---

## 三、菱形结构（钻石结构）★★★ 高频考点

```
    A
   / \
  B   C
   \ /
    D
```

| 要点 | 结论 |
|---|---|
| 结构 | B、C 都继承 A，D 同时继承 B、C |
| 根本问题 | D 中有**两份 A 的拷贝**（经B一份，经C一份），互不同步 |
| 关键考点 ★★★ | **即使 A/B/C/D 中所有成员名字都不重复**，`d.fA()` 依然报错——因为不知道走哪条路径的 A |
| using 能否解决 | 只能指定走哪条路径（如 `using B::fA;`），**问题本质未解决**：另一份 A 依然存在、依然可通过 `d.C::fA()` 访问，两份数据不同步 |
| 一句话结论 | 冲突的本质不是"名字重复"，而是"**共同祖先子对象被复制多份**" |

---

## 四、虚基类（virtual）解决方案 ★★★

| 要点 | 结论 |
|---|---|
| 语法 | 中间层写 `class B: virtual public A`、`class C: virtual public A` |
| 效果 | D 中**只保留一份** A 的子对象，`d.FA()` 正确无歧义 |
| 存储格式变化 | 多一层指针/偏移量表：B、C 子对象内部存 `A* p` 指向共享的那份 A，A 数据整体后置、由 D 统一构造 |
| 缺点1 ★★★ | 要求 B、C 的作者**提前**声明 virtual，否则现成类库无法事后补救 |
| 缺点2 | 类型的向上转换（D* → A*）更复杂、有额外开销 |

**判断依据**：题目若问"如何让菱形结构中共同基类只有一份" → 答案必是"虚基类/virtual继承"。

---

## 五、其它三种解决方案（不用virtual，从设计上规避菱形）

### 冲突本质回顾
- 函数名冲突（无状态）→ 问题较轻
- 实例变量冲突（有状态）→ 才是菱形结构真正的痛点
- 核心经验 ★★★：**只要带实例变量的基类不被重复继承，就不会有菱形问题**

### 三种方案对比

| 方案 | 做法 | 关键限制 |
|---|---|---|
| **限定为单继承** | 保留一条真正继承（is-a），其余用**组合**（成员变量，has-a）代替 | 指针成员形式需自己写拷贝构造/赋值/析构（三/五法则） |
| **接口继承** | 多个基类中**至多1个**带实例变量（普通类），其余全是**接口类** | 接口类：无实例变量、成员多为 `public`、常用纯虚函数 `=0` 强制实现 |
| **混入 Mixin** | 允许多个互相独立的基类叠加，但**带实例变量的基类之间不能有公共祖先** | 一旦两个"混入"的基类共享祖先 → 又变回菱形问题 |

### 无实例变量类的两种常见形态
| 类型 | 用途 |
|---|---|
| 用类型做区分标志 | 如自定义异常类 `ENormal`/`ESpecial` 代替 `throw 1/2` 魔法数字 |
| 工具类 | 只放 `static` 函数/变量，不需要实例化，如 `PackUtility` |
