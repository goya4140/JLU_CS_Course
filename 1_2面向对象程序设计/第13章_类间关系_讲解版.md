## 二、类间的联系方向

在两个类 A、B 之间建立联系时，首先要确定"谁认识谁"，这决定了代码结构。

- **单向联系**：只有一方持有对方的信息，比如 B 认识 A，但 A 完全不知道 B 的存在。这是最简单、耦合最小的写法。
- **双向联系**：A、B 互相持有对方的指针/引用，两边都能访问对方。这在现实建模中很常见（比如"学生知道自己的宿舍，宿舍也知道住了哪些学生"），但会带来循环依赖问题，需要用**前置声明**（`class B;`）来解决"谁先声明谁"的先后矛盾。

| 单向联系 | 双向联系 |
|---|---|
| `class A { };`<br>`class B { public: void f(A& a); private: A* mpA; };` | `class B;`<br>`class A { B* mpB; };`<br>`class B { public: void f(A* p); A g(); private: A* mpA; };` |
| 只有 B 认识 A，A 对 B 一无所知 | A、B 互相持有对方，需要用 `class B;` 前置声明来打破"先有鸡还是先有蛋"的循环 |

**理解要点**：双向联系不是语法糖，而是真实的双向耦合——改一方的接口，往往两个类都要重新编译。所以能用单向就不用双向。

## 三、类间关系的强弱（编译期依赖角度）

这一节的核心问题是："B 类要编译通过，到底离不离得开 A 的完整定义？" 离不开的程度不同，依赖的"强度"也不同。这是一个非常工程化的视角——不是在谈论逻辑语义（比如是不是"整体-部分"），而是在谈论**编译效率和耦合成本**。

### 3.1 强关联

**是什么**：如果 `B.h` 必须 `#include "a.h"` 才能编译通过，就说 A 和 B 之间存在强关联。

**为什么会发生**：常见于两种写法——
1. B 把 A 当作**对象成员**（而非指针/引用）；
2. B 的成员函数**内联**（写在类定义里）调用了 A 的成员，编译器需要看到 A 的完整定义才能做类型检查。

| 例1：对象成员导致强关联 | 例2：内联函数导致强关联 |
|---|---|
| `//b.h`<br>`#include "a.h"`<br>`class B {`<br>`    A mA;`<br>`};` | `// b.h`<br>`#include "a.h"`<br>`class B {`<br>`public:`<br>`    void f(A* pA) {`<br>`        pA->g();`<br>`    }`<br>`};` |
| 因为 `A mA` 是对象而非指针，编译器需要知道 A 的大小，必须包含 `a.h` | 内联函数体里直接调用了 `pA->g()`，编译器要检查 `g()` 是否存在、参数是否匹配，也必须包含 `a.h` |

**结论**：
1. 尽可能不用对象成员，改用指针或引用；
2. 尽可能不要把成员函数写成内联形式（不要直接写在类定义里），而是用**前置声明 + 类外实现**（外联）来避免头文件依赖。

**类比**：这就像你写合同时，如果条款里写"某物品的详细规格全文照抄"，那你必须先看到规格全文才能写合同；但如果只写"参见附件 X"，你可以先把合同签了，附件以后再对。

### 3.2 硬关联

**是什么**：A 和 B 之间存在**双向关系**，并且 B 对 A 是**强关联**（比如 B 里有 `A mA` 对象成员），这种"双向 + 强"的组合就叫硬关联——是最紧耦合的形式。

```cpp
// A.h
class B;              // 前置声明打破循环
class A {
public:
    A(int);
    B foo();           // A 认识 B（但只是声明，未强依赖）
private:
    int mData;
};

// B.h
#include "A.h"          // B 必须看到 A 的完整定义
class B {
public:
    B();
    B(int);
private:
    A mA;               // 对象成员 → 强关联
};
```

**理解要点**：硬关联之所以"硬"，是因为一旦 A 的定义（比如成员变量）发生变化，B 必须重新编译；而且因为是双向的，A 的接口变化也会波及 B，形成"牵一发动全身"的耦合链条。这是四种强度里最应该避免的写法。

### 3.3 弱关联

**是什么**：不是在头文件（.h）中要求包含对方，而是**只在 .cpp 实现文件中**才需要包含对方的头文件。也就是说，类的**声明**层面互不依赖，只有函数体的**实现**层面才需要用到对方的完整定义。

```cpp
// A.h —— 完全不需要 include b.h
class A {
public:
    A(int);
    B Func();          // 只是声明返回类型为 B（这里其实需要前置声明 class B;）
private:
    int mData;
};

// A.cpp —— 只有在实现里才需要真正用到 B 的完整定义
#include "a.h"
#include "b.h"
B A::Func() {
    return B(mData);
}
```

**结论**：这是**最常见、也是最值得推荐**的关联形式——头文件之间保持轻量，具体实现细节放到 .cpp 里去处理依赖。

### 3.4 软关联

**是什么**：A 只使用了 B 的**指针或引用**（不涉及对象、不需要调用 B 的成员函数），A 的头文件里只需要一个前置声明就够了。

```cpp
// A.h
class B;                  // 只需要前置声明
class A {
public:
    A(B* pb);
private:
    B* mpB;               // 指针形式，不需要 B 的完整定义
};
```

**结论**：尽可能使用指针或引用作为数据成员；函数参数尽量以指针或引用传递；函数返回值也尽量不要用"传值返回对象"的方式——这些都能把依赖降到最低。

### 3.5 四种强度对照表

| 关联类型 | 触发条件 | 依赖位置 | 耦合程度 |
|---|---|---|---|
| 硬关联 | 双向关系 + 一方对另一方是强关联 | .h 互相 include，且用对象成员 | ★★★★（最强，应避免） |
| 强关联 | 对象成员，或内联函数直接调用对方成员 | .h 中 include | ★★★ |
| 弱关联 | 只在返回值/实现细节中用到对方 | .cpp 中 include | ★★（推荐，最常见） |
| 软关联 | 只用指针/引用 | .h 中只需前置声明 | ★（最弱，最理想） |

### 3.6 降低编译期依赖性的整体策略

把上面几条策略汇总一下，实际上就是贯穿整章的一条设计原则——**"能用指针/引用，就不用对象"**：

- **自定义类型的数据成员**：优先用指针形式。
  - 引用形式的缺点：必须在构造函数初始化列表里赋值、对象一旦创建不能重新赋值（禁止赋值运算）、被引用对象的生存期必须比当前对象长。
  - 对象形式的缺点：定义当前类之前，必须先看到被包含类的完整定义（导致强关联）；但好处是编译器自动帮你处理构造、复制、赋值（不用自己写）。
  - 指针形式的缺点：可能需要你自己写构造、复制、赋值、析构（管理生命周期更麻烦）；好处是最灵活，完全由程序员自己控制。
- **函数的自定义类型参数**：用指针或引用传递，避免传值时的额外拷贝和强依赖。
- **函数返回的自定义类型**：尽量不要直接返回对象（除非必要），可结合前置声明和外联实现来减少依赖。

**类间联系强度从强到弱的完整排序**（含继承）：

1. 继承（类间的**垂直**关系，天然最强的耦合——子类完全依赖父类的实现细节）
2. 硬联系（硬关联）
3. 强联系（强关联）
4. 弱联系（弱关联）
5. 软联系（软关联）

## 四、类间的逻辑关系

上一节讲的是"工程实现角度"的强弱，这一节回到 UML/面向对象设计的**逻辑语义**角度，重新审视类间关系的分类。

- **垂直方向**（表示"类型层级"）：泛化（继承）、实现（接口实现）——本章不展开，后续章节详述。
- **水平方向**（表示"对象之间的协作关系"）：**关联**、**依赖**——这是本章的重点。

### 4.1 关联 vs 依赖：怎么区分？

两者的**代码形式**其实经常长得很像，区分的关键不在语法，而在于**语义**：这个类是否需要"长期持有、一直知道"对方。

| 代码形式 | 说明 | 属于哪种关系 |
|---|---|---|
| `class B { A* mpA; };` | A 作为 B 的**数据成员**，贯穿 B 对象的整个生存期 | **关联** |
| `class B { void Func(A* pa); };` | A 只是**函数参数**，用完即走 | 依赖 |
| `class B { A* Func01(); };` | A 只是**函数返回值**，临时产生 | 依赖 |
| `int B::Func02(int n) { A* pa = new A; ...; delete pa; return val; }` | A 只在**函数实现内部**临时创建、使用、销毁 | 依赖 |

**核心判断标准**：关联关系强调"B 类对象在其整个生存期内，都'一直知道'A 类对象"（比如作为成员变量长期持有）；依赖关系则是"临时的、用完即分手"的关系——A 只是作为参数传进来、或作为返回值临时产生、或在函数内部临时用一下，不会长期存在于 B 对象内部。

**类比**：关联就像你和你的室友——只要你们同住一个宿舍，你就一直"认识"他；依赖就像你去便利店买瓶水——你和收银员只在那一刻发生了交互，交易结束后彼此就没关系了。

## 五、关联关系详解

### 5.1 一般关联

**含义**：强调"非偶然性的知道"——不是临时用一下，而是长期持有对方的引用/指针作为成员。

**特点**：
- 可以是单向，也可以是双向
- 基数（多重性）可以是一对一、一对多、多对一、多对多

**例子**：学生与大学、课程的关系

```cpp
class University;
class Course;

class Student {
public:
    ....
private:
    University* univ;         // 一对一：一个学生对应一所大学
    Course* courses[30];      // 一对多：一个学生可以选多门课程
};
```

UML 表示为一条实线，箭头方向表示"谁知道谁"（这里是 Student → University，Student → Course）。

### 5.2 自关联

**含义**：一个类的对象关联同一个类的另一个（或多个）对象——即"自己认识自己类型的其他对象"。

**例子**：学生认识自己的室友和辅导员（辅导员本身也是学生管理系统里的一种角色，这里做简化类比）

```cpp
class Student {
public:
    ....
private:
    Student* mates[3];   // 关联同类的其他对象——室友
    Student* super;      // 关联同类的其他对象——上级/学长
};
```

**类比**：就像"员工"类里有个"经理"字段——经理本身也是员工类型的对象，这就是典型的自关联。

### 5.3 关联类

**含义**：当两个类之间的关联关系本身也携带了额外信息（不只是"谁认识谁"，还有"认识的细节"）时，可以把这层关联关系单独抽象成一个类——它既表示关系，也表示关系对应的数据。

**例子**：学生和老师是多对多的关联（一个学生对应多个老师，一个老师对应多个学生），而"课程"正好承载了这层关系（是这门课把老师和学生连接起来的），于是把 Course 设计成一个独立的关联类：

```
Student *---* Course *---* Teacher
```

Course 类提供 `getStudent()`、`getTeacher()`、`setStudent()`、`setTeacher()` 等接口，既是关联的载体，本身也是一个有意义的实体（有课程名称、学分等属性）。

**理解要点**：不是所有多对多关系都需要关联类，只有当"关系本身"携带了额外语义信息时，才值得单独建模成一个类。

## 六、聚集关联：聚合与组合

聚集关联是关联关系里的一个特殊子类，专门用来表达**"整体-部分"**的语义。它又细分为两种：**聚合**和**组合**，二者的代码形式几乎一样，区别只在于——**谁负责被包含对象的生死**。

### 6.1 核心区别

| | 聚合（Aggregation） | 组合（Composition） |
|---|---|---|
| 语义 | B "has-a" A | B "contain-a" A |
| 生死控制 | B **不**负责 A 对象的创建和销毁 | B **负责** A 对象的创建和销毁 |
| UML 符号 | 空心菱形 ◇ | 实心菱形 ◆ |
| 生存期关系 | A 的生死与 B 无关，A 可以独立于 B 存在 | A 的生死由 B 决定（不一定完全同生共死，但创建/销毁的责任在 B） |

### 6.2 代码对比

| 聚合关系（不负责创建/销毁） | 组合关系（负责创建/销毁） |
|---|---|
| `class A;`<br>`class B {`<br>`public:`<br>`    B(A* pa): mpA(pa) { }`<br>`private:`<br>`    A* mpA;`<br>`};` | `class A {`<br>`public:`<br>`    A(int n);`<br>`};`<br>`class B {`<br>`public:`<br>`    B(int n) { mpA = new A(n); }`<br>`    ~B() { delete mpA; }`<br>`private:`<br>`    A* mpA;`<br>`};` |
| A 对象是从外部传进来的（B 构造时"借用"一个已存在的 A），B 析构时不会 delete 它 | A 对象是 B 在内部 `new` 出来的，B 的析构函数负责 `delete`，B 完全控制 A 的生命周期 |

**关键判断标准**：看**构造函数怎么拿到成员对象**、**析构函数是否负责释放**——如果是外部传入指针、析构不 delete，就是聚合；如果是内部 new 出来、析构负责 delete，就是组合。

### 6.3 一个重要提醒：逻辑关系 ≠ 现实世界直觉

PPT 里特别强调了一点：聚合、组合是**程序设计层面的逻辑关系**，不能简单套用现实世界里"东西是不是这个物体的一部分"的直觉，要看**具体的编程场景需求**。

**现实世界例子**：
- 计算机有网卡才叫"完整的"计算机，但没有网卡也依然可以被称为计算机——所以更适合用**聚合**关系（网卡可以独立存在、可插拔）。
- 汽车没有轮子就不能叫汽车（功能上不完整）——所以更适合用**组合**关系（轮子和车身生死绑定）。

**类比理解**：聚合像"公司和员工"——公司解散了，员工依然作为独立的人存在，去别的公司上班；组合像"人和心脏"——心脏是人体的一部分，人没了心脏这个"部件对象"的意义也随之终结（在这个类比的抽象层面上）。

**设计要点**：到底选聚合还是组合，不是看"感觉上像不像整体的一部分"，而是要问自己：**这个部分对象的生命周期，是应该由整体对象来管理，还是可以独立存在、被多个整体共享？** 针对具体的问题域来做决定。

## 七、依赖关系详解

### 7.1 依赖关系的四种代码形式（与关联的对照）

前面第四节已经列过这张表，这里从"依赖"的角度再强调一遍：

```cpp
// 1. 函数参数：A 只是临时传进来用一下
class B { void Func(A* pa); };

// 2. 函数返回值：A 只是临时产生并返回
class B { A* Func01(); };

// 3. 函数实现内部：A 在函数体内临时创建、使用、销毁，B 的类定义中完全看不到 A
int B::Func02(int n) {
    A* pa = new A;
    int val = pa->g() + n;
    delete pa;
    return val;
}
```

UML 中依赖关系用**带箭头的虚线**表示（区别于关联的实线），这也直观地表达了"依赖是临时的、弱的联系"。

### 7.2 案例：老鼠吃苹果

**题目**：老鼠在苹果园中吃苹果，老鼠每吃一个苹果，就根据该苹果所含能量增加一些体重。设计老鼠和苹果类。

**分析过程（这是本章设计思维的精华所在）**：

1. **判断关系类型**：老鼠不需要"一直知道"某一个具体的苹果，苹果也不需要"一直知道"是被哪只老鼠吃掉的——两者不构成长期持有关系，所以不适合用关联（不需要成员变量互相持有），**依赖关系**就足够了。
2. **判断行为放在哪个类**：吃这个行为，是苹果和老鼠共同参与的动作。可以从两个角度实现：
   - 放在**老鼠类**里，语义是"我（老鼠）主动吃掉了它（苹果）"——对应方法名 `eat()`；
   - 放在**苹果类**里，语义是"我（苹果）被它（老鼠）吃掉了"——对应方法名 `eatenBy()`。
3. **设计原则**：核心功能应该放在"主动的、多变的"那个类里。老鼠是主动发起动作的一方（吃的行为由老鼠发起），所以更自然的设计是把 `eat()` 放进 Mouse 类。

**方案一：吃的逻辑放在 Mouse 类（推荐，因为老鼠是主动方）**

```cpp
// 苹果类
class Apple {
public:
    Apple(int e): mPower(e) { }
    int getEnergy() const { return mPower; }
private:
    int mPower;
};

// 老鼠类
class Mouse {
public:
    Mouse(int w): mWeight(w) { }
    int getWeight() const { return mWeight; }
    void eat(Apple& one) {
        mWeight += one.getEnergy() * 0.5;   // 老鼠主动"吃"苹果，增加体重
    }
private:
    int mWeight;
};
```

在这个方案里，Mouse 依赖 Apple（Mouse::eat 的参数是 Apple&），但 Apple 完全不知道 Mouse 的存在——**单向依赖**。

**方案二：吃的逻辑同时存在于两个类（eat 和 eatenBy 互相配合）**

```cpp
// 苹果类
class Apple {
public:
    Apple(int e): mPower(e) { }
    int getEnergy() const { return mPower; }
    void eatenBy(Mouse& m) {
        int w = m.getWeight();
        m.setWeight(w + mPower * 0.5);   // 苹果"被吃"，反过来修改老鼠的体重
    }
private:
    int mPower;
};

// 老鼠类
class Mouse {
public:
    Mouse(int w): mWeight(w) { }
    int getWeight() const { return mWeight; }
    void setWeight(int w) { mWeight = w; }
    void eat(Apple& one) { one.eatenBy(*this); }   // 老鼠调用苹果的 eatenBy，把自己传进去
private:
    int mWeight;
};
```

这个版本里 Apple 和 Mouse 互相依赖（双向依赖）——Mouse 依赖 Apple（在 eat 里用到 Apple），Apple 也依赖 Mouse（在 eatenBy 里用到 Mouse）。这种写法体现了"事件双方都可以有自己的视角"，但也带来了循环依赖，需要前置声明配合。

## 八、综合案例：学生与宿舍

这是本章最重要的一个综合案例，因为它展示了**同一个问题域，根据不同的关注点，可以选用完全不同的类间关系**。

**题目**：每个学生的信息除了姓名、学号，还要有宿舍信息（几号楼、第几层、几号房间、住了哪些学生）。

### 8.1 现实世界 vs 程序设计的落差

现实世界里，学生与宿舍的关系比较模糊，可能是普通关联，也可能是聚合。但在程序设计中，还要考虑**程序的关注点（谁是主角）**：

- 只是"顺带知道地址"，类似通信录场景——用**普通关联**即可；
- 以学生为中心的系统（比如学生管理程序）——学生类里持有宿舍信息，宿舍是学生的一个属性；
- 以宿舍为中心的系统（比如宿舍管理程序）——宿舍类里管理它包含的学生列表，学生是宿舍的一部分。

### 8.2 方向一：学生 → 宿舍

**（1）一般关联**：强调学生"知道"自己的地址信息，但学生也可以没有宿舍（走读生）。

```cpp
class Student {
public:
    Student(Dorm* aDorm): mpDorm(aDorm) { }
    const char* Address() const {
        if (mpDorm)
            return mpDorm->floor();
        else
            return "";     // 允许没有宿舍
    }
private:
    Dorm* mpDorm;
};
```

**（2）聚合**：强调"整体-部分"关系，但学生依然**可以没有宿舍**——宿舍对象由外部传入，Student 不负责创建/销毁它。代码和上面几乎一样，语义侧重点不同（强调这是学生信息里必要的"组成部分"而不只是随便"认识"一下）。

**（3）组合**：强调"整体-部分"关系，且**学生必须有宿舍**（不能为空），宿舍对象由 Student 自己创建和销毁：

```cpp
class Student {
public:
    Student(): mpDorm(new Dorm) { }    // 自己创建
    ~Student() { delete mpDorm; }      // 自己销毁
private:
    Dorm* mpDorm;
};
```

| 关系类型 | 是否可以没有宿舍 | 谁创建/销毁 Dorm |
|---|---|---|
| 一般关联 | 可以（mpDorm 可为空指针） | 外部创建，Student 不负责销毁 |
| 聚合 | 可以 | 外部创建，Student 不负责销毁 |
| 组合 | 不可以（必须有） | Student 自己 new / delete |

可以看到，聚合和一般关联在这个例子里代码形式几乎一样，区别更多在于**语义强调**（是否是"必要组成部分"），而组合和前两者的核心区别在于**生死控制权 + 是否允许为空**。

### 8.3 方向二：宿舍 → 学生

反过来，如果以宿舍为中心：

- **普通关联**：只强调宿舍"知道"住了哪些学生（可能只是存了个列表，用于查询）；
- **组合关系**：宿舍负责创建和销毁学生对象——这在语义上其实不太合理（现实中宿舍不可能"创造"或"消灭"一个学生），但纯粹从代码结构上演示：

```cpp
class Dorm {
public:
    Dorm() {
        for (int i = 0; i < 4; i++)
            mStudents[i] = new Student;      // 宿舍创建学生对象
    }
    ~Dorm() {
        for (int i = 0; i < 4; i++)
            delete mStudents[i];             // 宿舍销毁学生对象
    }
private:
    Student* mStudents[4];
};
```

- **聚合关系**：宿舍**不**负责创建/销毁学生，只是持有已存在的学生对象的指针，并提供添加/移除接口：

```cpp
class Dorm {
public:
    Dorm(Student* s[], int count): maxCount(count) {
        mStudents = new Student*[maxCount];
        for (int i = 0; i < count; i++)
            mStudents[i] = s[i];             // 外部传入，只是"收纳"进来
    }
    ~Dorm() { delete[] mStudents; }          // 只释放指针数组本身，不释放 Student 对象
    void AddStudent(Student* s, int index) {
        if (mStudents[index] == nullptr)
            mStudents[index] = s;
    }
    void RemoveStudent(int index) {
        mStudents[index] = nullptr;          // 只是移除引用，不 delete 学生对象
    }
private:
    int maxCount;
    Student** mStudents;
};
```

**理解要点**：注意组合版本里 `~Dorm()` 会 `delete mStudents[i]`（真正销毁学生对象），而聚合版本里 `RemoveStudent` 只是把指针置空、`~Dorm()` 也只 `delete[] mStudents`（释放的是指针数组这个容器本身，不是里面的学生对象）——这正是聚合"不负责部分对象生死"的具体体现。

### 8.4 练习案例：游戏角色关系设计

PPT 最后留了三个开放性练习题，供巩固本章所学：
- **Hero 与 Map 的关系**：英雄存在于地图上，地图先于英雄存在（或独立于某个英雄存在）——通常适合**聚合**（Hero 知道自己在哪张 Map 上，但不负责创建/销毁 Map）。
- **Hero 与 Goods（物品）的关系**：英雄拥有背包物品，物品通常随英雄的创建而初始化、随英雄销毁而清空——更适合**组合**（Hero 负责管理 Goods 对象的生死）。
- **Hero 与 NPCs 的关系**：英雄与 NPC 之间通常是临时性的交互（对话、交易），用完即分开——更接近**依赖关系**，而非长期持有的关联。

（以上练习题 PPT 未给出标准答案，鼓励结合具体游戏设计场景自行判断——这正体现了本章反复强调的核心思想：**关系怎么选，取决于问题域和程序的关注点，而不是死记硬背某种固定答案**。）

## 九、本章小结

1. **类间关系分两大方向**：垂直方向（泛化、实现，留待后续章节）和水平方向（关联、依赖）——本章聚焦水平方向。
2. **关联 vs 依赖的判断标准**：看对方是否作为**长期持有的成员变量**（关联），还是仅仅作为**函数参数/返回值/局部临时对象**（依赖）。
3. **聚合 vs 组合的判断标准**：都表达"整体-部分"关系，区别在于**整体对象是否负责部分对象的创建和销毁**——聚合不负责（has-a），组合负责（contain-a）。
4. **聚合/组合是逻辑关系，不是现实世界的直觉**：要结合具体程序的问题域来判断，而不是简单套用"是不是必要组成部分"的生活常识。
5. **编译期依赖强度从强到弱依次为**：继承 > 硬关联 > 强关联 > 弱关联 > 软关联；核心原则是**尽可能用指针或引用代替对象成员**，能减少头文件之间的耦合。
6. **降低耦合的具体手段**：数据成员优先用指针；函数参数用指针/引用传递；函数返回值避免直接返回对象；配合前置声明 + 类外实现（外联）来减少头文件依赖。
7. **同一个问题域，关系的选择取决于程序的关注点**（如学生宿舍案例：以学生为中心 vs 以宿舍为中心，会导致完全不同的类间关系设计）。
