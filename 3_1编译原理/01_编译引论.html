1. 编译为什么存在

1.1 人的表达与机器的执行之间有距离

人习惯写 sum = first + count * 10，其中有名字、表达式和运算顺序。处理器执行的却是特定指令集中的操作，例如从内存取值、在寄存器中相乘、把结果写回内存。它不会因为看到字母 count，就自动知道这个名字在哪里、占多大空间、应采用整数乘法还是浮点乘法。

编译程序（compiler）处理这种距离：根据源语言规则理解程序，再把它转换为目标语言中的程序。编译器本身也是程序，它的输入主要是另一份程序文本，因此是一种“处理程序的程序”。

不能把编译简单理解成“把英文换成 0 和 1”。编译首先要弄清结构和含义。例如 a+b*c 应先算乘法；同名 x 在不同函数里可能指不同变量；整数和实数可能需要不同指令。这些问题并不能靠逐字替换解决。

1.2 什么叫正确翻译

课件使用语义等价这个要求。语义是程序按照语言规则所表达的含义；等价意味着在约定的输入和执行条件下，译前与译后的可观察行为应一致。计算结果、输入输出、规定的副作用等都可能是观察对象。

以 sum = first + count * 10 为例，把它翻译成 (first+count)*10 就改变了含义。当 first=2、count=3 时，前者为 32，后者为 50。目标程序跑得再快，也不能弥补这样的错误。

理解补充：等价的精确范围由语言语义决定。涉及溢出、浮点舍入、异常和外部输入输出时，不能只比较理想数学表达式。例如在允许观察舍入差异的环境下，随意改变浮点加法顺序可能改变结果。

3. 程序设计语言的发展

3.1 机器语言：直接对应指令编码

机器语言以处理器规定的二进制编码表达指令。课件概括为“机器指令＝操作码＋操作数地址”：先说明做什么，再说明对什么数据或位置操作。

理解补充：这是入门抽象。具体指令也可能使用寄存器、立即数或隐含操作数，并非每个操作数都必须写成内存地址。机器语言依赖指令集，为一种处理器生成的指令不能无条件交给另一种处理器执行。

3.2 汇编语言：给机器指令起符号名字

汇编语言用助记符、寄存器名和标号表示机器指令，例如装入、存储与加法指令。人比起长串二进制，更容易阅读 LDA、STO 一类符号。

汇编器（assembler）把汇编语言程序转换为机器语言表示。汇编语言仍十分接近机器结构：程序员常需关注寄存器、地址和指令顺序。不能把汇编源文件文本直接当作处理器能执行的指令字节。

3.3 高级语言：按问题和结构描述计算

高级语言提供变量、函数、表达式和控制结构。例如 x=f(i,j) 不直接列出保存返回地址、传递参数和建立运行时空间的指令。

高级语言隐藏了许多机器细节，但这些细节最终仍须由语言实现系统处理。声明类型并不是无用的形式：编译器可能利用类型确定运算规则、空间大小和合法操作。后面的语义分析、存储管理和代码生成章节会逐项解释。

4. 编译、解释与转换

4.1 编译方式：先产生程序，再执行程序

编译方式可以概括为：

源程序 ──编译程序──→ 目标程序
                         ↓ 与输入数据一起执行
                      计算结果

编译时不必执行源程序描述的整个计算。对 read(x); print(x+1); 编译，可以先生成读取、加法、输出的指令；真正的 x 在运行目标程序时才输入。

课件举出 .c/.pas → .obj/.exe。其中 .obj 通常是尚需链接的目标文件，.exe 是某些平台的可执行文件。理解补充：编译、汇编、链接、装载是可分开的环节。链接把多个目标文件及所需库连接起来并处理外部引用；装载把可执行内容安排到运行环境中。不能要求每一次编译都立即产生可单独运行的 .exe。

目标语言也不一定比源语言“级别低”。广义编译包含源到源转换；本课程重点讨论高级语言到较低级表示的翻译。

4.2 解释方式：让实现程序执行输入程序的含义

解释程序（interpreter）接收程序及数据，执行程序描述的操作并产生结果。课件用“边翻译边执行”解释这一过程，强调它通常不先交付一份独立的目标程序。

源程序或中间表示 + 输入数据 ──解释程序──→ 计算结果

例如解释器读到“把 x 加 1”，便在自身运行过程中完成取值和加法。与编译后的程序相比，解释器在执行时通常还承担查找操作和控制执行的工作。

理解补充：解释器可以先进行词法、语法和语义处理，建立树或字节码，然后解释这些内部表示。因而“解释”不等于每运行一次语句就必须从源码字符重新开始，也不等于内部绝不生成代码。区分方式时要看讨论的是哪一层、是否预先生成并执行对应目标程序。

4.3 两种方式的比较要带前提

方面 课件给出的典型认识 理解时需要的前提
翻译结果 编译产生目标程序；解释直接得到执行结果 解释器可以保存内部树或字节码
执行速度 预先编译后通常少承担解释调度开销 实际速度还取决于优化、算法和实现方式
空间 解释执行时常需带着解释器及相关信息 编译产物及运行库也占空间，不能作绝对排序
可移植性 有对应解释器时，同一表示便于跨平台运行 每个平台仍要实现解释器或虚拟机
交互与诊断 解释方式通常便于交互、动态修改与运行时诊断 编译器和调试器也能提供丰富诊断
多次执行 编译成本可由反复运行摊薄 源码改变后可能需要重新编译

选择依据是需求：程序是否频繁变化、是否反复运行、启动与吞吐要求、平台条件等。课件的比较是典型教学场景，不是关于所有实现的性能定理。

4.4 混合实现：不同层次可以采用不同方式

课件备注中的 Java 例子是 .java → .class，再由 JVM 执行字节码。虚拟机是实现一套抽象指令与运行规则的软件或执行系统。它给不同平台提供统一的程序表示。

理解补充：执行字节码可以采用解释，也可以采用即时编译（JIT），即在运行期间把部分代码翻译成机器码。因此先编译字节码与随后解释或即时编译并不矛盾。

Python 源文件通常使用 .py 后缀；课件备注中的 .ph 是笔误。某些实现会生成或缓存 .pyc 字节码，但不能据此断言每次运行每个源文件都必定在磁盘写出 .pyc。这些例子用于理解实现层次，不用于概括语言的全部实现。

4.5 转换方式：借助已有语言实现

假设已有 A 语言的实现，要支持 B，可以安排：

B 程序 ──转换程序──→ 等价的 A 程序 ──A 的实现──→ 结果或目标程序

这样可复用 A 的编译器、库和平台支持。代价是转换器必须保留 B 的语义，必要时补上 A 本身不直接提供的运行支持。

课件认为两种语言接近，或 B 是 A 的扩展时便于采用这种方式。这是实施便利条件，不是数学上的必要条件。课件将 C++ 列为例子，应理解为早期 C++ 到 C 的实现思路，不能据此认定所有 C++ 编译器都先生成 C。

5. 编译程序的六个逻辑阶段

5.1 用一条赋值语句把阶段串起来

以下采用课件的 Pascal 风格程序，三个变量均为实数：

var sum, first, count: real;
begin
    sum := first + count * 10
end.

六阶段形成一条逻辑路线：

字符 → Token → 结构 → 带属性的结构 → 中间代码 → 优化代码 → 目标代码
       词法      语法       语义          生成          优化          生成

每个阶段回答不同问题。它们可以在实现中交错调用，并不必然是六个各自读完整文件的独立程序。

5.2 词法分析：字符怎样组成单词

词法分析按照单词构成规则分离字符，产生 Token，并发现词法错误。对例子得到：

<id,sum> <assign,:=> <id,first> <plus,+>
<id,count> <mult,*> <intConstant,10>

id 表示标识符类别，名字可直接存储，也可通过索引引用名字表。10 是一个常数单词，不能拆成两个彼此独立的数字 Token。词法分析还会处理空白、注释及位置记录。

例如某教学语言不允许 @，读到它便可报告词法错误。对 7L 是否应整体报错、拆成两个 Token，或作为某种数值后缀，必须依据具体语言规则，不能脱离语言作结论。

5.3 语法分析：单词怎样组成合法结构

语法分析依据文法判断 Token 的排列是否合法，并建立结构。例如例子的计算结构可以写成：

赋值
├─ 左边：sum
└─ 右边：加法
   ├─ first
   └─ 乘法
      ├─ count
      └─ 10

树把“乘法先于加法”明确表达出来。语法分析处理括号、语句组成、运算优先级等；仅看字符串里出现了合法单词还不够。first + * count 的每个单词都可能合法，但排列不构成合法表达式。

课件比较 i++ 与 i:=i+1：它们在不同语言中受到不同规则约束。判断错误以前要先确定源语言，不能拿 C 的规则检查 Pascal。

5.4 语义分析：合法结构是否表达合法含义

语义分析建立名字的属性与联系，进行静态语义检查，并为后续翻译准备信息。“静态”指不必执行程序就检查的性质。

常见检查包括名字是否声明、同一作用域中是否重复声明、操作数类型是否允许、赋值双方是否兼容、调用参数是否匹配。课件例子中如果只有 first 和 count 的声明，没有 sum，使用 sum 就是语义问题。

课件另一例把 count 声明成字符。按课件采用的 Pascal 教学规则，字符不能直接进行该乘法；但 C 中字符值可以参与整数提升，因而不能把这个错误原样套到 C 上。

语法检查与语义检查的区别可以这样看：x+y 有合法的加法结构，但若 x 是不支持加法的对象，仍可能语义不合法。符号表帮助编译器知道 x、y 究竟是什么。

5.5 中间代码生成：把复杂结构拆成简单操作

中间代码生成把已经理解的程序转换为便于后续处理的内部表示。课件采用四元式：

顺序 四元式 通俗解释
1 (int-to-real,10,-,t1) 把整数常数 10 转成实数
2 (*,count,t1,t2) 计算实数乘法，结果暂存 t2
3 (+,first,t2,t3) 把 first 与乘法结果相加
4 (:=,t3,-,sum) 把最后结果赋给 sum

为什么必须先转换？例子中 count 是 real，语言规定的混合类型运算可能要求把整数操作数提升为 real。不同类型往往对应不同运算指令；转换把这种要求表达清楚。

为什么需要临时名字？一条四元式只表达简单操作，中间结果需要被下一条引用。t1 等不是程序员声明的名字，而是编译器管理的暂存结果。

课件说明中间代码并非所有编译器都必须单独产生的阶段。如果不需要相应优化与移植安排，也可以在分析过程中直接生成目标代码。这里保留它，便于理解和实现后续处理。

5.6 中间代码优化：在保持行为的前提下减少代价

优化变换程序表示，以改善运行时间、空间或其他指定指标。例子的第一条只把一个已知常数转换成实数，可以在编译时完成：

(*,count,10.0,t2)
(+,first,t2,t3)
(:=,t3,-,sum)

运行时因此少做一次类型转换。这叫常量折叠：编译时计算结果已知的运算，并用结果替换。

课件强调，编译优化通常针对现有程序的实现，不能假定它会自动替学生重新设计更好的求解算法。选择辗转相除而非枚举求最大公约数属于算法设计；发现循环中重复计算的数组地址并减少重复工作属于编译优化的典型内容。

优化本身也消耗编译时间和开发成本。是否优化、优化到什么程度，要在编译速度、程序运行速度与代码大小之间权衡。编译器可以提供多种优化等级；优化不是保证所有指标都同时改善。

5.7 目标代码生成：安排具体指令

目标代码生成依据目标机的指令、寄存器与存储规则，把中间代码变成可进一步汇编或执行的代码。

为避免课件第 24 页 MOV、ADD 的方向歧义，这里使用明确约定的教学指令：LD R,A 表示把 A 的值装入 R，ST A,R 表示把 R 写入 A，二元运算的结果保存在第一个寄存器参数中。

LD   R1,count
MULT R1,#10.0
LD   R2,first
ADD  R2,R1
ST   sum,R2

执行后 R1 保存 count*10.0，R2 保存 first+count*10.0，最后把 R2 写给 sum。跟踪寄存器内容能检查“是否存回了真正的最终结果”。这些是教学伪指令，不宣称属于某个真实处理器指令集。

6. 贯穿全程的表格管理与错误处理

6.1 表格不是最后才建立

编译时需要保存许多“以后还要用”的信息，因此课件把表格管理放在主流程旁边，服务于多个阶段。

表或结构 保存什么 典型操作
名字索引表 标识符的拼写 新增、查找、复用索引
常量表 常量的类型和值 解析、查找、去重
符号表 声明、类别、类型、作用域与地址属性 声明、查找、作用域进出
类型信息表 数组、记录、指针等类型结构 建立和比较类型描述
语法分析表 状态和输入对应的分析动作 构表、查表

“表”泛指有组织的数据结构，不要求一定是二维表格。哈希表、树、链表、数组都可承担管理功能。名字索引表只知道“拼写是什么”，符号表还要知道“在这里指哪个声明”，两者职责不能混为一谈。

6.2 错误处理既要定位，也要避免误导

错误处理包括发现错误、给出诊断、决定如何恢复以及控制是否继续生成结果。理想诊断需要说明位置和原因，而不是只打印“编译失败”。

词法：非法字符
语法：括号或语句结构不完整
语义：名字未声明、类型不兼容
后续实现：编译器内部错误、目标限制等

为了在一次编译中报告多处错误，分析器可以跳到分号或其他同步位置再继续。这不意味着出错的程序已经正确，也不意味着必须继续产出可执行文件。恢复应尽量抑制由一个根本错误引起的成串误报。

理解补充：源程序检查主要集中在前端，但“进入代码生成以后绝不可能出错”不是严格结论。目标指令限制、资源限制和编译器实现缺陷都可能导致后续失败；要区分源程序错误和实现系统错误。

7. 阶段、遍、前端与后端

7.1 阶段回答“做什么”，遍回答“扫几次”

阶段（phase）按逻辑功能划分，例如词法分析、语义分析。遍（pass）是把源程序或某种中间表示从头到尾扫描并加工一次。

一遍扫描可以完成多个阶段。语法分析器一边向词法分析器索取 Token，一边检查结构并执行语义动作，就能把多种工作组织在一次扫描过程中。一个阶段也可以有多遍，例如先收集声明，再检查使用，或反复做不同优化。

因此“六个阶段＝六遍”不成立。遍的对象也不必是原始字符：Token 序列、语法树和四元式都可以被遍历。

7.2 为什么分遍

课件提出分遍的理由。可从三个实际问题理解：

  1. 信息尚未齐全。先收集声明或函数信息，后续再处理引用，能减少临时推迟处理的复杂度。
  2. 结构便于维护。把不同任务分开，方便调试、替换算法和验证。
  3. 资源与质量权衡。少遍可能减少中间存储和扫描成本；多遍可能获得更多分析信息并支持更充分优化。早期内存受限的实现也会通过分遍处理问题。

课件没有给出所有编译器都应采用的固定遍数。本课程按逻辑阶段讲授，不能据此推断最终实现必须逐阶段保存一个中间文件。

7.3 前端与后端使移植更容易

前端（front end）处理主要与源语言相关的事情：词法、语法、语义分析、中间表示生成，以及适合放在这一侧的目标机无关优化。

后端（back end）处理主要与目标机相关的事情：具体指令选择、寄存器与存储安排、目标相关优化、代码输出等。

可以把中间表示想成双方约定的接口：前端承诺“把源程序解释成这样的操作”，后端承诺“把这些操作实现到目标机上”。

C 前端 ──┐                 ┌── 目标机 A 后端
         ├── 共同的 IR ────┤
Pascal前端┘                 └── 目标机 B 后端

这样支持新的源语言或新的目标机时，可以复用已有部分。理解补充：实际边界未必完全纯净，类型大小、异常模型和调用约定等可能影响中间表示。课件的划分是一种设计原则，不要求前端对目标信息毫无了解。

8. 编译程序怎样实现和移植

8.1 直接用机器语言实现

编译器最终需要能在某台机器上运行，最直接的起点是用机器语言编写它。问题是代码难写、难调试、与机器高度绑定。课件把它作为实现路线的起点，不表示大型编译器通常应这样开发。

这里要区分两个问题：实现语言是编译器自身用什么写；被编译语言是编译器接受什么输入。用 C 写 Pascal 编译器完全可以；用某种语言写本语言的编译器也不矛盾。

8.2 自展法：从可实现的小子集滚成完整语言

自展法，也称雪球法先选取源语言 L 的小子集 L0，逐步扩展：

L0 ⊆ L1 ⊆ L2 ⊆ … ⊆ L

首先用已有手段实现 L0 的编译器；再用 L0 编写接受 L1 的编译器，把该源码交给已能运行的 L0 编译器，得到新的可执行编译器。继续用已经支持的 Li 编写接受更大子集的编译器，最终覆盖 L。

关键是“写第 i+1 步实现源码时，只使用当前已经能编译的功能”。如果源码用了尚未支持的特性，已有编译器就无法处理，雪球滚不起来。

理解补充：自举（bootstrapping）泛指借助已有实现建立新的实现。语言逐步自展可以成为自举路线之一；“编译器用本语言写”与“从子集不断扩展”分别描述实现语言和构建过程，不应当作同一个定义。

8.3 移植：在哪台机器运行，与给哪台机器生成代码

假设已有 A 机器上运行的 L 编译器 CCA，其实现源码 SA 也用 L 写成，现在要支持指令集不同的 B。

必须同时记录两项属性：宿主机是编译器运行的机器；目标机是输出程序运行的机器。例如“在 A 上运行、为 B 生成代码”就是交叉编译器，不能因为名称含 B 就以为它已能在 B 上运行。

课件列出三条移植途径：

途径 基本思路 需要解决的事情
目标代码转换 把 A 的目标表示转换为 B 的表示 指令、数据表示与运行环境差异
交叉编译 在 A 上建立能输出 B 代码的编译器 改造 B 后端，再生成并部署 B 程序
虚拟机移植 程序输出统一的虚拟机表示 在 B 上实现对应虚拟机与运行支持

交叉编译路线的详细过程：

  1. 修改 SA 的代码生成部分，得到源码 SB。SB 要生成 B 代码，但它此时仍是 L 源码。
  2. 用 CCA 编译 SB，得到一个在 A 上运行、输出 B 代码的可执行编译器。
  3. 把普通 L 程序交给它，即可在 A 上产生给 B 使用的程序。
  4. 若还需要在 B 上运行这个编译器，可再用交叉编译器编译 SB，生成 B 版本；同时准备其依赖的库与运行支持。

第 4 步是帮助区分“支持 B 为目标”与“编译器自身落地 B”的理解补充。课件第 29 页部分文字使用 SA、SB、S 时较简略，这里按宿主/目标关系展开，避免把源码直接误称为 B 可执行程序。

8.4 转换法与自动生成工具

转换法已经在 4.5 解释：先把新语言映射到已有语言，复用其实现。课件也称其为预处理法；这里的含义是语言转换，不应与 C 的宏预处理完全等同。

编译器生成工具从形式化规则生成部分分析器。课件列出 Flex、Yacc、LLGen、Bison：词法工具依据单词规则生成扫描程序，语法工具依据文法生成分析器框架。

工具减少重复编码，但需要人给出正确规则、语义动作、错误策略及其他阶段的实现。生成语法分析器不等于已经得到完整编译器；语义、运行时组织、优化和目标代码等仍需设计。

8.5 大模型调研怎样做才有依据

课件列出多个模型，并要求调研其生成各阶段程序的现状、优势和不足。该要求是一个调研主题，课件没有给出可信的统一测试成绩，因此本资料不把任何产品写成已经验证的最佳选择。

可以选同一组任务进行可重复比较：生成一个词法分析器、为指定文法构表、处理作用域、翻译一个表达式，再用正确输入、错误输入和边界案例核对。记录具体版本、提示、输出、错误类型和人工修正量。

优势可能是快速产生骨架或解释算法；需要验证的风险包括编造分析表、混淆语义约定、遗漏空产生式以及生成不能运行的代码。这些是检查维度，不是对课件所列某一产品当前能力的结论。要得到产品间的结论，仍需当时版本与实际实验数据。

8.6 开发前要确定哪些事

课件的开发要求可以转成如下检查表：

问题 不确定时会导致什么
源语言的语法、类型、作用域等规则是什么 接受错误程序或拒绝正确程序
目标指令、地址模型与运行支持是什么 生成无法执行或含义错误的代码
编译速度、诊断和优化要求是什么 设计成本与实际需求不相称
如何分遍、采用何种中间表示 信息传递不完整、阶段耦合过强
表结构与算法如何选择 查找慢、状态管理困难、实现难维护

“具体设计”不是先急着写代码，而是先把约定说清楚，再选择能够满足约定的数据结构和算法。

9. 怎样学习和使用编译技术

9.1 从语言使用走向语言理解

学会写表达式与函数，只说明会使用一门语言。实现编译器还要解释为什么类型需要转换、同名变量如何区别、递归为何不能共用一份局部空间等。后续章节会把这些规则落到具体结构和操作上。

课程同时训练抽象与形式化：抽象是保留解决问题所需的特征，例如把源文件看成字符流；形式化是用精确符号规定规则，例如用正则表达式描述单词、用文法描述嵌套结构。形式化减少“我觉得应该如此”的歧义，使算法能被验证和自动执行。

9.2 元级程序设计与系统设计能力

元级程序设计以程序为处理对象，例如分析、转换、生成和检查程序。编译器、静态检查器、代码生成器都体现这种思想。

编译器通常包含多个模块和复杂数据结构。学习如何规定接口、传递属性、管理状态、恢复错误、核对正确性，对大型软件设计有直接训练作用。只背概念而不手工跟踪例子，很难理解这些模块为什么必须这样配合。

9.3 应用不局限于编程语言

课件及备注列出查询优化、图像与游戏计算、机器学习计算、嵌入式和硬件描述语言、程序安全、调试器及系统开发等方向。

可以抓住它们共同的工作方式：先读取某种描述，建立结构与含义，再分析、变换或生成执行方案。数据库查询可以先分析查询结构再优化执行计划；配置文件和公式系统需要识别与解析；张量计算可以通过中间表示安排执行与优化。

这些应用复用的是方法，不意味着一个语法分析算法就能自动完成全部业务。课件关于自主创新与国产编译器的内容也可由此理解：语言工具链直接影响程序开发、性能和平台适配，需要长期积累正确性和工程能力。

9.4 课件所载课程安排

课件列教材为刘磊《编译原理及实现技术》第 3 版，理论课 48 学时、1—12 周；超星 MOOC 内部构成为作业 40%、签到 20%、视频 40%，该部分占总成绩 30%，期末考试占 70%。若两部分都用百分制，课件方案对应 总评=0.3×平时分+0.7×期末分。

这些是课件记载，并未核实本学期是否有调整。涉及提交时间或实际评分，应依据教师最新通知。内容按第 1—9 章排列，存储管理在授课中安排到优化后讲，故学习资料编号与部分课件封面编号不必一致。

10. 综合应用：从一句赋值核对各阶段的输入和输出

同一句程序经过六个逻辑阶段

sum、first、count为real；编译输入sum:=first+count*10。2.0与3.0仅用于执行核对。

完整轨迹（适合打印与连续核对）
阶段当前对象所用规则具体结果
词法源码字符按单词模式分离id(sum)、:=、id(first)、+、id(count)、*、int(10)
语法Token序列乘法高于加法sum := first + (count*10)
语义结构和声明整数允许提升realcount与10.0参与实数乘法，结果可赋给sum
IR带类型的结构显式转换与临时结果FLOAT 10→t1；MULTF count,t1→t2；ADDF first,t2→t3；ASSIG t3→sum
优化四元式已知常量转换提前计算用10.0替t1，运行保留乘法、加法、赋值
目标优化IR按教学LD/ST方向生成运行first=2、count=3时，写sum=32；编译时没有提前给sum赋值

初学时容易把词法、语法和语义都说成“查错”。这样背得出阶段名字，却无法解释同一程序为什么要交给几个模块处理。下面用同一输入把各阶段接起来；每一行的输出正好是下一行所需的信息。

前提：采用课件的 Pascal 风格语法，sum、first、count 都声明为 real；整数常量可以提升为 real。语句是 sum:=first+count*10。first=2.0、count=3.0 只用于后来核对执行结果，编译不需要预先知道这两个运行值。

子问题 处理对象和规则 具体输出 为什么下一步需要它
字符如何分词 匹配标识符、赋值符、常量和运算符 id(sum)、:=、id(first)、+、id(count)、*、int(10) 语法不再逐个区分字符
按什么结构计算 文法规定乘法优先 赋值树右部为 first+(count*10) 语义知道各操作的左右对象
用哪些类型 查三项声明，按 int→real 提升 乘法两侧都是 real，结果可赋 sum IR 可以选择实数运算与转换
如何拆成小操作 每条四元式保存一项结果 FLOAT 10→t1；MULTF count,t1→t2；ADDF first,t2→t3；ASSIG t3→sum 后续可检查哪条重复或已知
哪项可以提前计算 转换输入是已知常数 用 10.0 替代 t1，保留其余三条 运行时少一次已知转换
如何执行 按 LD/ST 方向和实数指令映射 取 count，乘 10.0，再加 first，写 sum 结果真实写到目标对象

这里原对象的值只在执行 ASSIG/ST 时改变；生成四元式不是提前运行整个源程序。代入运行值后 sum=32.0。若结构误排成 (first+count)*10，得到 50.0，说明翻译已经改变含义；若最后把乘法寄存器写回 sum，得到 30.0，说明后端存错结果。

10.1 把宿主、源语言、目标机分别放回移植流程

移植题常把“产生 B 机器代码”误读成“编译器自身能在 B 上运行”。这三个字段必须分别说明：接受哪种源码、程序在哪里运行、输出给谁执行。

步骤 现有对象 操作 得到的对象
1 在 A 运行、输出 A 代码的 L 编译器 CAA 用 L 修改其后端，源码记为 SAB 接受 L、准备输出 B 的编译器源码
2 CAA 和 SAB 在 A 上编译 SAB 在 A 运行、输出 B 代码的交叉编译器 CAB
3 CAB 和 SAB 仍在 A 上编译这份编译器源码 可在 B 运行、输出 B 代码的 CBB
4 CBB 及 B 的运行依赖 把产物交到 B 上运行 B 本地的 L 语言编译系统

第三步实际输出的编译器程序才改变宿主；第二步改变的是所生成程序的目标。流程是教学推导，没有在 A/B 两台实际机器上构建。是否还需运行库和链接支持，必须由具体平台确定。

  → 子集自展、转换、工具生成、交叉编译与虚拟机移植

11.2 自检问题与参考解释

1. 编译器和普通程序有什么区别？ 编译器仍是普通意义上的程序，但其主要处理对象也是程序；需要理解输入语言并保持其规定行为。

2. .obj 一定可以直接运行吗？ 不一定。它通常还需要链接；具体产物必须结合工具链和文件格式判断。

3. 解释器内部有字节码，就不算解释吗？ 仍可能算。内部表示与执行方式是两个问题，解释器可解释树或字节码。

4. a+*b 与未声明的 a 分别是什么问题？ 前者是结构问题，属于语法检查；后者是名字与声明的关系问题，属于语义检查。

5. 词法分析知道所有同名 x 都是同一个变量吗？ 不知道。词法可记录拼写；具体绑定依赖声明和作用域。

6. 为什么例子中 10 要转成 10.0？ 为满足教学语言对实数运算的类型要求。优化又可在编译时完成这个已知转换。

7. 六阶段为什么不等于六遍？ 前者划分功能，后者计扫描次数。一遍可执行多种功能，一个功能也可多次扫描。

8. 中间代码与优化都是不可缺少的吗？ 不是。课件明确允许直接生成目标代码，也可不进行优化；但结构和语义仍须被正确处理。

9. 在 A 上运行、输出 B 代码的编译器能直接放到 B 上运行吗？ 不能据此判断。它的宿主仍是 A，需要为自身生成 B 版本并满足 B 的运行依赖。

10. 用 L0 写接受 L1 的编译器矛盾吗？ 不矛盾。实现语言可以是小子集，输入语言可以是更大语言；前提是实现源码只使用已有工具能处理的功能。

11. 自动生成分析器是否等于自动生成整个编译器？ 不等于。输入规则及语义、运行时、后端等仍须完成。

12. 能否把 (a+b)+c 随意改成 a+(b+c)？ 必须检查源语言语义。理想实数成立不代表浮点运算或有溢出的整数运算必然保持行为。

12. 自测与答案：能否解释整个翻译流程

先独立回答，再对照理由。以下为本次自拟题，原期末题一.1在第 1 题中改写整合，不代表教师标准答案。

题号 学习任务 检查能力
1 解释与编译最根本的区别如何描述？解释器先建 AST 会改变判断吗？ 区分产物与执行方式
2 a+*b、使用未声明的 a、合法程序运行时输入使除数为零分别在哪处理？ 区分错误对象与已知信息
3 三个前端与四个后端共享一套 IR，要维护多少个主要模块？与每一对单独实现有何差别？ 理解前后端复用的条件
4 CAB 在 A 上编译自己的源码后得到什么？为什么不能直接把 CAB 的 A 可执行文件复制到 B？ 独立推导移植步骤

12.1 答案与理由

  1. 编译的外部过程把程序翻译成目标程序，执行目标程序才得到计算结果；解释由解释系统执行输入程序的含义并得到结果。先建立 AST 是内部处理安排，并不强制改变解释执行的性质。期末题采用课件的“是否先产生目标程序”表述；回答时可补一句讨论的是该层的执行流程。
  2. a+*b 是结构不合法，语法阶段可发现；未声明是绑定问题，语义阶段可发现；依赖未知运行输入的除零通常要运行时判断。若分母可在编译时证明为零，可以提前诊断，这不是与动态性质矛盾。
  3. 共享接口成立时是 3+4=7 个主要模块，单独实现每个组合是 3×4=12 套完整翻译器。7 不含公共 IR 的设计维护，也不表示总工作量严格按这个比例降低。
  4. CAB 接受 L 源码、输出 B 代码，因此编译 SAB 得 B 版本 CBB。CAB 自身是 A 指令编成的可执行文件；它输出哪种代码不能改变自己的指令集。

13. 排错与复习：先找混淆了哪一层

现象或疑问 可能原因 怎样核对 正确理解
