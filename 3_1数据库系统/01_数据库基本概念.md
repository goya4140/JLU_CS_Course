## 1. 【课程总结PPT重点知识点】从学校业务理解数据库、DBMS 与数据库系统

<a id="ch01-s003"></a>

### 1.1 学校需要记住哪些事实

学校要登记学生、开设课程，还要记住“谁选了哪门课”。例如，小林选了数据库课，成绩为 80。姓名可能重名，学校因此给每位学生分配学号，给每门课程分配课程号。

下面三张表只用于讲解。一行表示一条事实；列名说明这一格记的是什么。`SID`是学生编号，`CID`是课程编号，S1、C1 只是示例编号。

学生表 `student`：

| 学号 SID | 姓名 name | 所在系 dept |
| --- | --- | --- |
| S1 | 小林 | 计算机 |
| S2 | 小周 | 数学 |

课程表 `course`：

| 课程号 CID | 课程名 title |
| --- | --- |
| C1 | 数据库 |
| C2 | 程序设计 |

选课表 `takes`：

| 学号 SID | 课程号 CID | 成绩 score |
| --- | --- | --- |
| S1 | C1 | 80 |
| S1 | C2 | 90 |
| S2 | C1 | 70 |

第二张表中的 C1 说明“C1 是数据库课”；第三张表的第一行说明“S1 选了 C1，成绩 80”。利用编号匹配两张表，就能知道“小林的数据库成绩是 80”。不必在每条选课记录里重复写完整姓名和课程介绍。

<a id="ch01-s004"></a>

### 1.2 三个容易混淆的名称

**数据库**是按一定结构组织、能够长期保存的一组相关数据。这里的三张表及其记录可以组成一个小型学校数据库。“相关”表示它们能用学号、课程号联系起来；“长期保存”表示关掉查询窗口后，数据仍应保留。

**数据库管理系统**简称 **DBMS**，英文为 Database Management System，是管理数据库的软件。你提出“查小林成绩”的要求，DBMS 负责找到数据、组合结果、检查操作权限。数据库是被管理的数据，DBMS 是执行管理的软件。

**数据库系统**范围更大：包括数据库、DBMS、教务应用、使用人员和运行设备。例如学生在网页点击选课，网页应用向 DBMS 发出请求，DBMS 把记录写进数据库；服务器、网络和维护人员也属于整个系统的运行环境。

| 你指的对象 | 在本例中是什么 | 是否等于数据本身 |
| --- | --- | --- |
| 数据库 | 学生、课程、选课等记录及其结构 | 是管理对象 |
| DBMS | 负责查找、修改和保护这些记录的软件 | 否 |
| 数据库系统 | 数据、软件、教务网页、人员、设备等整体 | 包含数据 |

<a id="ch01-s005"></a>

### 1.3 DBMS 要解决哪些问题

“查得到”只是第一步。还要查得方便、处理得高效、阻止不合法的记录、限制谁能改数据，并在多人同时操作或机器故障时保持正确。下节分别用小场景说明这些目标。

<a id="ch01-s006"></a>

## 2. 【课程总结PPT重点知识点】普通文件管理为什么会遇到困难

这里的“文件系统”指用操作系统中的文件保存数据，再由各业务程序自行读写。例如教务处和财务处各维护一份学生表。文件当然能存数据；问题是规则和协调工作常分散在很多程序里。

<a id="ch01-s007"></a>

### 2.1 冗余与不一致：同一个地址有两份

假设教务文件记小林地址为“松林路”，财务文件也记“松林路”。同一个事实保存两次叫**数据冗余**。小林搬家后，教务处改成“校园路”，财务处没改，两份地址相互矛盾，叫**数据不一致**。

| 时刻 | 教务文件中的地址 | 财务文件中的地址 |
| --- | --- | --- |
| 修改前 | 松林路 | 松林路 |
| 只改一处后 | 校园路 | 松林路 |

数据库可以让两个部门查询同一份地址，从源头减少重复；若出于性能需要复制数据，还必须有维护一致性的办法。DBMS 不会自动识别所有现实中的重复事实，设计者仍要设计合理结构。

<a id="ch01-s008"></a>

### 2.2 访问困难与数据孤立：同一个学号写法不同

假设教务文件写 `S1,小林`，财务文件写 `学生编号=S1;欠费=0`。两者格式不同，新需求“列出已选数据库课且没有欠费的人”就要专门读两种格式再匹配。

**数据访问困难**指每个新问题都可能需要重新编写处理程序。**数据孤立**指数据分散在不同文件、不同格式中，难以统一查询；此处的“孤立”不是后文事务的“隔离性”。数据库用共同的结构描述和查询接口，降低组合数据的难度。

<a id="ch01-s009"></a>

### 2.3 完整性：不能选不存在的课程

若课程表只有 C1、C2，却出现选课 `(S1,C9,80)`，这条记录找不到对应课程。**完整性**指数据满足已声明的有效性规则，并不是“每一格都必须有值”。

**约束**就是交给数据库检查的规则，例如：

- 学号不能重复；
- 选课中的课程号必须在课程表中存在；
- 本教学业务规定成绩只能在 0—100 之间。

第一条检查身份唯一性，第二条检查表间对应关系，第三条检查取值范围。约束类型在第 02、03 章进一步解释。数据库只能执行你正确声明的规则，不能替你猜现实业务。

<a id="ch01-s010"></a>

### 2.4 原子性：转账的两步要一起完成

新场景是银行转账：甲有 500 元，乙有 300 元，甲向乙转 200 元。不考虑手续费，两人的总额应保持 800 元。

| 状态 | 甲余额 | 乙余额 | 合计 |
| --- | --- | --- | --- |
| 开始 | 500 | 300 | 800 |
| 只完成扣款 | 300 | 300 | 600 |
| 两步都完成 | 300 | 500 | 800 |

**事务**是数据库作为一个整体处理的一组业务操作，例如扣甲款、给乙入账。**原子性**要求这个整体全部成功，或者整体撤销；这里的“原子”意为不可拆开地完成，不是物理学中的原子。**回滚**就是撤销这个事务尚未完成的修改。详细恢复方法见第 06 章。

<a id="ch01-s011"></a>

### 2.5 并发：最后一个名额不能给两个人

假设一门课只剩 1 个名额。小林和小周同时申请，两人的程序都先看到“剩余 1”，然后各自认为能选课，最终可能录取两人。

**并发**表示多个任务在一段时间内交错推进，不要求硬件在同一瞬间执行两条指令。**并发控制**决定操作能怎样交错，避免破坏“人数不超过容量”等规则。第 06 章判断交错是否正确，第 07 章讲如何控制。

<a id="ch01-s012"></a>

### 2.6 安全：能查成绩不意味着能改成绩

学生可看自己的成绩，任课教师可录入本课程成绩，管理员可维护结构。**权限**规定某个用户对某个对象可以做什么；**角色**把一组权限起一个名称，如“任课教师”。把相关权限授给角色，再把角色分配给人员，可以减少重复授权。第 03 章讲授权语句。

<a id="ch01-s013"></a>

## 3. 【课程总结PPT重点知识点】数据抽象的三个层次

<a id="ch01-s014"></a>

### 3.1 为什么要分层

教务员只想知道学生成绩，不想先学数据在硬盘哪里。开发人员需要知道表和字段，却不一定需要知道每条记录占用哪块磁盘。**抽象**就是保留当前任务所需的细节，隐藏暂时无关的细节。

| 层次 | 回答的问题 | 学校例子 |
| --- | --- | --- |
| 物理层 | 数据实际怎样存放 | 学生记录放在哪个文件、哪个数据页 |
| 逻辑层 | 保存什么信息及其联系 | 学生表有学号、姓名、系；选课记录用学号对应学生 |
| 视图层 | 某类用户看到哪一部分 | 学生只看自己的选课与成绩 |

**数据页**是 DBMS 读写存储时使用的一块数据区域，通常容纳多条记录；本章无需记页大小。**视图**在这里指用户所看到的数据表达；SQL 中也有通过查询定义的具体“视图”对象，见第 03 章。

<a id="ch01-s015"></a>

### 3.2 物理数据独立性

假设查学号 S1 原来要逐行翻找，后来为学号增加一个索引。表仍叫 `student`，列仍是学号、姓名、系，教务员的查询不必因此改写。**物理数据独立性**指存储方法变化尽量不影响逻辑结构和使用它的程序。

<a id="ch01-s016"></a>

### 3.3 逻辑数据独立性

假设学生信息增加“邮箱”列，原先只显示姓名和成绩的页面应尽量继续工作。**逻辑数据独立性**指逻辑结构发生适当变化时，能通过视图或接口调整减少对既有应用的影响。

这不是承诺任意结构变化都无需改程序。若直接删除应用使用的姓名列，应用通常仍需调整。逻辑独立性往往比物理独立性难实现。

<a id="ch01-s017"></a>

## 4. 【课程总结PPT重点知识点】模式与实例

<a id="ch01-s018"></a>

### 4.1 先看空表和有数据的表

建表时先约定“有学号、姓名、系三列，学号不能重复”，此时可能还没有任何学生记录。这份结构和规则叫**模式**，英文 `schema`。

填入 S1、小林、计算机等记录后，某一时刻表中实际存在的行叫这个时刻的**实例**，英文 `instance`。这里不是举例时说的“一个例子”，也不是某些产品中指运行服务的“数据库实例”。

`student(SID,name,dept)`是一种简写：`student`为表名；括号内按顺序列出列名；逗号分隔列。它描述结构，并未说明现在有多少学生。

<a id="ch01-s019"></a>

### 4.2 同一个模式可以有不同实例

| 时刻 | 当前学生记录 | 模式是否变化 |
| --- | --- | --- |
| 入学登记前 | 空表 | 否 |
| 登记两人后 | S1 小林；S2 小周 | 否 |
| 增加 S3 后 | 原两人加 S3 小陈 | 否 |
| 增加邮箱列后 | 所有行可多记邮箱 | 是 |

“插入学生”改变实例；“增加列”改变模式。第 02 章会把表结构称为“关系模式”。

<a id="ch01-s020"></a>

## 5. 【课程总结PPT重点知识点】数据模型：用什么方式描述数据

**数据模型**是一套描述数据结构、联系、操作和规则的概念工具。它像一种表达方式：你要先决定用表、图形或层次结构表达业务，再决定实际记录什么。

<a id="ch01-s021"></a>

### 5.1 关系模型

第 1 节的三张表就是关系模型的直观入口。正式术语中，列叫**属性**，一行叫**元组**，整张符合模型要求的表叫**关系**。例如学号是一项属性，`(S1,小林,计算机)`是一个元组。正式的关系具有集合性质，整行重复、顺序等约定见第 02 章。

<a id="ch01-s022"></a>

### 5.2 实体—联系模型

设计者先画“学生”“课程”，再画“学生选课程”的联系。**实体**指业务中可区分的对象，例如小林这一名学生；**属性**描述对象，例如姓名；**联系**描述对象间的关联，例如选课。

ER 是 Entity–Relationship 的缩写，意思就是实体—联系。它通常用于先谈业务，再转成表，而不是直接替代 SQL 查询。完整方法见第 04 章。

<a id="ch01-s023"></a>

### 5.3 对象关系模型

假设学校要存教学楼的位置，位置可能包含经度、纬度两个部分。**复杂类型**允许把相关部分组织成一个有结构的值；**对象关系模型**是在关系模型上增加这类能力的模型。某些系统还允许类型继承，即较具体的类型沿用较一般类型的属性。具体支持方式取决于数据库产品，本章理解扩展目的即可。

<a id="ch01-s024"></a>

### 5.4 半结构化数据与 XML

假设不同学生的资料卡不一定有同样的附加项：有的人有社团列表，有的人有交流经历。**半结构化数据**允许记录具有不同字段或层次，不要求每条记录都严格用相同的列排列。

XML 是一种使用标签表示数据层次的文本格式。下面的标签 `<student>`表示学生内容的开始，`</student>`表示结束；`<name>`里面保存姓名。这个独立示例只展示格式，不是本章学生表的替代数据集。

```xml
<student>
  <id>S1</id>
  <name>小林</name>
</student>
```

“半结构化”不等于“没有任何结构”：标签名称和嵌套关系仍提供结构信息。

<a id="ch01-s025"></a>

## 6. 【课程总结PPT重点知识点】数据库语言与数据字典

<a id="ch01-s026"></a>

### 6.1 DDL：先约定表的结构

**数据定义语言**简称 DDL，Data Definition Language，用于定义表、列和规则。以下 SQL 建一个用于演示的新空表：

```sql
CREATE TABLE student (
    SID CHAR(2) PRIMARY KEY,
    name VARCHAR(30) NOT NULL,
    dept VARCHAR(20)
);
```

逐项读：

- `CREATE TABLE`意思是创建表，后面的 `student`是新表名。
- 外层括号包含列定义，逗号分隔三列，分号结束语句。
- `SID`是学号；`CHAR(2)`是长度为 2 的固定长度文字类型。
- `PRIMARY KEY`把学号指定为主码：用来区分学生，不能重复、不能空。
- `name`是姓名；`VARCHAR(30)`表示最多 30 个字符的可变长度文字。
- `NOT NULL`表示这一列不允许缺值；`dept`是系名，没有在此例声明必填。

这里只演示结构。第 03 章会解释类型长度、空值及产品差异。执行后是零行、三列的表，并不会自动生成 S1。

<a id="ch01-s027"></a>

### 6.2 DML：使用和改变记录

**数据操纵语言**简称 DML，Data Manipulation Language，用于查询、插入记录、修改记录、删除记录。这里的“删除记录”是数据库操作概念，不是在本电脑上删除 Markdown 文件。

想找计算机系学生，先用普通语言说“从学生表里，留下系为计算机的行，显示学号和姓名”，再写：

```sql
SELECT SID, name
FROM student
WHERE dept = '计算机';
```

`SELECT`后写要显示的列；`FROM`后写来源表；`WHERE`后写筛选条件；`=`表示相等；单引号框住文字常量。若使用第 1 节的数据，结果只有 `S1,小林`。查询不改变原表。

<a id="ch01-s028"></a>

### 6.3 过程式与声明式

**过程式**表达既说明要什么，也交代怎样一步步取得。例如“从第一行开始检查系名，每符合一行就输出”。**声明式**表达主要说明想要的结果，例如上面的 SQL；DBMS 决定采用逐行扫描还是索引查找等实现方法。

声明式不是没有执行步骤，而是用户不必把这些步骤写进查询。

<a id="ch01-s029"></a>

### 6.4 数据字典与元数据

DBMS 需要记住“学生表有哪些列、谁有权读取、学号是什么类型”。**元数据**就是描述数据的数据；**数据字典**是 DBMS 保存这些结构、规则和管理信息的地方。

学生姓名“小林”是业务数据；“姓名列最多 30 个字符”是元数据。混淆两者会把“改列类型”误认为“改某个姓名”。

<a id="ch01-s030"></a>

## 7. 【课程总结PPT重点知识点】数据库设计的四个阶段

学校提出“一个学生可选多门课，一门课可有多个学生；每次选课记一个成绩”，设计者可以这样推进：

| 阶段 | 先做的事情 | 得到什么 |
| --- | --- | --- |
| 需求分析 | 询问是否允许重修、成绩是否可暂缺 | 明确业务规则 |
| 概念设计 | 找出学生、课程、选课联系 | ER 模型 |
| 逻辑设计 | 转成 student、course、takes 三张表 | 表结构与约束 |
| 物理设计 | 判断常查学号还是课程号，选择索引等 | 存储与访问方案 |

本教学数据假设同一个学生对同一门课最多一条选课记录，不考虑学期和重修。真实系统若允许重修，就要增加学期或选课流水号等信息。这是从业务规则推出结构的例子。

**规范化**是按数据依赖分析并调整表结构，以减少重复事实和修改困难的方法，见第 05 章。**信息缺失**则是设计后无法表达需要的事实，例如只保存学生姓名与课程名，却没有地方记录成绩。

<a id="ch01-s031"></a>

## 8. 【课程总结PPT重点知识点】一条查询怎样经过 DBMS

<a id="ch01-s032"></a>

### 8.1 查询处理器：理解问题并选择步骤

仍用“查计算机系学生”。**查询处理器**负责把 SQL 变成可执行步骤。

1. **解析**：检查语句结构，确认 `student`和 `dept`存在。
2. **翻译**：把文本表达转成内部能处理的操作，例如筛行、取列。
3. **优化**：比较能得到相同结果的执行方法，估算时间、读页次数等代价。
4. **执行**：按选好的步骤读取并返回 `S1,小林`。

这些步骤组成**执行计划**。计划可以不同，结果必须符合查询含义；“优化”不允许为了快而漏掉正确记录。

<a id="ch01-s033"></a>

### 8.2 存储管理器：把逻辑记录与存储衔接起来

**存储管理器**负责组织文件、读写页和管理相关资源。**缓冲区**是内存中临时保存数据页的区域，减少重复读取磁盘。内存比磁盘访问快，但断电后通常不能像持久存储那样保留内容。

课件把权限与完整性、事务、文件、缓冲区管理列在存储管理器相关组件中；不同软件的实际模块边界可以不同。这是一种原理划分，不是每款产品必须采用的组织图。

<a id="ch01-s034"></a>

### 8.3 事务管理：协调并发与故障恢复

**事务管理**负责前面介绍的整体提交、回滚和并发协调。**提交**表示事务成功结束，其结果应被数据库持久保留。**故障恢复**利用持久保存的信息，把故障后的状态恢复到符合事务规则的状态。

它既不决定学生选什么课程，也不替应用判断业务输入是否合理。第 06、07 章深入讲解。

<a id="ch01-s035"></a>

## 9. 【课程总结PPT重点知识点】用户与数据库管理员

| 人员 | 学校场景中的动作 | 为什么需要这种角色 |
| --- | --- | --- |
| 普通用户 | 学生在页面点选课 | 不必会写查询语言 |
| 应用程序员 | 开发选课页面和转账逻辑 | 把业务流程接到数据库 |
| 熟练用户 | 教务分析人员直接写 SQL | 临时分析不都做成固定页面 |
| 专业用户 | 开发地图、工程设计等特殊应用 | 处理特殊数据和操作 |
| DBA | 配置权限、备份、监测性能 | 维护整个数据库的运行 |

**DBA**是 Database Administrator，数据库管理员。**备份**是保存可用于恢复的数据副本；**恢复**是利用备份及其他记录重建需要的状态。备份存在不等于必然能恢复，管理员还需要验证恢复过程。

**工作负载**指系统实际承受的查询、写入及其频率；**性能监控**就是观察这些操作的耗时和资源消耗，找出慢的原因。DBA 也负责容量规划，即估计未来数据与资源需求。

## 10. 【课程PPT补充知识点】体系结构与发展概览

<a id="ch01-s037"></a>

### 10.1 计算任务可以放在哪里

这里不用额外业务数据，仍讨论选课系统怎样部署。

| 形式 | 用普通语言解释 | 学校例子 |
| --- | --- | --- |
| 集中式 | 主要数据库工作集中在一处系统 | 一台中心数据库服务器 |
| 客户机／服务器 | 请求方与提供服务方分工 | 学生设备发请求，服务器处理 |
| 并行 | 多个处理资源协作完成工作 | 多个处理器共同执行大查询 |
| 分布式 | 数据或处理分布在多处，并协调工作 | 不同校区管理节点相互协作 |

**服务器**是提供服务的程序或设备，**客户机**是发出服务请求的一方。并行强调协作使用计算资源；分布式强调跨多个位置或节点的协调，二者可以同时存在。

<a id="ch01-s038"></a>

### 10.2 为什么出现多种模型

早期**层次模型**把数据组织成树状的父子结构；**网状模型**允许更复杂的记录联系；关系模型用表表达事实，使应用更少依赖具体访问路径。之后，复杂类型、网络访问、大规模分析等需求推动更多扩展。本章只了解变化的动因，不要求记发展年份。

## 11. 常见误解及修正

| 容易说错的话 | 具体问题 | 正确理解 |
| --- | --- | --- |
| “数据库就是管理软件” | 把数据和管理工具混为一谈 | 区分数据库与 DBMS |
| “新增一个学生就是改模式” | 列和规则并未变 | 改的是实例 |
| “SQL 不写步骤，所以无需执行计划” | 软件仍要真正读取数据 | DBMS 生成执行计划 |
| “有 DBMS 就能保证所有业务都正确” | 错误规则或错误应用仍会出错 | 需要正确设计、约束和程序 |
| “数据库不允许任何重复数据” | 受控副本可能服务性能或恢复 | 重复要有用途与维护办法 |

## 12. 本单元模拟题

<a id="ch01-s041"></a>

### 【模拟题相关补充】题目：什么是数据库索引？

**原题**

> 什么是数据库索引？

**PPT 参考答案**

> 索引是一种数据结构，是数据库管理系统中一个排序的数据结构，以协助快速查询、更新数据库表中数据。

**校正后的规范答案**

数据库索引是 DBMS 为加快数据定位而维护的辅助数据结构。索引通常把**搜索码值**映射到相应记录或数据页的位置。常见索引结构包括有序索引、B+ 树和散列索引。索引通常能减少查询需要访问的数据页，但会占用额外空间，并增加插入、删除和更新的维护成本。

**完整解析**

1. “索引是一种数据结构”是正确的核心表述。
2. PPT 把索引概括为“排序的数据结构”不够严谨。B+ 树等有序索引会维护次序，但散列索引并不按键值排序。
3. 索引主要直接提高的是**查找效率**。它不保证更新更快，因为更新数据时可能还要同步修改索引。
4. 索引一般保存“搜索码 + 指针”，并非复制整张表。

例如，对 `student(ID, name, dept_name)` 的 `ID` 建立索引后，查询某个学号时可沿索引定位记录，不必扫描所有学生。

**易错点**

- 索引的搜索码不一定是候选码，允许出现重复值。
- 一张表可以有多个索引，但索引越多，写操作维护成本通常越高。
- 本题来自模拟题，但完整的索引与散列理论位于未纳入本次整理范围的第 11 章。


<a id="ch01-s042"></a>

### 12.1 用小名单理解索引题

仍使用本章学生表，教务员希望按学号找学生。**搜索码**是用于查找的列或列组合，这里的“码”不一定是唯一标识；如果按系查找，同一个系可对应多名学生。**指针**在这里指能定位记录的位置说明，不要求你先了解程序指针。

教学用索引内容可以画成：

| 搜索码值（学号） | 对应位置 |
| --- | --- |
| S1 | 学生表中小林的记录 |
| S2 | 学生表中小周的记录 |

找 S2 时，先在索引中找 S2，再按位置取回“小周、数学”。真实索引查找开销取决于结构和数据规模，两行表不一定比直接扫描更快。

原答案提到的 **B+ 树**是一种按键值组织、通常可通过少数层次导航到数据的树形索引；**散列索引**先用计算规则把搜索值映射到存储位置，不靠维持全体键值的大小次序。这说明“索引一定排序”不是通用定义。完整结构属于课程第 11 章，此处只解释答题需要的作用。

## 13. 自拟自测题与逐步答案

以下四题为教学自测，不是原模拟题。

<a id="ch01-s044"></a>

### 13.1 新增邮箱列，还是新增一位学生？

**背景与问题**：学校学生表已有学号、姓名、系。操作甲新增邮箱列；操作乙登记 S3 小陈。哪一个改变模式？

**分析**：模式规定列和规则，甲改变列集合，因此改模式。乙仍按原三列增加一行，只改实例。**答案**：甲改模式，乙改实例。

<a id="ch01-s045"></a>

### 13.2 同一地址出现矛盾是什么问题？

**背景与问题**：教务与财务各存一份地址，搬家后只改教务记录。指出原先和修改后各有什么问题。

**分析**：原先同一事实记两份，是冗余；只改一处后内容矛盾，是不一致。可把共同地址集中管理，或建立同步维护机制。**答案**：冗余导致修改时容易不一致。

<a id="ch01-s046"></a>

### 13.3 建索引后页面查询仍照常工作

**背景与问题**：学生表新增学号索引，表名和列未变，网页查询未改。这说明哪种独立性？

**分析**：变化的是查找和存储方法，逻辑结构未变。**答案**：物理数据独立性；不能据此声称任意删列都不会影响网页。

<a id="ch01-s047"></a>

### 13.4 数据库能自动纠正写错的收款人吗？

**背景与问题**：应用把本应给乙的款转给了丙，扣款、入账都成功提交，总额没变。是否证明 DBMS 的原子性失效？

**分析**：两步作为整体完成，原子性可以成立；收款人错误是应用业务错误。必须校验输入和授权，必要时执行有记录的纠正业务。**答案**：不能归因于原子性失效，数据库机制需要正确业务程序配合。
