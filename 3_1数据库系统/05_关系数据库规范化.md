# 第5单元 关系数据库规范化

<a id="ch05-s002"></a>
## 1. 从选课汇总表发现重复与异常

<a id="ch05-s003"></a>

### 1.1 背景、字段与业务规则

学校把选课登记在一张汇总表 `ENROLL(S,C,SName,CName,Grade)`。S 学号，C 课程号，SName 学生姓名，CName 课程名，Grade 成绩。一行是一名学生对一门课程的选课；每学生每课程最多一次，不考虑学期重修。教学数据：

| S | C | SName | CName | Grade |
| --- | --- | --- | --- | --- |
| S1 | C1 | 小林 | 数据库 | 80 |
| S1 | C2 | 小林 | 程序设计 | 90 |
| S2 | C1 | 小周 | 数据库 | 70 |
| S3 | C2 | 小陈 | 程序设计 | 60 |

业务保证：同一学号对应一个姓名，同一课程号对应一个课程名，同一学生课程组合对应一个成绩。姓名与课程名并不假定唯一。编号、姓名、成绩是三类不同事实，不能从样本恰好不同就推断姓名也能决定学号。

<a id="ch05-s004"></a>

### 1.2 三种异常分别是什么

**冗余**是同一事实重复保存：S1 叫小林写了两次，C1 叫数据库也写了两次。

| 问题 | 业务动作 | 一张汇总表的困难 |
| --- | --- | --- |
| 更新异常 | C1 改名为“数据库基础” | 两行都要改，漏一行便矛盾 |
| 插入异常 | 新学生 S4 小吴尚未选课 | 没有完整选课事实就难按此结构登记 |
| 删除异常 | 取消 S2 的唯一选课 | 删除选课时连小周姓名信息也没处保留 |

这里“异常”是结构造成的不便或风险，不一定是软件弹出错误。规范化要把学生身份、课程身份、选课事实分开存，且证明能正确拼回来。

<a id="ch05-s005"></a>

## 2. 1NF 与 2NF：先搭入门桥梁

汇总表已经暴露出重复，但“每格是否只存一个值”和“名称是否只依赖组合身份的一部分”是两种问题。先分别检查这两层要求，后面才能理解为什么满足 1NF 仍可能需要拆表。

<a id="ch05-s006"></a>

### 2.1 1NF 要求当前字段里存单个值

**第一范式**简称 1NF，NF 是 Normal Form，范式，即结构应满足的规则。1NF 要求属性值在当前模型中是原子的：每格保存一个值，不把一组值当成一个普通格。

若一行写 S1 的课程为“C1,C2”、成绩为“80,90”，就把两组事实塞进一格，不符合本教学关系模型的表达。第 1 节四行分别表达选课，符合 1NF；但它仍有冗余，所以 1NF 不是充分的好设计保证。

<a id="ch05-s007"></a>

### 2.2 暂时用识别记录的方式理解 2NF

学号 S 单独不能区分一次选课，因为 S1 有两门；课程号 C 单独也不能，因为 C1 有两人。两者一起 `(S,C)`才区分一行。

姓名只依赖 S，不需要整个 S、C；课程名只依赖 C。它们是“由组合身份的一部分就能确定”的事实。**第二范式** 2NF 的正式定义要用下一节的候选码与非主属性：在 1NF 基础上，每个非主属性都应完全依赖每个候选码，不存在对候选码真子集的部分依赖。

“每个”不能只检查已选主码；单属性候选码没有非空的更小组成部分，通常不存在这种部分依赖。课件核心是 3NF／BCNF，2NF 在此用于解释为什么这张汇总表首先需要拆开。

<a id="ch05-s008"></a>

## 3. 函数依赖与码


拆表不能只凭“某列重复了”。先要确认哪些值相同会必然让另一些值相同，例如同学号总是同姓名。函数依赖把这种业务保证写成箭头，再用它区分能识别整行的属性和只描述一部分事实的属性。

<a id="ch05-s009"></a>

### 3.1 从普通语言到箭头

学校保证“知道学号，就唯一知道该学生姓名”，记作：
```text
S → SName
C → CName
SC → Grade
```
`→`读“函数决定”。左边叫**决定因素**，右边是被决定的属性。`SC`是集合 `{S,C}`的简写，不是把两个编号相乘或拼接成某个字符串。函数依赖说的是“同样的左边值，不能有不同的右边值”，不是一个需要编程计算的数学函数。

正式写 `X→Y`：X、Y 是属性集合。对任意两行，只要 X 上每个值都相同，Y 上每个值就必须相同。检查同 S1 的两行，姓名都小林，符合；若其中一行写小陈，则违背 S→SName。两行 S 不同，姓名相同不违背该依赖。

本章 `F`表示给定的函数依赖集合，即一组业务规则；`R`表示待讨论表的属性集合。集合表示不考虑排列与重复；`∈`表示“是其中一个成员”，`⊆`表示“是子集”。

<a id="ch05-s010"></a>

### 3.2 子集、真子集、平凡与非平凡

**子集**指一个集合的全部成员都在另一集合内；集合自己也是自己的子集。**真子集**还要求不能相等，例如 {S} 是 {S,C} 的真子集。

`SC→S`是**平凡依赖**，因为右边已经在左边里面：知道学号课程组合当然知道学号。`S→SName`是**非平凡依赖**，右边不全在左边内。规范化主要检查这些增加了新信息的依赖。

<a id="ch05-s011"></a>

### 3.3 超码、候选码、主码、主属性

**超码**是一组能决定表中全部属性的列。SC 决定 Grade，再由 S、C 分别得到两个名称，因此决定全部五列，是超码；SC 加 SName 仍是超码，但名称多余。

**候选码**是没有多余属性的超码；“最小”是不能再去掉属性，不要求它在所有候选码里列数最少。选择一个候选码作**主码**。**主属性**是出现在至少一个候选码中的属性；其他是**非主属性**。

本例候选码只有 SC，所以 S、C 是主属性，两个名称和成绩是非主属性。稍后用闭包证明，不只凭“看起来像编号”。

<a id="ch05-s012"></a>

### 3.4 部分依赖、完全依赖与传递依赖

**部分依赖**：候选码的真子集已能决定某非主属性；本例 S→SName、C→CName。**完全依赖**：整个决定因素能决定，去掉任一必要组成部分后不能；本业务 SC→Grade 是完全依赖，S 与 C 单独都不足。

**传递依赖**直观上是经过中间属性才能决定。独立学生行政表 `STUDENT_DEPT(S,Dept,Office)`，Dept 为所属系、Office 为系办公室；业务规定每学生一个系、每系一个办公室，则 S→Dept、Dept→Office，因此 S→Office。办公室在每个同系学生行中重复。这张表可没有组合码上的部分依赖，仍可能需要按 3NF 继续拆。

<a id="ch05-s013"></a>

## 4. Armstrong 公理：怎样推出更多依赖


题目只给了少量业务规则，但判断码和范式需要知道它们还保证哪些结论。公理用于从已有规则推出新规则，每一步都要能说明依据；它不会替我们添加题目没给的业务事实。

<a id="ch05-s014"></a>

### 4.1 三条基础规则先用普通语言理解

希腊字母 `α`、`β`、`γ`读阿尔法、贝塔、伽马，在此都代表属性集合；并排 `αβ`表示并集，也就是把两组属性合在一起且不重复。

| 公理 | 写法 | 为什么成立 |
| --- | --- | --- |
| 自反律 | 若 β⊆α，则 α→β | 知道一组值当然知道其中一部分 |
| 增广律 | α→β 则 αγ→βγ | 两行原先的 α 相同可确定 β；再同时要求 γ 相同，结果仍确定 |
| 传递律 | α→β、β→γ 则 α→γ | 先由 α 定 β，再由 β 定 γ |

公理是无需额外业务假设即可使用的推理规则。它们是**可靠**的，即推出来的依赖不会超出前提允许；也是**完备**的，即所有被前提逻辑保证的函数依赖均能用它们推出。学习时重点是每一步能指出依据。

<a id="ch05-s015"></a>

### 4.2 合并、分解与伪传递

**合并律**：α→β 且 α→γ，则 α→βγ。证明：

1. 对 α→β，两边增加 α，得 α→αβ。
2. 对 α→γ，两边增加 β，得 αβ→βγ。
3. 传递，得 α→βγ。

**分解律**：α→βγ，则 α→β 与 α→γ。因为 βγ→β、βγ→γ 都由自反律得到，再用传递。

**伪传递律**：α→β、βγ→δ，则 αγ→δ。这里 δ 读德尔塔，也是属性集合。先增广得 αγ→βγ，再传递。它用来处理第二条依赖还需要额外信息 γ 的情况，而不是把这项额外信息丢掉。

在主例，由 S→SName 和 SC→S（自反），传递得 SC→SName；再合并 SC→Grade 等，可知 SC 决定全部列。

<a id="ch05-s016"></a>

## 5. 属性闭包与候选码


要判断学号课程组合能否识别整行，就要看看“仅知道这些列时，沿规则还能知道哪些列”。属性闭包把这个过程变成可以逐轮检查的步骤，比直接猜主码更可靠。

<a id="ch05-s017"></a>

### 5.1 闭包就是“凭手上信息最终能知道什么”

给定 F，`X⁺`读“X 的闭包”，表示从属性集 X 出发，按 F 能确定的所有属性。上标 `+`不是数值加一，是推理结果的标记。**算法**就是一套明确可重复执行的步骤。

计算方法：先把 X 放进已知集合；逐条看依赖，左边全部已知就把右边加入；反复检查，直到没有新属性。

<a id="ch05-s018"></a>

### 5.2 对主例逐轮计算

| 轮次 | 当前已知属性 | 可以使用的规则 |
| --- | --- | --- |
| 开始 | S、C | 已知组合 |
| 第一次扩展 | S、C、SName | S→SName |
| 第二次扩展 | S、C、SName、CName | C→CName |
| 第三次扩展 | 全部五列 | SC→Grade |
| 再检查 | 无新增 | 停止 |

所以 (SC)⁺=R，SC 是超码。S⁺={S,SName}，C⁺={C,CName}，都不完整，去掉任一列就不是超码，因此 SC 是候选码。

S、C 都未出现在 F 的任何右边，无法由别的属性推出，任何候选码必须包含它们；而 SC 已是候选码，它的任何更大集合不最小。因此候选码只有 SC。这个结论相对于已声明的 F，不来自样本里的巧合。

<a id="ch05-s019"></a>

### 5.3 找候选码不能找到一个就停止

候选码需要同时满足“闭包覆盖全部属性”和“删去任一组成属性后不再覆盖”。找到一组后，还要检查其他可能的组合，避免漏码。可以按以下步骤进行。

对于未出现在任何依赖右部的属性，没有规则能从其他属性补出它，因此在本章普通有限属性集与给定依赖模型中，每个候选码都要含它。右部出现过的属性则不意味着一定能省略，还要计算。

1. 找不在任何依赖右边的属性：它们必须包含在每个候选码中。
2. 从这些属性出发，补充可能需要的属性并算闭包。
3. 闭包完整时检查每个组成属性能否去掉。
4. 继续寻找不同组合；已有候选码的超集无须再作为候选码。

原因是闭包算法只能从依赖右部补入新属性；从未出现在右部的属性，若起点没有，就永远补不出来。即使允许空集决定常量，这个结论仍成立：由空集推出的常量属性也会出现在相应依赖的右部。对只有五个属性的模拟题可以枚举所有子集，大模式不能把小题穷举误当作总是高效的办法。

<a id="ch05-s020"></a>

## 6. F⁺ 与依赖蕴含


“X 能得到哪些属性”和“整组规则能推出哪些依赖”不是同一个问题。两者都叫闭包，但一个结果是属性集合，另一个结果是规则集合。分清输入与输出后，才不会把 X⁺与 F⁺当成相同对象。

`F⁺`是 F 的**依赖闭包**，即由 F 能推出的全部函数依赖；与 X⁺不同，一个是“规则的集合”，一个是“属性的集合”。

**蕴含**表示前提必然保证结论。判断 F 是否蕴含 X→Y，只需计算 X⁺，看 Y 是否全部包含在 X⁺中：
```text
F 蕴含 X→Y  ⇔  Y⊆X⁺
```
`⇔`表示“当且仅当”，左右两个条件相互等价。本例 SC⁺含 SName，因此 F 蕴含 SC→SName；S⁺不含 Grade，因此不能推出 S→Grade。

说“不能推出”不等于所有数据实例都会违反它；某些小样本可能偶然符合。设计依据要保证所有合法实例。

<a id="ch05-s021"></a>

## 7. 正则覆盖：把规则写得精简且等价


同一个业务保证可以重复写，也可以写成可由其他规则推出的形式。正则覆盖要把表达简化，同时保持原来的全部推理能力。每次删掉的不是“看起来多余的字”，而是已经证明能够被剩余规则替代的部分。

<a id="ch05-s022"></a>

### 7.1 覆盖不是少写一条就更好

**正则覆盖**记 `Fc`，是与 F 能推出相同规则、又去掉冗余表达的依赖集。`Fc⁺=F⁺`表示推理能力相同。“冗余”是某条或某个属性可由其他规则替代。

课件正则覆盖允许合并同左部依赖；很多“最小覆盖”算法习惯保持右部单属性。两种表示形式要按课程约定区分，不能只按条数判断对错。

<a id="ch05-s023"></a>

### 7.2 一个完整算例：逐项去掉多余部分

这是独立的三属性模式 R(A,B,C)，A、B、C 是列名代号；给定业务 F={A→BC，B→C，AB→C}，不假定这些列具体是学号。目标是简化规则而不改变结论。

先把 A→BC 拆为 A→B、A→C，便于检查：

| 步骤 | 当前规则 | 为什么能改 |
| --- | --- | --- |
| 初始拆开 | A→B；A→C；B→C；AB→C | 合并／分解等价 |
| 精简 AB→C 左边 | 将它换成 B→C | 即使不要求 A，B 已能决定 C，A 多余 |
| 去掉重复 | A→B；A→C；B→C | 同一条 B→C 不需写两遍 |
| 检查 A→C | 暂时移除后 A⁺仍含 A、B、C | A→B 再 B→C，所以该条冗余 |
| 最终 | A→B；B→C | 两条分别移除都会失去对应推理能力 |

这里的**左部多余属性**是去掉后依赖仍由当前集合保证；**右部多余属性**是从该规则右边去掉后，仍能用调整后的整个集合推出它。初始合并写法中，A→BC 的右侧 C 可由 A→B、B→C 补回。

检查右部时不能留下原规则再说“当然能推出”，那会循环自证。每次改变后用当前集合重新计算。最终 A⁺=ABC、B⁺=BC、C⁺=C，与原 F 相同，因此 Fc={A→B,B→C} 等价。

<a id="ch05-s024"></a>

## 8. BCNF：每个非平凡决定因素都应是超码


当某个非唯一编号只能决定一项名称，这个名称往往要在多条记录里重复。BCNF 针对这种由局部决定因素带来的重复，但判断与分解必须相对于依赖规则，不能只数某列重复几次。拆完还要分别证明能拼回、原规则能否局部检查。

<a id="ch05-s025"></a>

### 8.1 白话与正式条件

BCNF 是 Boyce–Codd Normal Form，博伊斯—科德范式。它要求一条非平凡函数依赖的左侧能确定整个关系，而不是只能确定一小部分、却让这个局部事实在很多行里重复。

正式条件：对 F⁺中每条 X→Y，如果 Y 不全包含在 X 内，X 就必须能决定 R 的全部属性。以 S→SName 为例，知道 S 只能得到姓名，不能知道这个学生选哪门课、成绩如何，因此 S 不是 ENROLL 的超码，这条非平凡依赖违反 BCNF。不要把“能确定右边”误当成“能确定整行”。

<a id="ch05-s026"></a>

### 8.2 按一条违反规则的依赖拆

若 X→Y 违反 BCNF，可以分成：
```text
R1 = X∪Y
R2 = R−(Y−X)
```
`∪`表示集合合并；`−`表示去掉集合中的成员；这里操作的是属性集合。先把决定因素与被决定属性放一起；剩下的表保留 X 用作拼回的对应列。

对 S→SName：

- R1(S,SName)，存学生姓名事实；
- R2(S,C,CName,Grade)，去掉姓名但保留 S。

再对 R2 的 C→CName 拆：

- COURSE(C,CName)；
- TAKES(S,C,Grade)。

<a id="ch05-s027"></a>

### 8.3 展示最终三张完整表

STUDENT：

| S | SName |
| --- | --- |
| S1 | 小林 |
| S2 | 小周 |
| S3 | 小陈 |

COURSE：

| C | CName |
| --- | --- |
| C1 | 数据库 |
| C2 | 程序设计 |

TAKES：

| S | C | Grade |
| --- | --- | --- |
| S1 | C1 | 80 |
| S1 | C2 | 90 |
| S2 | C1 | 70 |
| S3 | C2 | 60 |

STUDENT 的 S 是码，COURSE 的 C 是码，TAKES 的 SC 是码。在各自投影依赖下均满足 BCNF。规范化分解从原表投影得到这些记录；真实设计此后可以独立新增尚未选课的 S4 或无人选的 C3，这不是声称原表已含那些事实。

<a id="ch05-s028"></a>

### 8.4 分解算法与两个后续问题


投影依赖不只来自原规则中原样留下的条目。举一个课件式独立小例：R(A,B,C,D,E)，F={A→B，BC→D}，子表 R2(A,C,D,E) 虽然没有 B，却仍有 AC→D，因为 A 先得到 B，再与 C 一起得到 D。AC 不能得到 E，所以在 R2 内不是超码；R2 仍违反 BCNF。检查子表时要继承可推导的规则，不能因为原 F 没有完全落在 R2 的一条就宣告无依赖。

**分解**把原模式拆为若干子模式；每个子模式继承在其属性上成立的**投影依赖**，即 F⁺中左右都在该子模式内的依赖。不是机械保留原 F 中“看起来没跨表”的几条就够。

逐表寻找违反 BCNF 的依赖并拆，直到所有子表满足。每次上述二表拆法可以证明无损，但 BCNF 不保证全部原依赖都能在单表内检查；第 10、11 节分别证明这两项性质。

<a id="ch05-s029"></a>

## 9. 3NF：允许右边是主属性的特定情况


强行达到 BCNF 有时会把必须一起检查的属性拆开。3NF 放宽一类特定依赖，帮助在减少重复与保留约束检查能力之间作取舍。这不是允许任意冗余，而是用“左部是否超码、右部是否主属性”给出明确条件。

<a id="ch05-s030"></a>

### 9.1 正式条件逐项读

**第三范式** 3NF 的正式条件是在 F⁺中检查 X→A 这样的单属性右部依赖；只要符合下面三种情况之一就允许。这里 X 是决定因素，A 是一个被决定的属性，不是任意整组右部。

1. A 在 X 内，是平凡依赖；
2. X 是超码；
3. A 是主属性，即出现在某个候选码中。

这里右部用单属性 A，若原规则右边多列，先拆开检查。BCNF 只接受前两种，因此 BCNF 一定满足 3NF，反过来不一定。第 2 节 ENROLL 的非主名称由 S 或 C 局部确定，也不满足 3NF。

<a id="ch05-s031"></a>

### 9.2 一个 3NF 但非 BCNF 的完整例子

独立模式 R(A,B,C)，规则 F={AB→C，C→B}。A、B、C 是三列代号，不与上一节独立算例共用依赖。

| 起点 | 闭包 | 说明 |
| --- | --- | --- |
| A | A | 非超码 |
| B | B | 非超码 |
| C | BC | 非超码 |
| AB | ABC | 最小超码 |
| AC | ABC | 最小超码 |

候选码 AB、AC，三列都属于至少一个码，因此全是主属性。AB→C 左侧是码；C→B 左侧不是码，但 B 为主属性，符合 3NF；后者仍违反 BCNF。

合法教学数据可为 (a1,b1,c1)、(a2,b1,c1)：同 C 都为 b1，同 AB 对应单个 C，符合规则。样本不替代上面的闭包证明。

<a id="ch05-s032"></a>

### 9.3 3NF 综合法：围绕精简规则建表

**综合**表示把需要一起维护的属性组合成子模式。课程常用步骤：

1. 求正则／最小覆盖，确保依赖等价。
2. 每个 X→Y 建含 X∪Y 的子模式，同左部可合并。
3. 若没有任何子模式包含原模式的一个候选码，再加一个候选码模式。
4. 删除被别的子模式完全包含的冗余子模式。

主例 Fc={S→SName,C→CName,SC→Grade}得到与第 8 节相同三表。TAKES 已包含 SC，不需另加码表。

独立 R(A,B,C)，F={A→B}中，候选码 AC。只建 AB 会漏 C；因此建 AB、AC，A→B 可局部检查，且分解无损。合法数据 (a1,b1,c1)、(a1,b1,c2)投影并连接仍是原两行，说明保留 C 和关联列的重要性。

对第 9.2 节，AB→C 直接生成 ABC，C→B 生成 CB，后者被 ABC 包含，可以保留整个 ABC 作为 3NF 结果；为了强行达到 BCNF 而拆，会引出依赖保持问题。

<a id="ch05-s033"></a>

## 10. 无损连接：拆开再拼不会造假记录


表拆开后，不能只检查每张子表是否保存了原来的值；还要检查拼回时会不会把本来不相关的值错误配在一起。无损连接比较的是原合法关系与重建结果是否恰好相同，既不能少事实，也不能多假事实。

<a id="ch05-s034"></a>

### 10.1 “无损”不仅是没有丢原来的行

**无损连接分解**要求任一满足 F 的原关系，投影到子表后再自然连接，恰好得到原关系。投影是取指定列并按关系集合约定去重；自然连接按所有同名列匹配。见第 02 章。

**有损分解**常见问题是拼回时产生原来没有的组合，称**伪元组**。并非只看字面理解成行数减少。

<a id="ch05-s035"></a>

### 10.2 一个会多出两行的反例

独立 R(A,B,C)教学数据：

| A | B | C |
| --- | --- | --- |
| a1 | b1 | c1 |
| a2 | b1 | c2 |

拆 AB 与 BC，分别为 (a1,b1),(a2,b1)与(b1,c1),(b1,c2)。因为共同 B 都是 b1，拼回所有四种：

| A | B | C | 是否原有 |
| --- | --- | --- | --- |
| a1 | b1 | c1 | 是 |
| a1 | b1 | c2 | 否 |
| a2 | b1 | c1 | 否 |
| a2 | b1 | c2 | 是 |

如果没有 B→A 或 B→C 等保证对应唯一的规则，这个二表分解不能认定无损。

<a id="ch05-s036"></a>

### 10.3 二表判据与主例证明


为什么看交集？自然连接就是靠共同列配对。如果同一个共同值在两边都能对应多个彼此独立的剩余值，就可能把它们交叉组合成原表没有的行。共同列决定至少一侧全部属性，才限制住这种不受保证的配对。下面给出的是相对于函数依赖的二表判据，不是任意多表的万能公式。

当 R1∪R2=R 时，相对于函数依赖 F，二表分解无损当且仅当：
```text
(R1∩R2) → R1  或  (R1∩R2) → R2
```
`∩`是交集，即共同属性。箭头仍是函数决定；右边 R1 表示决定它全部属性。白话是“用共同列匹配时，至少一边不会在同一个匹配值下提供互相矛盾的多种身份事实”。

主例第一次交集 S，S→SName，因此 S 决定 STUDENT 全部列，无损。第二次交集 C，C→CName，因此 C 决定 COURSE 全部列，也无损。逐步的无损分解合起来仍能正确恢复 ENROLL 四条完整记录。

只能在“两个子模式覆盖原模式”等条件下直接用此判据；多表不能仅逐对试几个交集就声称证明完毕。

<a id="ch05-s037"></a>

### 10.4 多表检验中的 chase 是什么

二表判据不能直接用于任意多表分解。对多张表，需要观察给定依赖能否把连接中的对应关系限制到足以恢复原表。**Chase**常译“追赶法”，用规则不断合并必须相同的符号，检验多表连接会不会产生不受原规则保证的组合。这不是追踪程序执行。

以主例最终 STUDENT、COURSE、TAKES 为例，建立符号表。aS 等“a”符号代表该列的目标值；u、v、w 等代表暂未知的值，每个未知格起初不同。

| 子表行 | S | C | SName | CName | Grade |
| --- | --- | --- | --- | --- | --- |
| STUDENT | aS | u1 | aSN | u2 | u3 |
| COURSE | v1 | aC | v2 | aCN | v3 |
| TAKES | aS | aC | w1 | w2 | aG |

由 S→SName，第一行与第三行 S 相同，故第三行 w1 必须等于 aSN；由 C→CName，第二行与第三行 C 相同，第三行 w2 必须等于 aCN。于是 TAKES 行变成 aS、aC、aSN、aCN、aG，全为目标 a 符号，这表明按这些依赖该分解无损。

一般算法需对任意相同左部的行反复统一右部符号；出现全 a 行是这个函数依赖 chase 检验的成功条件。本例展示原理，二表题仍优先用第 10.3 节判据。

<a id="ch05-s038"></a>

## 11. 依赖保持：拆后规则能否分别检查


即使拆开再拼能得到原信息，以后各表独立插入的新记录仍可能违背原规则。依赖保持关心的是“只检查各表内部条件够不够”，和无损的“能不能还原原合法数据”是两个问题。

<a id="ch05-s039"></a>

### 11.1 把信息正确与规则好检查分开

**依赖保持**要求各子表上能检查的投影依赖合起来，仍能推出原 F。形式上，若 Fi 是第 i 个子表的投影依赖，应有：
```text
(F1∪F2∪…∪Fn)⁺ = F⁺
```
i、n 是编号与子表数量，省略号表示中间所有子表。白话是“只维护各表内部规则，也不会漏掉原有业务规则”。

主例 S→SName 在 STUDENT，C→CName 在 COURSE，SC→Grade 在 TAKES，原三条都能局部检查，因此保持依赖；第 10 节的无损证明不能替代这项证明。

<a id="ch05-s040"></a>

### 11.2 无损却不保持依赖的具体反例

对第 9.2 节 R(A,B,C)，按 C→B 拆成 CB 与 AC。交集 C 能决定 CB，所以无损；两表也满足 BCNF。但 AB→C 横跨，不能仅凭两个表分别合法来保证它。

子表可分别取：

| C | B |
| --- | --- |
| c1 | b1 |
| c2 | b1 |

| A | C |
| --- | --- |
| a1 | c1 |
| a1 | c2 |

CB 满足 C→B，AC 没有需要额外限制的非平凡投影依赖。拼回是 (a1,b1,c1)、(a1,b1,c2)，同 AB 对应两 C，违反 AB→C。这证明各表局部检查不足，因而不保持依赖。

这不推翻“无损”：无损说的是从一个**原本合法的原表**出发拆并拼能恢复；这里是独立维护子表时加入了不符合原整体规则的数据。

<a id="ch05-s041"></a>

## 12. 多值依赖与 4NF


有些重复不是“一个值决定另一个值”，而是两组独立的多值信息被展开成所有组合。此时每个学生确实可以有多种爱好、多种语言，不能硬写成学号决定单一爱好；需要多值依赖描述组合独立性。

<a id="ch05-s042"></a>

### 12.1 函数依赖不能概括所有独立重复

**独立业务**：学生的爱好与会用的语言彼此独立，希望记下任意组合。表 `SKILL(S,H,L)`，S 学号、H 爱好、L 语言。S1 有游泳、绘画两爱好，中文、英语两语言。

| S | H | L |
| --- | --- | --- |
| S1 | 游泳 | 中文 |
| S1 | 游泳 | 英语 |
| S1 | 绘画 | 中文 |
| S1 | 绘画 | 英语 |

S 不能函数决定单个 H，因为一个学生有多爱好。**多值依赖** `S↠H`表示，对给定 S，它的 H 集合与其余 L 的选择独立，需要能自由组合。`↠`是双箭头，不能按普通 S→H 理解。

同 S 的两行若为 (S1,游泳,中文)、(S1,绘画,英语)，独立性要求另外两种交叉组合也应存在。若业务是“用某语言参加某爱好”，两者不独立，就不能假设这种多值依赖。

<a id="ch05-s043"></a>

### 12.2 4NF 规则与拆分结果

**第四范式** 4NF 要求每个非平凡多值依赖的决定因素是超码。多值依赖 X↠Y 平凡的常见情况是 Y⊆X，或 X∪Y 已覆盖全部属性；此时没有额外独立部分需要表达。

SKILL 的 S 不是超码，却存在非平凡 S↠H，因此拆：

- STUDENT_HOBBY(S,H)：S1 游泳；S1 绘画。
- STUDENT_LANGUAGE(S,L)：S1 中文；S1 英语。

按 S 连接恢复原四种组合，无损，且不再为每种语言重复爱好。4NF 比 BCNF 还处理多值独立性，不能拿两者条件互换。

<a id="ch05-s044"></a>

## 13. 设计取舍与时间数据

<a id="ch05-s045"></a>

### 13.1 正确设计不等于拆得越多越好

拆表减少重复，也增加连接成本。**反规范化**是为明确性能目的有控制地保存一些重复信息；前提是知道要维护哪些一致性规则，不能把方便写一张大表当成充分理由。

键、外码、业务查询和更新频率都应一起考虑。范式保证某类结构性质，不保证索引最优、权限正确或所有业务语义都完整。

<a id="ch05-s046"></a>

### 13.2 有效时间与事务时间

**独立地址历史**：小林实际在 9 月 1 日搬到校园路，学校到 9 月 5 日才收到并录入信息。

- **有效时间**描述事实在现实中何时生效：9 月 1 日。
- **事务时间**描述数据库何时记录或认为该版本有效：9 月 5 日起。

这里“事务时间”是时态数据库术语，不是一次转账耗时。若只覆盖旧地址，无法回答“9 月 3 日他实际住哪”与“9 月 3 日数据库当时记在哪”这两个不同问题。可以保存生效区间与记录区间；区间端点、是否含结束时间等必须明确。

## 14. “NP问题”与算法难度

<a id="ch05-s048"></a>

### 14.1 先说明“规模变大”是什么意思

一题只有五列，手算所有属性组合尚可；若有 n 列，属性子集共有 2 的 n 次方个。n 是列数，`2ⁿ`表示 2 连乘 n 次；每列都有选或不选两种情况，所以得到这个数量。

**多项式时间**表示运行步骤可用输入规模的固定次幂控制，例如 n²；**指数增长**如 2ⁿ，规模增加时可能很快变得难以穷举。不能因手算某题麻烦，就直接判断它具有哪种理论复杂性。

<a id="ch05-s049"></a>

### 14.2 对照实际课件区分三个问题

课程 `ch8.pdf` 对不同问题分别给出了结论：

- 第 44 页：对给定原模式 R 和依赖集 F，检查 F 中各非平凡依赖的左部是否为超码，足以判断原模式 BCNF；不必展开全部 F⁺。分解后子模式却不能只检查原 F 中原样留下的规则，要考虑投影依赖。
- 第 54 页：一般的 **3NF 判定是 NP-hard**；难点包括判定某属性是否属于某个候选码。NP-hard 常译“NP 难”，是一种严格的复杂性分类，不能简单理解为“绝对无法解”或“每个小例都很慢”。
- 第 42 页：给定分解的依赖保持可用多项式算法检验，不必先显式列出全部 F⁺。
- 第 54—55 页：3NF 综合分解有多项式算法；“判定给定模式是否 3NF”与“构造一个 3NF 分解”是不同问题。

课程总结把“NP问题”标在 BCNF 判定与分解、3NF 判定附近，但未把所有问题的输入、目标和限制写完整。不能据此概括为“所有 BCNF 检查和分解都 NP-hard”。若讨论另一个受限分解或优化问题的复杂性，需要先明确输入、目标与限制，不能直接沿用这里的结论。

<a id="ch05-s050"></a>

### 14.3 不展开 F⁺也能检查依赖保持

对一条待检查依赖 X→Y，先令 result=X，result 是当前可得到的属性集合。对每个子模式 Ri，计算：
```text
t = (result∩Ri)⁺∩Ri
result = result∪t
```
Ri 是第 i 个子模式；t 是临时新增信息。先拿手上已知且在这个子表的属性，用原 F 算闭包，再只留下本子表能承载的结果；把这些信息加入 result。遍历并重复直到没有新增。若包含 Y，则该依赖被保持。对原 F 的每一条都检查。

第 11.2 节 CB、AC，从 AB 出发：在 CB 内只有 B，可得的仍只有 B；在 AC 内只有 A，可得的仍只有 A。重复后仍 AB，得不到 C，故 AB→C 不保持。这与反例证明一致。

## 15. 常见误解

| 误解 | 为什么不对 |
| --- | --- |
| 样本姓名不重复，姓名就是永久候选码 | 样本巧合不等于业务保证 |
| AB→C 可以拆左边为 A→C、B→C | 分解律拆右边，不能随意拆决定因素 |
| 去掉规则时还用被去掉的规则证明它 | 循环论证，必须重算当前集合的闭包 |
| 3NF 就一定 BCNF | 3NF 允许某些右部主属性例外 |
| 无损就保持依赖 | 信息恢复与局部规则检查不同 |
| BCNF 分解后只看原 F 中完全留在子表的规则 | 必须考虑 F⁺的投影依赖 |

## 16. 本单元模拟题

<a id="ch05-s053"></a>

### 题目一：第一范式

**原题**

> 若关系 R 所有的属性都是不可再分的数据项，则该关系最低满足第几范式？

**PPT 参考答案**

> 第一范式。

**解析**

关系中每个属性值均为原子值，满足 1NF 的定义。题目没有提供函数依赖，无法进一步判断 2NF、3NF 或 BCNF，因此“最低满足 1NF”是正确答案。

<a id="ch05-s054"></a>

### 题目二：函数依赖推理

**原题**

> `AB→C` 能蕴含 `A→C`、`B→C` 吗？

**PPT 参考答案**

> 不能。

**完整解析**

不能。`AB→C` 表示 A 与 B 的组合能决定 C，不能说明其中任何一个属性单独决定 C。

反例：

| A | B | C |
| --- | --- | --- |
| 1 | 1 | x |
| 1 | 2 | y |
| 2 | 1 | z |

每个 `(A,B)` 组合唯一，因此可满足 `AB→C`；但相同 A 对应不同 C，相同 B 也对应不同 C，所以 `A→C`、`B→C` 都不成立。

<a id="ch05-s055"></a>

### 题目三：证明合并律

**原题**

> 请用阿姆斯特朗三定律（分解律、增强律和传递律）证明合并律，写出每一步骤的依据。

**PPT 情况**

PPT 只列出题目，没有给出文字证明。

**规范证明**

已知 `α→β` 和 `α→γ`，证明 `α→βγ`：

1. 由 `α→β`，使用增广律在两侧增加 α，得 `α→αβ`。
2. 由 `α→γ`，使用增广律在两侧增加 β，得 `αβ→βγ`。
3. 对步骤 1、2 使用传递律，得 `α→βγ`。

因此合并律成立。严格说，Armstrong 三公理通常指自反律、增广律和传递律；分解律是可由三公理推出的规则。题目采用的是课件表述，作答时按教师口径写出每步依据即可。

<a id="ch05-s056"></a>

### 题目四：3NF 与 BCNF 判断

**原题**

> 设有属于 1NF 的关系模式 `R=(A,B,C,D,E)`，R 上的函数依赖集 `F={BC→AD，AD→EB，E→C}`。  
> （1）R 是否属于 3NF？为什么？  
> （2）R 是否属于 BCNF？为什么？

**PPT 参考答案**

> 候选码为 `BC`、`AD`、`BE`。函数依赖集 F 中所有右部属性都在某个候选码中，因此属于 3NF。`E→C` 是非平凡依赖，而 E 不是超码，因此不属于 BCNF。

**完整推导**

<a id="ch05-s057"></a>

#### 第一步：求候选码

```text
(BC)⁺
= BC
⇒ BCAD        使用 BC→AD
⇒ ABCDE       使用 AD→EB
```

`B⁺`、`C⁺` 都不能得到全部属性，因此 `BC` 是候选码。

```text
(AD)⁺
= AD
⇒ ADEB        使用 AD→EB
⇒ ABCDE       使用 E→C
```

`A⁺`、`D⁺` 均不完整，因此 `AD` 是候选码。

```text
(BE)⁺
= BE
⇒ BEC         使用 E→C
⇒ ABCDE       使用 BC→AD
```

`B⁺`、`E⁺` 均不完整，因此 `BE` 是候选码。

主属性集合为 `{A,B,C,D,E}`，即所有属性都是主属性。

<a id="ch05-s058"></a>

#### 第二步：判断 3NF

把右部拆成单属性后检查。对每条非平凡依赖，虽然决定因素不一定都是超码，但右部属性全部为主属性，因此 R 满足 3NF。

<a id="ch05-s059"></a>

#### 第三步：判断 BCNF

`E⁺={E,C}`，不能得到 R 的全部属性，所以 E 不是超码。`E→C` 非平凡，违反 BCNF，故 R 不属于 BCNF。

<a id="ch05-s060"></a>

#### 一种 BCNF 分解

按 `E→C` 分解：

```text
R1(E,C)
R2(A,B,D,E)
```

- 交集为 `{E}`，且 `E→EC`，因此分解无损。
- `R1` 中 E 是码，满足 BCNF。
- `R2` 中投影依赖的决定因素可作为超码，满足 BCNF。
- 原依赖 `BC→AD` 跨越两个子模式，不能仅靠分别检查 `R1`、`R2` 直接保证，因此该分解不保持全部依赖。


<a id="ch05-s061"></a>

### 16.1 对原模拟题补足背景与每步含义

<a id="ch05-s062"></a>

#### 原子值题：条件只保证到哪里

题目讨论一张关系表，不限定学生或银行业务。“所有属性不可再分”是在当前模型里每格一个值，因此直接对应 1NF。没有给函数依赖，无法知道有无部分依赖、传递依赖；不能根据 1NF 条件继续断言 3NF。

<a id="ch05-s063"></a>

#### AB→C 题：逐对检查反例

A、B、C 是三列的代号，反例中的 1、2、x、y、z 是教学值。前三行的 AB 分别 (1,1)、(1,2)、(2,1)，无相同 AB 对不同 C，因此满足 AB→C。

第 1、2 行 A 都为 1，但 C 为 x、y，所以 A→C 失败；第 1、3 行 B 都为 1，但 C 为 x、z，所以 B→C 失败。这个反例足以说明“不能由组合依赖必然推出任一单列依赖”，不表示所有满足组合依赖的数据都必然违反单列依赖。

<a id="ch05-s064"></a>

#### 合并律题：字母不是数值乘法

原证明中 αβ、βγ 是属性集合并集，例如 α={学号}、β={姓名}、γ={所属系}，合并律就是“学号分别确定姓名和系，因此同时确定姓名与系”。增广相同属性后重复成员只保留一次，所以 αα 写回 α。这解释了第一步为何从 α→β 得到 α→αβ，而不是出现两个不同 α。

<a id="ch05-s065"></a>

#### 五属性题：不遗漏候选码，并证明分解的代价

原题仅提供 R、F，没有业务背景；A—E 是属性代号，不能擅自解释成学生或银行字段。目标纯粹是依赖推理，不需虚构数据含义。

单属性闭包：A⁺={A}、B⁺={B}、C⁺={C}、D⁺={D}、E⁺={E,C}，都不是超码。十种两属性组合检查如下：

| 组合 | 闭包 | 是否候选码 |
| --- | --- | --- |
| AB | AB | 否 |
| AC | AC | 否 |
| AD | ABCDE | 是 |
| AE | ACE | 否 |
| BC | ABCDE | 是 |
| BD | BD | 否 |
| BE | ABCDE | 是 |
| CD | CD | 否 |
| CE | CE | 否 |
| DE | CDE | 否 |

未包含 AD、BC、BE 的三属性组合只需检查 ACE、CDE，闭包均不完整；所有四属性或五属性集合都包含某个已找到的码，不最小。因此全部候选码恰是 AD、BC、BE，原答案没有漏码。全部属性是主属性，故 3NF 条件的“右部主属性”能覆盖各非平凡依赖。

分解 EC 与 ABDE 后，ABDE 内的重要投影依赖为：

- AD→BE，直接来自 AD→EB。
- BE→AD，因为 E→C 后结合 B 得 BC，再用 BC→AD。

AD、BE 在 ABDE 上都是候选码。对 ABDE 所有属性子集的闭包检查可知，非超码子集不会推出本子模式内的新属性，所以它满足 BCNF；不能只以“看见两条左边像码”替代投影检查。

为何不保持 BC→AD？合并局部依赖 E→C、AD→BE、BE→AD，从 BC 出发没有 E，也没有 AD 或 BE，闭包仍为 BC，得不到 AD。原 F 却明确规定 BC→AD，因此存在丢失的检查能力。与此同时，交集 E 决定 EC，所以二表分解无损。两项证明依据不同。

## 17. 自拟自测题与逐步答案

以下四题为自拟题。

<a id="ch05-s067"></a>

### 17.1 求属性闭包与全部候选码

**条件**：独立 R(A,B,C,D)，F={A→B,B→C}，A—D 为列名代号。问 A⁺及候选码。

**步骤**：A 开始可得 B，再得 C，无规则能得 D，所以 A⁺=ABC。A、D 未在任何右边出现，码必须包含它们。AD⁺开始 AD，加入 B、C 得 ABCD；去 A 只剩 D，去 D 只得 ABC。

**结论**：候选码只有 AD。A 并不是码，尽管它能确定三列。

<a id="ch05-s068"></a>

### 17.2 2NF 已经成立，为什么还要拆？

**条件**：R(S,Dept,Office)，每学生一个系、每系一个办公室；F={S→Dept,Dept→Office}。S、Dept、Office 依次学号、系、办公室。

**步骤**：S⁺含全部，唯一候选码 S。码只有一个属性，没有本例所指的真子集部分依赖，满足 2NF。Dept 非超码，Office 非主属性，Dept→Office 违反 3NF。

**分解**：STUDENT_DEPT(S,Dept)与DEPT_OFFICE(Dept,Office)。交集 Dept 决定后表，故无损；两条原依赖各在一表，故保持依赖。**结论**：2NF 仍可能有传递造成的重复。

<a id="ch05-s069"></a>

### 17.3 判断 AB 与 BC 分解是否无损

**条件**：R(A,B,C)，F={A→B}。拟拆 AB、BC。

**步骤**：交集 B。B⁺只有 B，既不能决定 AB，也不能决定 BC。二表判据失败。第 10.2 节两行反例满足 A→B，却拼出四行。

**结论**：该分解相对于 F 有损。改为 AB、AC，交集 A 决定 AB，才是无损；并且 A→B 在 AB 内能检查。

<a id="ch05-s070"></a>

### 17.4 一份正则覆盖是否等价？

**条件**：R(A,B,C)，F={A→B,B→C,A→C}，有人建议只保留 A→C。

**步骤**：A→C 的确可由前两条推得，所以能去掉它；反过来仅 A→C 无法推出 A→B 或 B→C。分别算 A⁺=AC、B⁺=B 就看出差异。

**结论**：建议不等价；可采用 Fc={A→B,B→C}。简化规则要保留全部推理能力，不是条数越少越好。

## 19. 用同一张检查表，分清四种结论

面对 R 和 F，以及一个准备采用的分解，按下面顺序记录结论，不能用其中一项代替其他项。

| 要判断的事 | 输入是什么 | 要证明什么 | 主例 ENROLL 的结果 |
| --- | --- | --- | --- |
| 候选码 | R、F、一个属性组合 | 决定全部属性且不能再删 | SC 是唯一候选码 |
| 3NF/BCNF | 依赖与候选码/超码信息 | 每项非平凡依赖符合相应条件 | 原汇总表不符合，三张分表符合 BCNF |
| 无损连接 | 分解和原依赖 | 每个原合法实例拆后拼回恰好相等 | 两次交集决定一侧，分解无损 |
| 依赖保持 | 各子表投影依赖 | 局部规则联合仍推出原规则 | 三条主例规则各在一张表中，可保持 |

“拆得更细”不是最终目标。第 9.2 节 ABC 满足 3NF 却不满足 BCNF，按 C→B 拆为 CB/AC 后可以无损且都达 BCNF，但 AB→C 不再能只靠两张表内部检查。这个例子同时满足某些性质、失去另一种性质，正是需要分开判断的原因。

判定、构造和验证也是不同任务：判断一张已有表属于哪种范式，不等于构造一个分解；验证给定分解是否保持依赖，也不需要先把全部 F⁺列成巨大的清单。复杂性结论应带着具体任务和输入条件阅读。

## 20. 本章概念与方法速查

按用途查找概念或方法，再回正文看条件与完整例子。表中的“类别”帮助区分对象、性质、操作和协议。

| 名称 | 类别 | 解决什么问题 | 基本形式或读法 | 注意点与正文 |
| --- | --- | --- | --- | --- |
| 更新/插入/删除异常 | 结构造成的风险 | 同一类事实被重复或与另一类事实捆绑保存。 | 先看一行包含了几种不同事实。 | 正常的受控重复与未维护的冗余要分清。 [回正文](#ch05-s004) |
| 函数依赖 X→Y | 业务保证 | 两行的 X 相同时，Y 必须也相同。 | 同左值不能对应不同右值。 | 不是编程函数，也不是凭当前样本没冲突就成立。 [回正文](#ch05-s009) |
| 平凡/非平凡与主/非主属性 | 两个不同分类角度 | 依赖是否增加新属性，与属性是否出现在某候选码中。 | Y⊆X 是平凡；候选码中的列是主属性。 | 不要把“主属性”只理解为已选主码中的列。 [回正文](#ch05-s010) |
| 超码、候选码与主码 | 识别属性集合 | 超码覆盖全体，候选码无多余，主码从候选码选定。 | 计算闭包，再逐个删除检验最小性。 | 找到一组候选码不保证已经找全。 [回正文](#ch05-s011) |
| 属性闭包 X⁺ | 属性推理结果 | 从 X 沿依赖得到的全部属性。 | 先放 X，左部全已知时加右部，反复直到不增长。 | 不是数值加一；还需最小性才能判候选码。 [回正文](#ch05-s017) |
| 依赖闭包 F⁺与蕴含 | 规则推理结果 | F⁺是全部可推出规则；用 X⁺检查一条依赖是否被保证。 | F 蕴含 X→Y，当且仅当 Y⊆X⁺。 | 属性集合和规则集合是不同结果；不能推出不代表所有样本都违反。 [回正文](#ch05-s020) |
| Armstrong 公理 | 推理规则 | 自反、增广和传递推出可靠的依赖结论。 | 知道整体可知部分；双方加同属性；顺链传递。 | 增广改变两边；分解律拆右边，不随意拆左边。 [回正文](#ch05-s014) |
| 正则覆盖/最小覆盖 | 等价的规则精简 | 去掉多余属性或依赖，保持全部推理能力。 | 先明确表示约定；每次调整后重算相应闭包。 | 不能留下被删规则来证明它自己；同左部合并与单右部形式要按课程区分。 [回正文](#ch05-s022) |
| 1NF 与 2NF | 入门结构标准 | 每格一个原子值，并避免非主属性只依赖候选码的一部分。 | 先检查值，再检查非主属性对每个候选码的依赖。 | 2NF 不能只检查选定主码，也不能保证没有传递造成的重复。 [回正文](#ch05-s005) |
| BCNF | 函数依赖范式 | 每个非平凡决定因素都必须能识别本关系整行。 | 非平凡 X→Y 时，X⁺应包含本关系全部属性。 | 子表要考虑投影依赖，不能只看原 F 中原样剩余的条目。 [回正文](#ch05-s024) |
| 3NF | 较宽松的函数依赖范式 | 平凡、左部超码，或右部单属性为主属性，满足一项即可。 | 先确定所有候选码与主属性，再逐项判断。 | BCNF 推出 3NF，反向不保证。 [回正文](#ch05-s029) |
| BCNF 分解与 3NF 综合 | 两种构造方法 | 前者按违反依赖拆，后者围绕等价精简规则建子模式。 | 违反 X→Y 可拆 XY 与 R−(Y−X)；综合还检查候选码是否被包含。 | 检查每次拆的性质，并给出依赖保持的单独证明。 [回正文](#ch05-s026) |
| 无损连接 | 信息恢复性质 | 从原合法关系投影再连接，恰好还原，不产生假组合。 | 二表覆盖 R 时，交集应决定至少一侧全部属性。 | 二表判据不直接适用于随便的多表逐对比较。 [回正文](#ch05-s033) |
| Chase | 多表无损检验方法 | 用依赖合并必须相同的符号，找全目标符号行。 | 每子表一行，本表列用 a，其他格初始不同 b 符号，再反复统一。 | 这是符号检验，不是实际查询执行轨迹。 [回正文](#ch05-s037) |
| 依赖保持 | 规则检查性质 | 各表内部规则合起来仍能保证全部原业务依赖。 | 比较投影依赖联合的推理能力与 F。 | 无损不等于保持依赖，两项用不同证据证明。 [回正文](#ch05-s038) |
| 多值依赖与 4NF | 独立多值信息 | 给定 X 时，Y 与剩余属性的选择能自由组合。 | X↠Y；非平凡多值决定因素应为超码。 | 若某爱好依赖所用语言，就不能假设自由组合。 [回正文](#ch05-s041) |
| 有效时间与事务时间 | 两种历史观察 | 现实何时生效，以及数据库何时记录这个版本。 | 分别保存事实区间和记录区间。 | 事务时间不是业务操作耗时，区间边界要说明。 [回正文](#ch05-s046) |
| 判定、构造与验证的复杂性 | 任务区分 | 原模式范式判断、分解构造、给定分解性质验证是不同问题。 | 明确输入、输出与限制，再读 NP-hard 等结论。 | 不展开 F⁺也可以用闭包步骤检查依赖保持。 [回正文](#ch05-s049) |
