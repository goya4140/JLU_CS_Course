数据库与数据库管理系统

1.1 先从一个最朴素的说法开始

想象一下学校的档案室：一排排柜子里装着学生的学籍卡、教师的人事卡、课程表和成绩单。柜子本身只是存放东西的地方，真正让档案"好用"的，是那套分类规则、索引卡片和借阅制度。数据库管理系统（DBMS，Database Management System）在计算机世界里扮演的，就是"柜子加整套管理制度"的角色。

课件给 DBMS 下的定义包含三个缺一不可的部分，你可以把它记成"数据、程序、环境"三件套：

相互关联的数据关于某个特定企业/组织的信息集合
访问数据的一组程序负责增删改查与管理
方便而高效的使用环境让用户不必关心底层细节

注意这里的"企业（enterprise）"是个广义说法，不一定指公司，任何一个需要管理信息的组织都算，比如一所大学、一家银行、一个电商平台。数据库里存放的，就是关于这个组织的、彼此之间存在联系的数据。

1.2 数据库其实就在你身边

课件特意列出了一批数据库应用场景，因为很多人平时感觉不到数据库的存在，其实它几乎渗透了日常生活的每个角落：

应用领域典型数据库任务
银行业交易处理（转账、取款、余额）
航空业机票预订、航班时刻表
大学注册选课、成绩管理
销售行业客户、商品、采购信息
在线零售订单跟踪、个性化推荐
制造业生产、库存、订单、供应链
人力资源员工档案、工资、个税扣减记录
生活类比

你在手机银行 App 上点一下"转账"，背后是银行的数据库在同时改两个账户；你在购物网站看到的"猜你喜欢"，是数据库根据你过去的订单算出来的；你选课系统里看到的剩余名额，也是数据库实时统计的结果。这些场景有一个共同点：数据量大、要长期保存、还要被很多人同时使用，这正是数据库要解决的典型问题。

1.3 贯穿全书的"大学数据库"例子

为了让概念有个具体的落点，课件用一个大学数据库当贯穿全书的例子。它需要支持的应用程序包括：

  • 添加新的学生、教师和课程；
  • 给学生注册课程，并生成班级花名册（class roster）；
  • 录入学生成绩、计算平均学分绩点（GPA），并生成成绩单（transcript）。

这个例子看起来简单，但它背后会牵出后面所有章节的内容：怎么把这些信息组织成一张张表（关系模型）、怎么用 SQL 提问、怎么设计才能避免冗余、多人同时选课时怎么保证名额不出错。课件同时提醒了一个历史背景：早期的数据库应用，是直接搭建在文件系统之上的——这正好引出下一节的问题。

2

文件系统的七大痛点

在数据库出现之前，程序员确实是用操作系统提供的文件来存数据的：需要什么信息就定义一个文件，写专门的程序去读写。这不是不能用，但随着数据规模和使用人数增长，麻烦会一个接一个冒出来。课件把这些麻烦归纳成七个方面，它们也是理解"为什么需要 DBMS"的核心论据。

2.1 前四个痛点：数据本身管不好

数据冗余与不一致

同一份信息在不同文件里重复存放，而且文件格式还各不相同。比如学生的地址在学籍文件和宿舍文件里各存一份，搬一次家就得改两处，漏改一处就对不上了。

数据访问困难

每来一个新的查询需求，就得新写一个程序。想临时查"所有工资超过一万元的教师"，如果现成程序没这个功能，只能临时开发，非常死板。

数据孤立

数据散落在多个文件、多种格式里，彼此之间是"孤岛"。想把学生信息和成绩信息连起来回答问题，得先费劲地处理格式差异。

完整性问题

像"账户余额必须大于 0"这样的完整性约束，被"埋"在程序代码里，而不是显式地写在数据旁边。想新增或修改一条约束，往往要改动很多程序。

2.2 后三个痛点：更新、并发与安全

痛点五：更新的原子性没法保证

"原子性"这个词后面讲事务时还会反复出现，它的意思是：一组操作要么全部做完，要么就像完全没发生过，不能停在中间。课件用转账举例：从一个账户扣钱、往另一个账户加钱，这两步本该是一个整体。如果系统在两步之间崩溃，钱就凭空消失了，数据库会停在一个自相矛盾的状态。普通文件系统没有义务帮你守住这条底线。

痛点六：多用户并发访问会互相打架

为了性能，数据库必须允许多个用户同时访问，但不加控制的并发会制造不一致。课件给了一个很经典的例子：两个人同时读同一个余额（比如 100），又同时各取 50。两个程序都按"100 减 50"去算，最后余额变成 50，而正确结果应该是 0——系统少扣了 50。

易混点提醒

"并发"本身不是坏事，恰恰相反，让很多人同时用是提升性能的必要手段。真正出问题的是不受控制的并发。所以数据库要做的不是禁止并发，而是设计一套并发控制机制，让大家在并发的同时仍然得到正确结果——这是第 15 章的主题。

痛点七：安全性难以保证

现实中经常需要让用户"只能看到一部分数据"。比如普通员工可以查同事的办公电话，但不应该看到每个人的工资。在文件系统里想做到这种细粒度的访问控制非常困难，而数据库系统把授权机制做成了标准功能。

知识点说明

课件在讲完七个痛点后给出一句总结：数据库系统对上述所有问题都提供了解决方案。这句话其实是整门课的"目录索引"——冗余问题靠规范化和 ER 设计解决，访问问题靠 SQL 解决，原子性靠事务管理解决，并发问题靠并发控制解决，安全问题靠授权机制解决。学到后面每一章时，你都可以回头看看它对应这里的哪个痛点。

数据抽象的三个层次

数据库要同时伺候两类差别很大的使用者：写底层存储程序的工程师关心字节在磁盘上怎么摆，而做成绩查询的教务人员只想知道"某个学生考了多少分"。如果让所有人都面对全部细节，系统会复杂到没法用。解决办法是分层抽象——不同的人只看不同详细程度的视图。

3.1 物理层、逻辑层、视图层

层次回答的问题课件中的说明
物理层
physical level		一条记录在磁盘上到底怎么存？描述一条记录（例如客户记录）的实际存储方式，是最底层的细节
逻辑层
logical level		数据库里存了哪些数据？它们之间什么关系？用记录类型描述数据及数据间的关系，例如教师记录由 ID、姓名、系名、工资四个字段组成
视图层
view level		某个具体用户能看到什么？应用程序隐藏数据类型细节；视图还能出于安全目的隐藏信息，比如把员工工资藏起来

课件在逻辑层给了一个教师记录类型的伪代码，你可以直观感受一下"逻辑层描述"长什么样：

type instructor = record   ID      : string;   name    : string;   dept_name: string;   salary  : integer; end;
生活类比

用手机点外卖时，你看到的是菜品名称、图片和价格（视图层）；餐厅内部的进销存系统记录了每份食材的供应商和库存（逻辑层）；而仓库管理员还要操心每种食材放在哪个货架、用什么容器装（物理层）。同一套数据，三个层次的人各看各的，互不干扰。

3.2 模式与实例：像"类型"和"变量"一样

课件用编程语言里的"类型"和"变量"来类比这两个概念，有编程基础的话会非常好理解：

  • 模式（schema）：数据库的逻辑结构，相当于程序里的类型信息。比如"数据库由客户、账户以及它们之间的关系组成"，这句话描述的就是模式。模式又分物理模式（物理层的设计）和逻辑模式（逻辑层的设计）。
  • 实例（instance）：数据库在某个特定时刻的实际内容，相当于变量在某一时刻的取值。今天数据库里有 1000 名学生，明年变成 1200 名，变的是实例，而"学生由哪些字段构成"这个模式通常不变。

3.3 物理数据独立性

这是分层抽象带来的一个重要好处。物理数据独立性指的是：修改物理模式（比如换一种磁盘存储方式、调整文件组织）时，不需要改变逻辑模式。因为应用程序依赖的是逻辑模式，底层存储怎么优化，上层应用完全不用重写。

课件还顺带总结了一个通用设计思想：各个层次和部件之间的接口应该定义清晰，这样改动某些部分时才不会严重波及其他部分。这和软件工程里"高内聚、低耦合"的思路是一脉相承的。

易混点提醒

物理独立性说的是"物理层变了，逻辑层不用跟着变"，而不是"逻辑层可以随便改"。逻辑模式的变更（比如新增一个字段）同样可能影响应用程序，只是这类影响在数据库里也有相应机制（如视图）来缓冲，不要把两层的独立性混为一谈。

4

数据模型家族

盖房子需要图纸语言，组织数据也需要一套"描述语言"。数据模型就是这样一组工具，它用来描述四个方面：数据本身、数据之间的关系、数据的语义（含义）、数据上的约束。课件把常见的数据模型分成几大类，它们恰好对应教材的不同章节。

4.1 四类主流模型

数据模型特点与用途教材位置
关系模型用一张张二维表组织数据，是当今绝对主流的模型第 2 章
实体-联系模型（ER）主要用于数据库设计阶段，把企业建模成实体和联系的集合第 7 章
基于对象的模型包括面向对象模型和对象-关系模型，吸收了面向对象的思想概念扩展
半结构化数据模型典型代表是 XML，数据不要求严格固定的模式数据交换

另外课件还提到两类更老的模型：网状模型（network model）和层次模型（hierarchical model），它们在关系模型普及之前被广泛使用，现在主要作为历史背景了解即可。

4.2 关系模型：一张表就是一个关系

关系模型里的数据以表格形式呈现，列（columns）描述字段，行（rows）描述一条条具体记录。比如教师表的每一行是一位教师，每一列分别是 ID、姓名、系名、工资。这种表示方式直观、有坚实的数学基础（关系代数），而且配合 SQL 使用非常方便，所以成为主流。课件还展示了一个完整的示例关系数据库，由多张相互关联的表组成，这会在第 2 章详细展开。

4.3 对象-关系模型与 XML

对象-关系数据模型

经典关系模型要求值是"扁平的、原子的"，一个格子里只能放一个不可再分的值。对象-关系模型在关系模型的基础上加入面向对象的特性，允许元组的属性拥有复杂类型，甚至嵌套关系这种非原子值；同时它保留了关系模型的根基，尤其是声明式的数据访问方式，并与已有的关系语言保持向上兼容。

XML：可扩展标记语言

XML 由万维网联盟（W3C）定义，最初是作为文档标记语言而不是数据库语言设计的。但它允许自定义标签、建立嵌套的标签结构，这让它成为一种非常好的数据交换方式，而不只是文档格式。课件指出，XML 已经成为新一代数据交换格式的基础，围绕它有一整套解析、浏览和查询工具。

知识点说明

初学者容易把"数据模型"和"数据库"当成一回事。数据模型是描述数据的一套规则和工具，相当于语法；数据库是按照某种模型组织起来的具体数据，相当于用语法写成的文章。同一个数据库管理系统可以支持一种或多种模型，理清这层关系，后面学关系模型时就不会发懵。

5

DML 与 DDL：数据库的两类语言

和数据库打交道离不开语言，而数据库语言按用途分成两大块：一块负责"存取操作数据"，一块负责"定义数据结构"。这两个缩写在整门课里会反复出现，先在这里把它们分清楚。

5.1 数据操纵语言 DML

DML（Data Manipulation Language，数据操纵语言）用来访问和操纵按照某种数据模型组织好的数据，它也叫查询语言（query language）。按"用户要告诉系统多少细节"，DML 分成两类：

类别用户需要说明什么特点
过程化
procedural		需要什么数据 以及 怎么拿到这些数据用户要规定获取步骤，控制力强但更费心
声明式（非过程化）
declarative		只说需要什么数据，不说怎么拿用户只描述目标，具体执行由系统决定，更简单

课件明确指出：SQL 是使用最广泛的查询语言，它整体上属于声明式语言——你写一句"找出 ID 为 22222 的教师姓名"，不用管系统是怎么翻表、走不走索引的。

5.2 数据定义语言 DDL 与数据字典

DDL（Data Definition Language，数据定义语言）是用来定义数据库模式的一套记法。课件给出的例子是建一张教师表：

create table instructor (   ID      char(5),   name    varchar(20),   dept_name varchar(20),   salary  numeric(8,2))

DDL 编译器会生成一组表，存放在数据字典（data dictionary）里。数据字典里装的是"关于数据的数据"，也就是元数据（metadata），主要包括：

  • 数据库模式：定义了有哪些表、每张表有哪些字段；
  • 完整性约束：比如主键约束（ID 能唯一标识一位教师）、参照完整性（例如任何教师元组里的系名，都必须在院系关系中真实出现）；
  • 授权信息：谁有权限访问哪些数据。

5.3 SQL 长什么样，应用程序怎么连数据库

课件给了两个 SQL 例子，让你先有个直观印象。第一个是找出 ID 为 22222 的教师姓名：

select name from  instructor where instructor.ID = '22222'

第二个是找出预算超过 95000 的系里所有教师的 ID 和系名：

select instructor.ID, department.dept_name from  instructor, department where instructor.dept_name = department.dept_name   and department.budget > 95000

应用程序一般通过两条途径访问数据库：一是嵌入式 SQL，也就是对编程语言做扩展，把 SQL 写进程序里；二是应用程序接口，比如 ODBC/JDBC，程序通过接口把 SQL 查询发给数据库。这些内容对应教材第 3、4、5 章。

易混点提醒

DML 和 DDL 不是两种互相独立的语言，而是同一种数据库语言（SQL）里的两类功能。SQL 里既有 select/insert/update/delete 这些 DML 语句，也有 create/alter/drop 这些 DDL 语句，考试时让你判断某条语句属于哪类，看它是"操作数据"还是"定义结构"即可。

6

数据库设计：决定数据的总体结构

数据库设计指的是设计数据库的总体结构，课件把它分成逻辑设计和物理设计两个层面，又把要做的决策分成"业务决策"和"计算机科学决策"。

6.1 逻辑设计与物理设计

  • 逻辑设计（Logical Design）：决定数据库模式，也就是要找到一组"好的"关系模式。这里面又分两种决策：
    • 业务决策：数据库里到底应该记录哪些属性？这取决于组织的业务需求，比如要不要记录学生的家庭住址；
    • 计算机科学决策：应该有哪些关系模式？这些属性怎么分配到不同的关系模式中？这是技术层面的取舍。
  • 物理设计（Physical Design）：决定数据库的物理布局，比如数据在磁盘上怎么组织、建哪些索引。

6.2 为什么要纠结"好的模式"

课件抛出了一个问题："这个设计有什么毛病吗？"最容易想到的坏设计，就是把所有字段塞进一张大表。比如把教师 ID、姓名、系名、系预算全放在教师表里：系里有 50 位教师，系预算就重复存 50 份；一旦调整预算，50 个地方都得改，漏改就不一致。这就是前面说的冗余痛点在设计阶段的具体表现。

6.3 两条设计路线：规范化理论与 ER 模型

规范化理论（第 8 章）

把"什么样的设计是坏的"形式化下来，并给出检测方法。它通过函数依赖和各级范式，让你能判断一个模式是否存在冗余、该怎么分解。

实体-联系模型（第 7 章）

把企业建模成实体和联系的集合。实体是企业中可区分的"事物"，用一组属性描述；联系是几个实体之间的关联，用 ER 图直观表示。

课件在讲 ER 模型时还埋了一个伏笔：在 ER 建模之后，教师和学生表里原本的 dept_name 字段发生了变化——它被"联系"取代了。这正是 ER 模型用来消除冗余的方式，第 7 章会详细讲怎么把 ER 图转换成关系表。

知识点说明

ER 模型和规范化理论不是二选一的竞争关系，更像是设计流程里配合使用的两个工具：先用 ER 模型把现实世界的需求画出来，再把 ER 图转换成关系模式，最后用规范化理论检查这些模式是否足够"好"、需不需要进一步分解。

7

数据库系统内部的三大件

从外部看，数据库是一个整体；打开这个"黑箱"，里面有三个核心部件分工协作：存储管理、查询处理、事务管理。这一节先建立整体印象，后面的章节会逐个深入。

7.1 存储管理：管数据怎么落盘

存储管理器（storage manager）是一个程序模块，它在底层存储的数据，与上层提交的应用程序和查询之间提供接口。它负责两类任务：与文件管理器交互，以及高效地存储、检索和更新数据。涉及的核心问题有三个：存储访问、文件组织、索引与散列。换句话说，数据最终怎么写到磁盘、怎么快速找回来，都是存储管理器的事。

7.2 查询处理：把一句提问变成结果

当你写出一条 SQL，系统并不是直接"理解"了它，而是要走三步：

解析与翻译parsing and translation
优化optimization
执行evaluation

同一个查询往往有多种等价的表达方式，每种运算又有不同的算法可选。课件特别强调：好的执行方式和坏的执行方式，成本差距可能大得惊人。所以系统需要估算各个运算的成本，而这又高度依赖数据库维护的关系统计信息，还要估算中间结果的统计量，才能算出复杂表达式的总成本。这正是查询优化这一大块内容的由来。

7.3 事务管理：管故障和并发

这一部件回答两个吓人的问题：系统崩了怎么办？多个人同时改同一份数据怎么办？先明确事务的定义：事务是一组操作的集合，它在数据库应用中完成一个单一的逻辑功能。比如转账这件事，涉及的所有读写合起来就是一个事务。

  • 事务管理部件保证即使发生系统故障（断电、操作系统崩溃）或事务自身失败，数据库仍能保持一致（正确）的状态；
  • 并发控制管理器控制并发事务之间的相互影响，保证数据库的一致性。
生活类比

把数据库想象成一家餐厅：存储管理器是后厨的仓库管理员，负责食材分门别类、随用随取；查询处理器是前台接单和出餐的调度，要选最快的做菜路线；事务管理器则像一套应急预案，既保证停电恢复后账目不乱，也保证多个服务员同时点单时不会把同一道菜卖重。

8

体系结构、用户与管理员、发展史

8.1 数据库体系结构

数据库系统的架构很大程度上受它运行的计算机系统影响，课件列出四种形态：

架构直观含义
集中式（centralized）所有功能集中在一台机器上
客户-服务器（client-server）客户端负责交互，服务器负责数据管理
并行（parallel，多处理器）多处理器协同工作，提升处理能力
分布式（distributed）数据分散在多个地点，逻辑上仍是一个整体

8.2 数据库用户与管理员

使用数据库的人角色不同，关心的层次也不同。课件区分了普通数据库用户和数据库管理员（DBA，Database Administrator）。DBA 对整个系统负有集中管理职责，这类职责包括：模式定义、存储结构与访问方式定义、数据访问授权、日常运维（如性能调优、备份恢复、用户管理）。普通用户则主要通过应用程序或查询语言与数据打交道，不需要关心底层结构。

8.3 数据库系统发展简史

课件按年代梳理了这条技术演进线，了解它有助于你理解各种模型为什么会出现：

年代关键进展
1950 年代至 1960 年代初用磁带做存储，只能顺序访问；用穿孔卡片输入，数据处理方式原始
1960 年代末至 1970 年代硬盘出现，支持直接访问；网状、层次模型广泛使用；Ted Codd 提出关系数据模型（后来因此获图灵奖）；IBM 启动 System R、加州大学伯克利分校启动 Ingres 原型；出现了当时高性能的事务处理
1980 年代关系原型走向商业化，SQL 成为工业标准；并行与分布式数据库、面向对象数据库出现
1990 年代大型决策支持与数据挖掘应用兴起；出现数 TB 级的大型数据仓库；电子商务出现
2000 年代初XML 与 XQuery 标准；自动化数据库管理
2000 年代后期巨型数据存储系统出现，如 Google BigTable、Yahoo PNuts、Amazon 的相关系统
知识点说明

注意这条历史主线背后的驱动力：存储介质的进步（磁带→硬盘）打开了新的数据访问方式，而应用规模的增长又不断催生新的数据模型和架构。关系模型能取代网状、层次模型，靠的是更简单的逻辑和坚实的数学基础；后来的大数据系统则是在互联网规模下对新问题的回应。
