事务

一次转账要扣一个账户、加另一个账户，中间任何一步出错都可能让钱"凭空消失"。事务就是把这样一组操作打包成一个不可分割的逻辑单元，用 ACID 四性保证它在故障和并发面前依然正确。这一单元还会引出可串行化、可恢复调度和 SQL 隔离级别，为下一章并发控制打基础。

开篇导读：什么是事务

事务是一段程序执行单元，它访问、也可能更新若干数据项。课件的经典例子是"从账户 A 转 50 元到账户 B"，一共六步：读 A、A 减 50、写 A、读 B、B 加 50、写 B。

围绕这组操作有两类必须处理的问题：各种故障（硬件故障、系统崩溃）和多个事务的并发执行。整章就是回答：在这两种情况下，系统怎样保证数据不出错。

ACID 四性

为了维护数据完整性，数据库系统必须保证事务具备四个性质，首字母合起来就是 ACID。

原子性 Atomicity

事务的全部操作要么都正确反映到数据库，要么一个都不反映。转账若在第 3 步后、第 6 步前失败，部分执行的更新不能留在库里。

一致性 Consistency

孤立执行一个事务，会保持数据库的一致性。本例中 A 与 B 之和在执行前后不变。

隔离性 Isolation

多个事务并发执行时，每个事务都感觉不到其他事务的存在，中间结果对其他事务隐藏。

持久性 Durability

事务成功完成后，它对数据库的修改即使遇到系统故障也必须持久保留。

课件对隔离性的描述更具体：对任意一对事务 Tᵢ、Tⱼ，在 Tᵢ 看来，Tⱼ 要么在它开始前就已结束、要么在它结束后才开始。一致性要求既包括显式的主键、外键约束，也包括隐式约束（如全部账户余额之和减去贷款总额必须等于手头现金）。事务执行过程中数据库可能暂时不一致，但成功结束时必须恢复一致，错误的事务逻辑本身会导致不一致。

2

事务状态

一个事务在生命周期里会在五种状态之间切换。

活动 active初始状态，执行中
部分提交最后一条语句执行完
失败 failed无法继续正常执行
中止 aborted已回滚、恢复到开始前
提交 committed成功完成

为什么最后一条语句执行完只是"部分提交"而不是直接提交？因为此刻数据可能还在内存缓冲区，真正写入磁盘、确认无误后才转入提交。中止之后有两个选择：重启事务（仅当没有内部逻辑错误时可行）或杀掉事务。

3

并发执行与调度

为什么要并发

让多个事务并发有两个好处：提高处理器和磁盘利用率，从而提升吞吐量（一个事务用 CPU 时另一个可以读磁盘）；缩短平均响应时间，短事务不必排在长事务后面干等。并发控制机制就是实现隔离性、防止并发事务破坏一致性的手段。

调度（schedule）

调度是一个指令序列，规定并发事务各指令按什么时间顺序执行。它必须包含这些事务的全部指令，并且保持每个事务内部指令的原有顺序。成功完成的事务最后一条是 commit，失败的最后一条是 abort。

所有事务一个接一个、互不交错的调度叫串行调度。基本假设是每个事务单独执行都保持一致性，所以串行调度必然保持一致。课件给出了 T1 在前、T2 在前两种串行调度，以及一个非串行、却与某个串行调度等价的并发调度；还给出一个破坏了 A+B 之和的坏调度，说明不是所有并发调度都正确。

4

冲突可串行化

课件先做简化：只关注 read 和 write 两类指令，事务在两次读写之间可以在本地缓冲区做任意计算。

什么是冲突指令

事务 Tᵢ 的指令 lᵢ 和 Tⱼ 的指令 lⱼ 冲突，当且仅当它们访问同一个数据项 Q，且至少有一个是 write：

指令组合是否冲突
read(Q) 与 read(Q)不冲突
read(Q) 与 write(Q)冲突
write(Q) 与 read(Q)冲突
write(Q) 与 write(Q)冲突

冲突会在两条指令之间强制一个逻辑上的先后顺序。反过来，如果两条相邻指令不冲突，交换它们结果不变。

冲突等价与冲突可串行化

如果调度 S 能通过一系列不冲突指令的交换变换成 S′，就说 S 和 S′ 冲突等价。若 S 能这样变换成某个串行调度，S 就是冲突可串行化的。课件的 Schedule 3 经过若干次交换变成 T1 在前的串行调度，所以它冲突可串行化；而有的调度怎么交换都无法变成任何串行调度，就不是冲突可串行化的。

5

视图可串行化

两个调度 S、S′ 视图等价，需要对每个数据项 Q 同时满足三个条件：

  1. 若 S 中 Tᵢ 读 Q 的初始值，S′ 中也必须由 Tᵢ 读初始值；
  2. 若 S 中 Tᵢ 读到的 Q 值是 Tⱼ 写出来的，S′ 中 Tᵢ 也必须读同一个 Tⱼ 写出的值；
  3. S 中对 Q 做最终 write 的事务，在 S′ 中也必须做最终 write。

若 S 与某个串行调度视图等价，它就是视图可串行化的。每个冲突可串行化的调度也视图可串行化，但反过来不成立：存在视图可串行化、却不冲突可串行化的调度，课件指出这类调度都含有盲写（blind write），即事务没读过数据就直接写。

6

优先图与可串行化测试

优先图（precedence graph）是一个有向图，顶点是各个事务。如果 Tᵢ 比 Tⱼ 先访问了引发冲突的数据项，就画一条 Tᵢ → Tⱼ 的边，还可以用数据项给边做标注。

一个调度冲突可串行化 ⇔ 它的优先图无环

环检测算法耗时约 n²（更好的是 n+e）。若图无环，对它做拓扑排序就能得到一个可串行化顺序，比如 T5→T1→T3→T2→T4。

视图可串行化没法直接用优先图判断，其扩展测试的代价关于图规模是指数级的，判定问题属于 NP 完全类，所以不太可能存在高效算法；实践中只检查一些充分条件。

7

可恢复调度、级联回滚与无级联

可恢复调度

如果 Tⱼ 读了 Tᵢ 之前写的数据项，那么 Tᵢ 的 commit 必须出现在 Tⱼ 的 commit 之前，这样的调度才是可恢复调度。否则 Tᵢ 一旦中止，Tⱼ 可能已经把读到的不一致结果展示给用户，无法收回。

级联回滚

级联回滚（cascading rollback）指一个事务失败，引发一连串事务都要回滚。当 T10、T11、T12 都还没提交、且后者读了前者写的数据时，T10 失败会迫使 T11、T12 全部回滚，可能导致大量工作被撤销。

无级联调度

在无级联（cascadeless）调度里，若 Tⱼ 要读 Tᵢ 写的数据，Tᵢ 的 commit 必须出现在 Tⱼ 的读操作之前，这样级联回滚不可能发生。每个无级联调度都可恢复，最好把调度限制在无级联范围内。

8

并发控制目标与弱一致性

数据库必须保证所有实际产生的调度都冲突或视图可串行化、可恢复，最好无级联。一次只运行一个事务的策略虽然生成串行调度，并发度却太差。等调度执行完再去测可串行化又为时已晚，所以目标是设计能提前保证可串行化的并发控制协议。

这类协议通常不会边执行边检查优先图，而是施加一套规则从根源上避免不可串行化的调度；不同协议在"允许的并发量"和"开销"之间做权衡。

有些应用愿意接受弱一致性，允许不可串行化的调度，比如只读事务想估算全账户总余额、查询优化器用的统计数据本来就允许近似。这是用准确性换性能。

SQL 隔离级别与事务定义

SQL-92 四个隔离级别

级别能读到什么
可串行化 serializable默认，最强
可重复读 repeatable read只读已提交记录，重复读同一记录值相同，但仍可能不可串行化
读已提交 read committed只读已提交记录，但连续两次读可能得到不同的已提交值
读未提交 read uncommitted连未提交的记录也可能读到

课件警告：有些数据库默认并不保证可串行化，比如 Oracle 和 PostgreSQL 默认采用 SQL 标准之外的"快照隔离"。

SQL 中的事务定义

事务隐式开始，以 commit work（提交并开启新事务）或 rollback work（中止当前事务）结束。多数系统默认每条 SQL 成功后也隐式提交，可以用指令关闭，比如 JDBC 里的 connection.setAutoCommit(false)。

本章小结与自测

一条主线

事务是不可分割的执行单元，靠 ACID 四性在故障和并发面前保证正确。判断并发调度是否正确，看它是否等价于某个串行调度：冲突可串行化可用优先图无环快速判定，视图可串行化更宽松但判定是 NP 完全；恢复方面要求可恢复、最好无级联。SQL 提供四个隔离级别，在一致性和性能之间取舍。

一句话记忆：事务把"一串操作"变成"一件事"，可串行化让"并发"看起来像"排队"。
