## 1. 【课程PPT补充知识点】为什么需要并发控制协议


上一章能判断交错是否正确，这一章要解决执行时的选择：某个事务现在想读写数据，应当放行、等待，还是撤销重试？先看两个事务同时改余额，再比较不同控制办法。

**背景**：账户 A 有 500 元，T1 存入 100，T2 取出 50。若两人都先读 500，再分别写 600、450，最终可能为 450，丢失 T1 的存款；正确结果应为 550。

**并发控制协议**是一组约束事务访问数据的规则，例如读取前申请许可、提交前验证。它不能替应用判断收款人是否正确，但可以限制交错，避免已正确编写的事务相互破坏。

并发度高通常能减少闲等，却必须满足所选的隔离与恢复要求。各协议的“可串行化”“是否等待”“恢复性质”要分别判断。

<a id="ch07-s003"></a>

## 2. 【课程总结PPT重点基础】共享锁与排他锁


访问同一项数据前，事务可以先申请许可。只读与修改对他人的影响不同，因此用共享锁和排他锁分别表达这两种需求；兼容性表判断的是同一个对象上能否同时持有两种锁。

<a id="ch07-s004"></a>

### 2.1 锁是一种受系统管理的访问许可

**锁**表示事务取得对某数据对象的特定访问许可。它不会把数字本身改成“锁住”字符串。

- **共享锁 S**用于读；多个事务可以同时以 S 读同一对象。
- **排他锁 X**用于写；其他事务不能同时在同一对象上持有 S 或 X。

S 来自 Shared，X 表示 Exclusive；`lock-S(A)`表示申请 A 的共享锁，`lock-X(A)`申请排他锁，`unlock(A)`释放本事务持有的 A 锁。申请可能被授予，也可能等待；尚未获准就不能当成已经执行了受保护读写。

<a id="ch07-s005"></a>

### 2.2 兼容矩阵怎样读

**兼容**表示两个不同事务的锁是否可以同时在同一对象上存在。行是已持有的模式，列是新申请的模式。

| 已持有 \ 新申请 | S | X |
| --- | --- | --- |
| S | 可同时持有 | 等待 |
| X | 等待 | 等待 |

T1 在 A 上持 S，T2 也申请 S，二者可读；T2 申请 X 则等待，因为修改可能使 T1 正在读的状态改变。两个事务锁不同对象时不能仅凭这个同对象矩阵判断阻塞。

<a id="ch07-s006"></a>

### 2.3 一个从 500 正确算到 550 的时间线

| 顺序 | T1 存 100 | T2 取 50 | A |
| --- | --- | --- | --- |
| 1 | 获得 X(A) | — | 500 |
| 2 | 读 500，计算并写 600 | — | 600 |
| 3 | — | 申请 X(A)，等待 | 600 |
| 4 | 提交，释放 A | — | 600 |
| 5 | — | 获得 X(A)，读 600 | 600 |
| 6 | — | 写 550，提交，释放 | 550 |

`—`表示该栏此时没有动作，不是减法。T2 必须在拿到许可后重新按 600 计算，不能把等待前读出的旧 500 当成当前余额。

<a id="ch07-s007"></a>

## 3. 【课程总结PPT重点基础】只要求每次访问有锁为什么还不够


每次访问都有锁，只能说明单次操作受保护；如果业务做一半就释放锁，别人仍可能使用这段中间结果。下面用转账说明，锁保护的持续时间也会影响整个事务是否正确。

**独立背景**：A=500、B=300；T1 转 200，T2 统计总额。若 T1 写 A=300 后立即解锁 A，未处理 B 时 T2 先读 A=300，后来又在 B 更新前读 B=300，算得 600。

每次读写前都有适当锁，仍可能看到半笔业务。锁不仅要规定“读 S、写 X”，还要规定获取、释放的整体次序。两阶段锁就是一种保证冲突可串行化的次序规则；是否避免未提交读取，还需要它的严格变体。

<a id="ch07-s008"></a>

## 4. 【课程总结PPT重点知识点】基本两阶段锁 2PL


为了保证冲突可串行化，不能让事务随时拿锁、随时释放后又拿新锁。两阶段锁规定一次明确的转折：前面可以增加持锁，开始释放后就只能减少。这里的“两阶段”是持锁过程，不是业务恰好只有两步。

> **本节为课程总结PPT明确列出的重点知识点：两阶段锁。**

<a id="ch07-s009"></a>

### 4.1 两个阶段分界在哪里

2PL 是 Two-Phase Locking，两阶段锁：

1. **增长阶段**：可以获得新锁、升级已有锁，不能释放锁。
2. **收缩阶段**：可以释放锁、降级，不能再获得新锁或升级。

第一次释放或降级后就进入收缩阶段。不是“前一半语句加锁、后一半解锁”，也不是“两把锁”。

**锁点**是事务获得最后一把锁的时刻。锁点可能早于第一次释放锁，它们不是同一概念。按锁点先后可构造与基本 2PL 调度冲突等价的串行次序。

<a id="ch07-s010"></a>

### 4.2 同一业务怎样满足规则

独立事务 T1 修改 A 并读取 B：

| 顺序 | 动作 | 所处阶段与理由 |
| --- | --- | --- |
| 1 | 获得 X(A) | 增长 |
| 2 | 读写 A | 已有许可 |
| 3 | 获得 S(B) | 增长；这是最后获锁，锁点 |
| 4 | 读 B | 仍未释放 |
| 5 | 释放 A | 进入收缩 |
| 6 | 释放 B | 收缩 |
| 7 | 提交 | 结束 |

若第 5 步后再申请 C 的锁，就违反 2PL，即使 C 和其他人没有冲突也不符合该协议。

<a id="ch07-s011"></a>

### 4.3 基本 2PL 不能自动避免脏读

独立序列：T1 获 X(A)，写 A，释放 A；T2 获 S(A)，读该未提交值，提交并释放；T1 中止。两个事务各自都是先获得后释放，符合基本 2PL，但 T2 提交依赖失败 T1，可能不可恢复。

因此“保证冲突可串行化”与“保证可恢复、无级联或严格”是不同承诺。基本 2PL 也可能死锁，后文说明。

<a id="ch07-s012"></a>

## 5. 【课程PPT补充知识点，但属于 2PL 理解基础】锁转换：升级与降级


事务有时先读、后来决定修改，原有共享锁需要升级；也可能不再修改，只保留读许可。锁转换会改变权限强弱，同时必须遵守两阶段的先后规则。

<a id="ch07-s013"></a>

### 5.1 先读后写为什么要升级

T1 起初只读 A，持 S(A)，后来发现需要修改，申请 **S→X 升级**。若 T2 仍持 S(A)，T1 不能立即拿 X，必须等其他共享者退出。

两个事务都持 S(A)，又都请求升级 X，可能相互等待。升级不是靠“我已经有 S”就可无视其他事务。

<a id="ch07-s014"></a>

### 5.2 转换也受阶段限制

**降级 X→S**表示不再写，保留读许可。课程允许转换的基本 2PL 中，升级只能在增长阶段，降级只能在收缩阶段；降级后不能再升级或获取新锁。

在严格 2PL 中，X 必须一直保留到提交／中止，不能在此前通过降级变相提前释放写保护。这一限制仍要与两阶段的获取顺序一起满足。

<a id="ch07-s015"></a>

## 6. 【课程总结PPT重点知识点】严格与强严格两阶段锁


基本两阶段锁保证的串行化还不能解决所有失败处理问题。若写锁提前释放，别人仍可能读到未提交值。严格和强严格版本进一步规定哪些锁必须保持到事务结束，重点看“释放时刻”而不只记名称。

> **本节为课程总结PPT明确列出的重点知识点：严格两阶段锁与强两阶段锁。**

<a id="ch07-s016"></a>

### 6.1 严格 2PL：写锁一直保留到结束

**严格两阶段锁**在 2PL 规则上增加：所有 X 锁保留到提交或中止。S 锁可以在满足收缩规则时提前释放。

第 4.2 节例子若改为：获 X(A)、读写 A、获 S(B)、读 B、释放 B、提交并释放 A，就满足严格 2PL。释放 B 后不能再申请新锁；提前释放 S 不代表可重新增长。

X 不提前释放，其他事务便不能在 T1 结束前读或覆盖其写，生成严格调度，有利于恢复。严格 2PL 仍可能死锁。

<a id="ch07-s017"></a>

### 6.2 强严格／严密 2PL：读锁也保留到结束

**强严格两阶段锁**也称严密两阶段锁，英文课件为 rigorous 2PL，要求 S、X 全保留到提交／中止。同例获 X(A)、读写、获 S(B)、读 B，直到提交再全部释放。

它更容易按提交次序理解串行顺序，但持锁时间可能更长。“严格”在不同教材中偶有命名差异，本章按课程的 strict 只保留 X、rigorous 保留全部锁。

<a id="ch07-s018"></a>

### 6.3 三种协议逐项对照

| 协议 | 获锁／释锁遵守两阶段 | X 保留到结束 | S 保留到结束 | 可否死锁 |
| --- | --- | --- | --- | --- |
| 基本 2PL | 是 | 不要求 | 不要求 | 可以 |
| 严格 2PL | 是 | 要求 | 不一定 | 可以 |
| 强严格 2PL | 是 | 要求 | 要求 | 可以 |

“两阶段”主要管获取与释放次序；“严格变体”补充未提交写的保护。不要只记哪一种锁留到提交而忘了禁止释放后再获取。

<a id="ch07-s019"></a>

## 7. 【课程PPT补充知识点】锁管理器、队列与饥饿


锁请求并非一提交就能执行。系统需要记录谁持有锁、谁排队等待，以及何时唤醒请求；兼容只是能否共同持有的条件，实际是否立即获准还可能受公平排队规则影响。

**锁管理器**维护谁持有哪些锁、谁在等什么。**等待队列**记录尚不能授予的申请。

例如 T1 持 S(A)，T2 请求 X(A)开始等待，随后 T3 又请求 S(A)。即使 T3 与当前 S 兼容，如果不断允许新读者越过 T2，T2 的 X 可能一直得不到。**饥饿**就是某事务持续无法得到执行机会，不一定存在相互等待的环。

公平队列、避免新兼容请求无限越过旧请求等策略可以缓解饥饿。具体授予顺序属于实现选择；不能把“没有死锁”当成“一定没有长期等待”。

<a id="ch07-s020"></a>

## 8. 【课程PPT补充知识点】基于图的树协议


两阶段锁是一种通用办法。如果数据对象已有树状访问顺序，还可以利用父子关系约束拿锁。树形协议允许某些提前释放，但它有自己的访问规则，不能直接套用两阶段锁的判断。

**图协议**预先给数据项规定访问方向；**偏序**表示只规定部分对象必须先后，例如父节点先于子节点，两兄弟之间不必规定先后。树协议是课件中的一种具体结构规则，并非任意图都能直接照用。

<a id="ch07-s021"></a>

### 8.1 新场景和规则

假设可锁对象组织成树：根 R 的两个子节点 A、B；A 的子节点 A1。这里树表示访问规则的组织结构，不是事务优先图。

课程的树协议使用排他锁：

1. 第一个锁可在树上任意节点取得。
2. 后续锁某节点前必须持有它的父节点锁。
3. 可提前释放锁。
4. 同一事务释放过的节点不能再锁。

`父节点`是树中紧邻上一级对象；**子节点**是下一级。**后代**包括更下面任意层级。

<a id="ch07-s022"></a>

### 8.2 一个允许提前释放却不是 2PL 的例子

T1 获 A，获 A1，释放 A1，再获 R 违反树协议：R 不是在持有父节点条件下取得的后续锁。合规例可为先获 R，再获 A，释放 R，再获 A1（此时仍持 A），最后释放 A1、A。

这个合规例在释放 R 后又获得 A1，不满足 2PL，但满足树协议。树协议保证冲突可串行化且避免死锁，说明 2PL 不是唯一正确协议；其基本规则不自动保证可恢复／无级联，需要另加提交相关限制。按课件树的前提讨论，不能把任意循环对象图直接套用树协议。

<a id="ch07-s023"></a>

## 9. 【课程总结PPT重点基础】死锁：双方各等对方释放


等待通常只是稍后才能执行，但如果事务互相等对方释放锁，谁也走不下去。死锁分析首先要区分“已经获准的锁”与“仍在等待的请求”，被阻塞的访问并没有执行。

> **本节属于课程总结PPT“死锁检测与恢复”的必要概念基础。**

<a id="ch07-s024"></a>

### 9.1 两个账户上的完整等待时间线

T1、T2 都想修改 A 与 B。先不指定余额，死锁只依赖锁持有和请求关系。

| 顺序 | T1 | T2 | 当前锁 |
| --- | --- | --- | --- |
| 1 | 获 X(A) | — | A 由 T1 持有 |
| 2 | — | 获 X(B) | B 由 T2 持有 |
| 3 | 请求 X(B)，等待 | — | T2 未释放 B |
| 4 | — | 请求 X(A)，等待 | T1 未释放 A |

T1 不拿到 B 不继续，T2 不拿到 A 不继续；又都不能在当前业务中自然释放对方需要的锁，叫**死锁**。不是电脑完全无响应的定义，而是这一组事务循环阻塞。

<a id="ch07-s025"></a>

### 9.2 为什么两阶段锁也能死锁

两事务都在增长阶段申请新锁，没有提前释放，恰好都符合 2PL。协议保证的串行化性质与能否顺利取得锁不同。系统要防止这种状态或在发生后检测和恢复。

<a id="ch07-s026"></a>

## 10. 【课程PPT补充知识点】死锁预防：不让循环等待形成


死锁发生后可以检测并打破，也可以事先限制请求方式，使等待环无法形成。预防方法各有代价：提前拿齐锁可能降低并发，统一顺序要求事务遵守访问次序，时间戳方法则决定谁等待、谁重试。

<a id="ch07-s027"></a>

### 10.1 一次取得全部锁与统一顺序

**保守两阶段锁**要求开始前一次取得所有所需锁，拿不全就不持有一部分等待。好处是避免“各拿一部分”；代价是可能不知道未来需要哪些对象，且持锁较早影响并发。

**全局锁顺序**要求所有事务按同一对象顺序，例如都先 A 后 B。第 9 节 T2 就不能先拿 B 再要 A。必须连升级、动态访问等实际规则一起设计，不能仅在两行示例里口头说排序。

<a id="ch07-s028"></a>

### 10.2 wait-die：老的可以等，年轻的回滚

给每个事务分配唯一**时间戳** TS，数值越小越老，表示逻辑先后而非一定是秒数。设 TS(T1)=10，TS(T2)=20。

**wait-die**，常称等待—死亡，申请者遇到别人持锁时：

- 老申请者可等待年轻持有者；
- 年轻申请者遇到老持有者则回滚，不等待。

T1 要 T2 的锁，可等；T2 要 T1 的锁，T2 回滚。等待边只从老到年轻，不会形成环。重启通常保留原时间戳，减少永远“年轻”而反复被牺牲的风险。

<a id="ch07-s029"></a>

### 10.3 wound-wait：老的迫使年轻持有者回滚

**wound-wait**，常称伤害—等待：

- 老申请者遇到年轻持有者，使年轻持有者回滚；
- 年轻申请者遇到老持有者，年轻申请者等待。

T1 要 T2 的锁，T2 被回滚；T2 要 T1 的锁，T2 等待。等待边只从年轻到老，也不会成环。两算法比较的是“申请者”与“持有者”，不要把谁等待、谁回滚写反。

<a id="ch07-s030"></a>

### 10.4 超时不是死锁的证明

**超时**指等待超过设定时长便采取中止等措施，简单但可能把正常的长等待误判成死锁，也可能较晚发现真正死锁。它可以作为处理策略，不等价于图上已证实有环。

<a id="ch07-s031"></a>

## 11. 【课程总结PPT重点知识点】等待图检测死锁


要找死锁，必须把当前等待关系画出来。等待图中的箭头从“想继续却被挡住的事务”指向“占着所需锁的事务”；它记录当前阻塞，与上一章记录已发生冲突先后的优先图不同。

> **本节为课程总结PPT明确列出的重点知识点：死锁检测。**

<a id="ch07-s032"></a>

### 11.1 节点和边表示什么

**等待图**每事务一个节点。若 Ti 正等待 Tj 持有的不兼容锁，画 Ti→Tj；箭头指向阻塞它的人。

第 9 节的请求 X(B)给 T1→T2，请求 X(A)给 T2→T1，形成环。对课程的普通事务锁等待模型，等待图有环说明死锁；实际系统还可能涉及其他资源与特殊等待，需要用它自己的资源模型。

<a id="ch07-s033"></a>

### 11.2 与上一章优先图对照

| 图 | 边的依据 | 有环说明 |
| --- | --- | --- |
| 优先图 | 已发生的冲突操作先后 | 不冲突可串行化 |
| 等待图 | 当前阻塞的锁请求 | 事务锁死锁 |

同样画 T1→T2，含义不同。一个无等待的调度也可有优先图环；存在优先关系不表示事务正在等锁。

<a id="ch07-s034"></a>

### 11.3 检测时机

锁管理器可在新增等待边时或周期性检查是否有环。频繁检查开销大；太久不查会延长阻塞。检测后仍需选事务撤销，图本身不会释放锁。

<a id="ch07-s035"></a>

## 12. 【课程总结PPT重点知识点】死锁恢复与牺牲者


检测到环只是定位问题，还没有让系统继续运行。接下来需选择一个事务撤销，释放它的锁，让其他事务走下去；重试时也要防止某个事务反复被选中。

> **本节为课程总结PPT明确列出的重点知识点：死锁恢复。**

<a id="ch07-s036"></a>

### 12.1 完整恢复过程

**牺牲者**是系统选择回滚以破环的事务，不是永久删除用户。对第 9 节选择 T2：

1. 中止 T2，撤销它已做的修改；在安全的撤销顺序下释放它的锁。
2. T2 不再持有 B，T1 的 X(B)可授予。
3. T1 完成并提交，释放 A、B。
4. 根据应用重试策略，T2 从一致状态重新执行。

撤销与释放要配合恢复协议，不能先随意放出未恢复数据再让别人读取。若采用部分回滚，也必须确实打破环并维护锁与修改的一致规则。

<a id="ch07-s037"></a>

### 12.2 如何选择与避免总牺牲同一人

可考虑已执行工作量、已写数据量、回滚代价、持锁数量、已回滚次数等。“成本低”不等于永远牺牲最年轻或最短事务，否则同一事务可能饥饿。系统可把重试次数加入选择依据。

<a id="ch07-s038"></a>

## 13. 【课程PPT补充知识点】锁粒度：锁多大范围


锁可以覆盖一行、一页或整张表。范围大时锁数量少，却更容易挡住无关访问；范围小时并发更灵活，但管理开销增加。因此，“锁住多大范围”与“授予读还是写权限”是两个问题。

**粒度**是锁覆盖对象的大小，和锁模式 S／X 是两个维度。典型层次为数据库→表→数据页→记录；页是 DBMS 管理的一块存储区域，含若干记录。

**独立订单场景**：T1 改订单 O1，T2 改 O2，二者在同一订单表、不同记录。

- 若都要求表级 X，会相互阻塞。
- 若只在不同记录上持 X，可并发处理。
- 若事务改全表上百万行，逐行维护锁开销又较大。

细粒度通常提高并发机会，粗粒度减少锁管理数量。**锁升级**是实现中把很多细锁合并为较粗锁以控制开销，不能与 S→X 的模式升级混淆。

<a id="ch07-s039"></a>

## 14. 【课程PPT补充知识点，较重要】意向锁：在上层声明下层的计划


如果有人锁了表内的一行，另一个人直接请求整张表的锁，系统需要快速知道下层有人使用。意向锁在祖先层留下这种提示；它本身并不授予每一行的读写权限。

<a id="ch07-s040"></a>

### 14.1 为什么只锁一行还要通知表层

T1 在订单 O1 上持 X；T2 想一次锁整张订单表 S。若系统每次必须检查表内每条记录的锁，代价很大。**意向锁**在祖先对象上记录“下层有或将有哪种锁”，帮助快速判断粗锁能否授予。

**祖先**指路径中的上层节点，包括父节点以及更上层。意向锁不是独立替代叶子记录读写许可的办法。

<a id="ch07-s041"></a>

### 14.2 IS、IX、SIX 分别承诺什么

| 模式 | 完整意思 | 本订单场景用途 |
| --- | --- | --- |
| IS | 意向共享 | 准备在下层读某些记录 |
| IX | 意向排他 | 准备在下层写某些记录 |
| SIX | 当前对象共享，同时下层意向排他 | 要读全表，并写其中某几行 |

IS 中 S 指共享；IX 中 X 指排他；SIX 可理解为 S 与 IX 合在一起。要只改 O1，沿数据库、表等路径放 IX，再在 O1 放 X。另一个只改 O2 的事务也可在同表放 IX，它们并不因此冲突；各行上的 X 仍需分别检查。

<a id="ch07-s042"></a>

### 14.3 同一节点上的完整兼容矩阵

行是别人已持有，列是新申请；“是”表示模式允许同时存在，不承诺队列策略一定立刻授予。

| 已持有 \ 新申请 | IS | IX | S | SIX | X |
| --- | --- | --- | --- | --- | --- |
| IS | 是 | 是 | 是 | 是 | 否 |
| IX | 是 | 是 | 否 | 否 | 否 |
| S | 是 | 否 | 是 | 否 | 否 |
| SIX | 是 | 否 | 否 | 否 | 否 |
| X | 否 | 否 | 否 | 否 | 否 |

IX 与 S 不兼容，因为一方声明要改部分行，另一方要共享读整个范围。IX 与 IX 兼容，只表示双方都可能改不同下层对象；若最终都改 O1，叶子 X 仍冲突。

SIX 与 IS 兼容：全表读取者允许另一个事务在下层读未被 X 锁住的行；但后者真读被锁 O1 时，仍会在 O1 上等。表层兼容不取消下层检查。

<a id="ch07-s043"></a>

### 14.4 沿层次加锁与释放

课程规则：先锁根；子节点要 S 或 IS，父节点需有 IS 或合适更强模式；子节点要 X、IX、SIX，父节点需有 IX 或 SIX。从上往下加锁，从下往上释放，并满足所选 2PL。

若祖先已有覆盖整个子树的 X，通常无需机械为每个后代再加 X；具体实现及已有较强许可的处理由产品确定。本章按课程标准路径规则手算。

<a id="ch07-s044"></a>

## 15. 【课程PPT补充知识点】时间戳排序协议


锁可能让事务等待。时间戳排序改为先给事务规定逻辑顺序，再检查每次读写是否仍符合这个顺序；不合格时通常撤销重试。时间戳是用于排序的标记，不是某项数据的数值。

<a id="ch07-s045"></a>

### 15.1 三个数字先解释清楚

事务 TS 越小，计划串行次序越早。每个数据项 Q 保存：

- `RTS(Q)`：成功读取 Q 的事务中最大时间戳；
- `WTS(Q)`：成功写入 Q 的事务中最大时间戳。

RTS 是读时间戳，WTS 是写时间戳；初始可设 0。它们记录已发生操作在逻辑顺序中的位置，不是读取次数、当前余额或等待时间。

**目标**：让冲突操作符合 TS 的先后。违反已确立的顺序时回滚，基本协议不靠锁等待，因此不形成这种锁死锁，但可能反复回滚，也不自动保证恢复性质。

<a id="ch07-s046"></a>

### 15.2 读规则与数字例


**课件符号核对。** ch15.pdf 第 32 页的两项分别印为 TS≤WTS 时拒绝、TS≥WTS 时允许，等号同时落入两项，存在边界冲突。本文按“TS<WTS 拒绝，否则允许”的规则解释：等号可能表示事务读自己刚写的值，不应仅因同一时间戳而拒绝。这里明确修正教材页的符号冲突，不把两项原样当作一致规则；若考试要求逐字使用课件，应向任课教师确认这一等号。

T 请求读 Q：

- 若 `TS(T)<WTS(Q)`，回滚：较新事务已经写过，老事务不能读到按顺序应在它之后才写的值。
- 否则允许，更新 `RTS(Q)=max(RTS(Q),TS(T))`。max 表示取两个数中较大的一个。

独立初始 RTS=WTS=0。T2 的 TS=20，先写 Q，使 WTS=20；T1 的 TS=10，后来想读，10<20，回滚。另一个 TS=30 的 T3 读，30≥20，可读，RTS 变 30。

<a id="ch07-s047"></a>

### 15.3 写规则与两个不同失败原因

T 请求写 Q：

1. 若 TS(T)<RTS(Q)，回滚：较新的读者已读到旧值，插入一个本应更早的写会使读来源不符串行次序。
2. 否则若 TS(T)<WTS(Q)，基本协议回滚：已有较新的写。
3. 否则允许写，WTS 更新为 TS(T)。

| 独立场景 | RTS | WTS | 申请者 TS | 结果与依据 |
| --- | --- | --- | --- | --- |
| 较新事务先读 | 20 | 0 | 10 | 10<20，因读顺序回滚 |
| 较新事务先写 | 0 | 20 | 10 | 10<20，因写顺序回滚 |
| 顺序可接受 | 10 | 20 | 30 | 30 不小于两者，可写，WTS=30 |

两检查不应只挑一个。数值只是教学逻辑时钟，未指定产品实际实现。

<a id="ch07-s048"></a>

## 16. 【课程PPT补充知识点】Thomas 写规则


较老事务迟来的写入，有时已被较新写入盖过，继续写反而会把数据退回旧状态。Thomas 写规则允许在特定条件下忽略这个过时写入，但必须先检查是否已有较新事务读过；两个条件不能交换检查顺序。

**背景**：时间戳 20 的事务已经写了 Q，TS=10 的老事务后来请求写；若这次老写的效果在计划串行顺序里反正被新写覆盖，可能可以忽略。

Thomas 写规则仍先检查 TS<RTS，成立则回滚；只有通过这个检查后，若 TS<WTS，才把这次写视为**过时写**而忽略，不改值和 WTS，事务可继续。

| RTS | WTS | TS | Thomas 处理 |
| --- | --- | --- | --- |
| 0 | 20 | 10 | 读检查通过，写过时，忽略 |
| 30 | 20 | 10 | 先因 10<30 回滚，不能直接忽略 |
| 10 | 20 | 30 | 两检查通过，正常写 |

**忽略**不是提交所有业务，也不是回滚整个事务，只是这次写不再落入当前值。该规则可接受某些视图可串行化但不冲突可串行化的调度，不能说与基本时间戳排序接受范围完全相同。



<a id="ch07-s049"></a>

## 17. 【课程PPT补充知识点】基于验证的乐观并发控制


冲突不频繁时，可以先在私有工作区尝试执行，提交前再检查是否与其他事务冲突。验证通过才把修改写入；因此“已经计算好了”与“获准提交修改”仍是两件事。

<a id="ch07-s050"></a>

### 17.1 先尝试，提交前检查

**乐观**表示假设冲突不多，先做计算，最后验证；不表示无条件相信结果。三个阶段：

1. **读阶段**：读数据库，把要改的新值放在事务自己的暂存区域，尚不对其他事务发布。
2. **验证阶段**：检查它与其他事务是否有无法接受的冲突。
3. **写阶段**：通过后发布修改；失败则丢弃暂存结果并重试。

`RS(T)`为事务的**读集**，即它读取过哪些数据项；`WS(T)`为**写集**，即计划修改哪些数据项。RS、WS 是集合，不是金额。不同实现还要覆盖条件查询范围，不能只记录实际读到的现有行而漏掉幻读风险。

<a id="ch07-s051"></a>

### 17.2 一个通过和一个失败的完整场景

独立账户 A=500、B=300。T1 想存入 100，读 A，暂存 A=600；T2 想取出 50，读 A=500，暂存 A=450。T1 验证、写 A=600并完成。T2 验证时发现较早 T1 的写集 {A} 与自己的读集 {A} 相交：它的计算基于被改变的旧状态，不能照常发布；需要回滚重试。重试若读到已提交的 600，再减 50，才得到正确 550。

另一个独立场景中，T2 改为只给 B 存入 50，从 300 算到 350。它只读写 B，则 T1 的 {A} 与它的 {B} 无交集，可能通过并发验证，最终 A=600、B=350。是否通过还需对所有相关事务检查，不仅对这一对。

<a id="ch07-s052"></a>

### 17.3 课件验证条件逐项解释

按验证时刻给事务排串行次序。设 Ti 比 Tj 更早验证。`Start(T)`是读阶段开始，`Validation(T)`是验证开始，`Finish(T)`是写阶段结束。课件第 42—44 页为简单起见，假设验证和写阶段作为整体串行执行。每个较早 Ti 与当前 Tj 需满足以下至少一项：

| 条件 | 为什么可接受 |
| --- | --- |
| Finish(Ti)<Start(Tj) | Ti 已完成，Tj 从新状态开始 |
| Start(Tj)<Finish(Ti)<Validation(Tj)，且 WS(Ti)∩RS(Tj)=空集 | 写阶段虽在 Tj 读取期间结束，但没改 Tj 用过的数据 |

`∩`是交集，`∪`是并集，空集表示没有共同数据项。表中不等号描述阶段相对次序，边界同一时刻如何排序由实现定义。

例如 Ti 从时刻 1 开始、4 验证、5 完成，Tj 从 2 开始、6 验证：属于第二种时间关系。若 WS(Ti)={A}、RS(Tj)={B}，交集空，可通过这一对检查；若 RS(Tj)={A}，失败。在这套课件假设下，不让另一个事务在较早事务写阶段尚未结束时并发进入验证／发布；放宽这一假设需要扩展协议，不直接套用这两项条件。

这是课程的验证模型，不是所有标为“乐观锁”的软件都完整实现这套协议；单行版本号检查也不能自动覆盖跨行约束。

<a id="ch07-s053"></a>

## 18. 【课程PPT补充知识点，较重要】MVCC：一项数据保留多个版本


读者如果能使用合适的旧版本，就不必每次都等待正在产生的新版本。多版本方法解决的是保留哪些值、怎样选择读取版本、何时发布新版本；是否保证串行化还要看具体规则。

<a id="ch07-s054"></a>

### 18.1 为什么保留历史值

**多版本并发控制**简称 MVCC，Multi-Version Concurrency Control。数据修改后不立即抹掉所有旧值，读取者按规则选择合适版本，减少读写互相等待。

独立账户 Q 的历史如下，每行一个已提交版本：

| 版本写时间戳 WTS | 值 |
| --- | --- |
| 0 | 500 |
| 20 | 600 |

按快照时间 10 读取，选不晚于 10 的最新版本，得到 500；按时间 30，得到 600。“最新”是相对于该次读取的可见范围，不是总读物理上最后写入的值。快照是某个逻辑时点允许看到的数据状态，具体按事务或按语句建立取决于隔离级别与实现。

<a id="ch07-s055"></a>

### 18.2 多版本时间戳排序怎样手算

课程的多版本时间戳方法为每个版本 Qk 保存写时间戳 WTS(Qk)与最大读时间戳 RTS(Qk)。k 是版本编号。事务 T 先选择 WTS 不大于 TS(T)的最新版本；读取后提升该版本 RTS。

用教学已提交历史：旧版本 WTS=0、RTS=0、值 500；新版本 WTS=20、RTS=20、值 600。TS=10 的事务读旧版本，把旧版 RTS 改为 10。

随后若 TS=5 的老事务想写，它选旧版，但 5<旧版 RTS 10，说明逻辑上较新的读者已读到旧版；再补一个更早写会破坏读取顺序，因此回滚。TS=15 的事务计划把选到的旧值 500 加 50，得到 550；读旧版后把其 RTS 提到 15，再写时 15≥15，可创建 WTS=15、值 550 的新版本，旧版仍保留。按 TS=16 读取时选 15 版，按 TS=30 读取时选 20 版。

如果同一事务继续写自己的同时间戳版本，可以更新该版本；具体发布、未提交版本可见性和回收规则取决于协议。**基本多版本时间戳规则本身并不自动保证所有读取只读已提交数据**；上例刻意使用已提交历史以讲版本选择，实现还须安排提交与恢复规则。

<a id="ch07-s056"></a>

### 18.3 课件的多版本两阶段锁：读者与更新者分工

课件 `ch15.pdf`第 49—50 页采用明确的两类事务：

- **只读事务**开始时读取提交计数器 ts-counter，作为自己的快照时间，不更新数据。
- **更新事务**读时获 S、写时获 X，全部锁保留到结束，即强严格 2PL。

ts-counter 是系统用来编号提交次序的数字，不是余额。更新先创建新版本，暂用 `∞`（无穷大）作“尚不可被普通有限时间戳快照选到”的标记；提交时把新版本时间戳改成计数器加 1，再推进计数器，并按协议结束和释放锁。实现需要协调这些动作，不能让读者选到发布一半的状态。

**完整小例**：计数器 5，Q 的已提交版本时间戳 5、值 500。只读 T1 开始，快照为 5。更新 T2 获 X(Q)，写暂定版本 600；T1 仍可按版本规则读旧版 500。T2 提交，新版标为 6，计数器变 6。此后开始的只读 T3 快照 6，读 600；T1 仍读 500。更新者之间遵守强严格 2PL，课程这一具体方案生成可串行化调度。

这比只说“MVCC 用历史值”多了更新和发布规则。其他 MVCC 产品未必采用同一方案，不能把这一保证推广给所有快照隔离。

<a id="ch07-s057"></a>

### 18.4 多版本的成本

保存版本消耗空间；长期读取可能使旧版迟迟不能回收。**版本回收**是数据库内部丢弃已无读取者需要的历史记录，教学讨论不涉及本电脑文件清理。

## 19. 【课程PPT补充知识点，较重要】快照隔离与写偏差


两人各改不同记录，未必没有冲突：他们可能依据同一份旧快照作出决定，合起来破坏跨记录的业务规则。下面的值班例子说明，只检查是否写同一行不足以保证串行化。

<a id="ch07-s059"></a>

### 19.1 两位医生共同承担一个约束

**独立业务**：值班表 `doctor(DID,on_duty)`每行一位医生；DID 医生编号，on_duty 是否值班。开始 D1、D2 都为“是”，规则要求至少一人值班。

**快照隔离**通常让事务读其开始时的已提交快照，并防止并发事务在同一数据对象上发生某类写写冲突；精确机制按实现确定。

| 顺序 | T1（D1 请假） | T2（D2 请假） |
| --- | --- | --- |
| 1 | 看到两人都在岗 | — |
| 2 | — | 也看到两人都在岗 |
| 3 | 因为 D2 在岗，改 D1 为否 | — |
| 4 | — | 因为 D1 在岗，改 D2 为否 |
| 5 | 提交 | 提交 |

它们改不同的行，可能没有同一行写写冲突；但最终 D1 否、D2 否，违反“至少一人”。这种各自基于快照做合法判断、共同破坏跨行规则的现象叫**写偏差**。

<a id="ch07-s060"></a>

### 19.2 为什么不是任一串行次序的结果

若 T1 先完整提交，T2 后读取，会看到仅 D2 在岗，不能再让 D2 请假；交换同理。因此这次双双成功结果不是正确串行执行的结果。

可采用能检测这种依赖的可串行化隔离，或把共同约束关联到统一需要锁／更新的对象等办法。不能只给各医生自己那行加锁就说已解决，因为读的是共同条件。MVCC 和稳定快照都不自动等于可串行化。

<a id="ch07-s061"></a>

## 20. 【课程PPT补充知识点，较重要】幻读、谓词锁与范围锁


查询条件覆盖的不只是现有行。别人新增一行后，它也可能突然符合条件，形成幻读。因此保护“查到的那些行”与保护“整个条件范围”效果不同。

<a id="ch07-s062"></a>

### 20.1 只锁现有记录为何拦不住新记录

独立选课表初始 S1 C1。T1 查所有 C1 选课并锁住 S1 C1；T2 插入 S2 C1，它是新行，并不是已锁住的那条旧记录。T1 再查可能从一人变两人。

**谓词**是筛选条件，例如 CID='C1'。**谓词锁**保护满足该条件的数据范围与潜在加入者；**范围锁**利用索引等方式保护一段键值范围。目的不仅是锁住现有行，还要协调可能使查询结果集合改变的插入、删除、更新。

<a id="ch07-s063"></a>

### 20.2 一个数字区间的插入例子

独立表 `item(item_id,price)`每行一件物品，item_id 编号、price 价格。已有价格 10、20、40，T1 查 `price>=20 AND price<40`，目前只有价格 20 的记录。T2 插入价格 30，如果只锁现有 20 行，不会直接冲突；保护 [20,40) 范围则能发现它会加入本次查询。

方括号 `[`表示包含 20，圆括号 `)`表示不含 40；这是数学区间写法，不是 SQL 的一种新类型。

<a id="ch07-s064"></a>

### 20.3 快照不变与可串行化仍须分开

事务级快照可能让 T1 再读时仍看旧集合，表面上没有幻影行；但它和其他事务的整体决策仍可能写偏差。防止可见幻读与保证全部操作可串行化不是等价命题。

<a id="ch07-s065"></a>

## 21. 【课程PPT补充知识点】SQL 隔离级别怎样读


应用通常通过隔离级别选择可接受的并发影响。级别名称给出一组最低行为要求，但产品实现可能更强、也可能采用不同机制；要把标准现象表与具体数据库说明分开理解。

下表是标准常用现象表的最低保证。“可能”表示级别允许，并不表示每个产品每次都发生；具体实现可以更强。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED，读未提交 | 可能 | 可能 | 可能 |
| READ COMMITTED，读已提交 | 不允许 | 可能 | 可能 |
| REPEATABLE READ，可重复读 | 不允许 | 不允许 | 可能 |
| SERIALIZABLE，可串行化 | 不允许 | 不允许 | 不允许 |

仅这三类现象表不是全部隔离语义。例如快照隔离的写偏差不被“本事务重复读是否变化”完整概括。某产品 REPEATABLE READ 可能使用快照而避免某些幻读，另一些使用锁；产品的同名级别不能据名称推断所有行为。

课程风格设置：
```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```
`SET TRANSACTION`设置事务选项，`ISOLATION LEVEL`指定隔离级别。必须在产品允许的事务阶段设置；实际开始事务语法、失败重试和生效范围需按 DBMS 核实。SERIALIZABLE 也可能以检测后中止冲突事务的方式保证结果，不等于所有事务都事先逐个排队。

<a id="ch07-s066"></a>

## 22. 【课程PPT补充知识点】索引并发：逻辑保护与结构保护


访问表中数据常要经过索引。事务锁保护业务层面的访问顺序，索引内部还需要短时间保护页结构，防止并发拆分或修改时把结构弄坏；两种保护的对象和持续时间不同。

<a id="ch07-s067"></a>

### 22.1 B+ 树中的短暂保护

**B+ 树**是按搜索键组织的树形索引，内部节点帮助定位，叶节点存键和对应记录位置。查询价格 30 可能从根沿若干节点到叶节点。插入可能使节点**分裂**，即把过满节点分成多个节点并调整父节点。

**闩锁 latch**是短暂保护内存中页或索引结构一致性的同步工具；**事务锁**主要保护业务隔离，可跨较长时间持有。不要把它们都叫“锁”后就机械套用提交前保留的相同规则。

**锁耦合／闩锁耦合**指向下移动时先保护下一个节点，再释放不再需要的上一个节点，避免路径在读取中被修改；具体索引算法有不同策略。这里解释用途，不承诺所有 B+ 树实现都按同一耦合方式。

<a id="ch07-s068"></a>

### 22.2 next-key 的直观范围

**next-key 锁**常译临键锁，是某些实现把索引记录及邻接间隙一起保护的方式。**间隙**指两个相邻键之间可插新键的位置。

以索引已有键 10、20、40 为例，常见示意中记录 20 的 next-key 覆盖 (10,20]：保护 20 及其前面的间隙，因此可阻止插入 15。记录锁只护 20，不同；间隙锁关注可插位置，也不同。

具体边界、相等条件与锁范围是产品实现事项，不把此示意当作标准 SQL 强制行为。查询 [20,40) 实际锁到哪里，还需看索引、访问路径和具体协议。

## 23. 【课程PPT补充知识点】用同一组问题比较协议

| 方法 | 主要控制什么 | 是否可能等待锁 | 需要留意什么 |
| --- | --- | --- | --- |
| 基本 2PL | 获锁与释放次序 | 是 | 可死锁，恢复性质需补充 |
| 严格／强严格 2PL | 两阶段加未结束事务保护 | 是 | 仍可死锁 |
| 树协议 | 父子访问顺序 | 是 | 可提前释放，恢复需额外规则 |
| 基本时间戳 | 冲突服从 TS 次序 | 不靠锁等待 | 回滚、恢复性质 |
| 验证方法 | 发布前冲突检查 | 视实现 | 暂存、读写集和重试 |
| MVCC | 读取合适历史版本 | 视写协议 | 版本维护、写冲突、写偏差 |

对“是否保证可串行化”，必须明确协议变体与约束。标准 2PL、课程树协议、基本时间戳及完整验证协议有相应保证；“使用多版本”这个名字本身不足以给结论。

## 26. 自拟自测题与逐步答案

以下五题为自拟题。

<a id="ch07-s073"></a>

### 26.1 加锁顺序合不合法？

**给定 T1**：获 S(A)，读 A，释放 A，获 X(B)，写 B，提交。A、B 为不同数据项。

**步骤**：首次释放 A 已进入收缩阶段；后来获 X(B)是新锁，所以违反 2PL。数据项不同不取消阶段规则。

**修改**：先获 S(A)、读 A、获 X(B)、写 B，再释放锁。若要严格 2PL，X(B)还须保留到提交；若要强严格，S(A)也保留。**结论**：原序列不合法，调整次序后仍须按变体检查保留要求。

<a id="ch07-s074"></a>

### 26.2 等待图如何检测与破环？

**背景**：T1 持 X(A)要 B，T2 持 X(B)要 C，T3 持 X(C)要 A。

**步骤**：三条边为 T1→T2、T2→T3、T3→T1，有环，死锁。若选 T3 回滚，撤销它的修改并释放 C，T2 可取得 C并完成；T2 结束释放 B，T1 再完成。

**结论**：必须回滚至少一个能破环的事务或使用等效安全恢复手段；仅画图或喊“等待更久”不会自动解除死锁。T3 重试应采用避免长期饥饿的策略。

<a id="ch07-s075"></a>

### 26.3 意向锁怎样沿路径放？

**背景**：T1 只想修改订单表内 O1，T2 只想修改 O2，两行不同；省略页层次，路径为数据库→订单表→记录。

**步骤**：各自在数据库与表申请 IX，再在自己的记录申请 X。两个表层 IX 兼容，不同记录 X 不直接冲突。若 T3 要整张表 S，会与已有 IX 不兼容而等待。

**结论**：意向锁让细锁与粗锁相互协调；它不是禁止所有同表并发修改。

<a id="ch07-s076"></a>

### 26.4 时间戳旧写应忽略还是回滚？

**给定**：Q 的 RTS=25、WTS=20，申请事务 TS=10；问 Thomas 处理。

**步骤**：先检查 10<25，说明较新读者已经读过；必须回滚，不能因为 10<20 就直接忽略。若另一个独立情况 RTS=5、WTS=20，则读检查通过，写已过时，忽略此次写。

**结论**：检查顺序决定答案。忽略只跳过一次写，不是整体提交。

<a id="ch07-s077"></a>

### 26.5 医生各改自己一行为什么还会错？

**背景**：第 19 节两人都在岗，至少一人值班；各事务看到原快照，只改自己为不在岗。

**步骤**：写集分别 {D1}、{D2}，单纯同一行写冲突检测不会碰撞；但 T1 依赖 D2 保持在岗，T2 依赖 D1 保持在岗，共同提交让两人都不在岗。串行次序下第二人应被规则拒绝。

**结论**：写偏差；需要保护共同约束的合适串行化机制或共同协调对象，稳定快照与分开两把行锁并不足以自动解决。

## 28. 请求、获准、执行：检查协议时不可省略的三步

事务说“我要读 X”，不表示读已经发生。先申请所需锁，锁管理器按兼容性和队列规则判断是否获准；获准后才能执行受保护的访问。等待期间，程序不能把尚未执行的读取当成已经拿到了值。

| 时刻 | T1 | T2 | 对 X 的实际影响 |
| --- | --- | --- | --- |
| 1 | 获得 X(X)，写入 X=300，尚未提交 | 尚未访问 | 产生未提交修改 |
| 2 | 继续持有写锁 | 请求 S(X)，因不兼容而等待 | T2 没有读到 300 |
| 3 | 提交，释放写锁 | 等待请求可以被重新检查 | 提交结果确认为 300 |
| 4 | 已结束 | 获准 S(X)，然后读取 | T2 此时读到已提交的 300 |

上表采用严格两阶段锁，假定没有更早的排队请求。若 T1 在第 3 步中止，撤销后再释放锁，T2 获准时读到的应是恢复后的值。不能把“请求锁”直接记成 r2(X)，否则会凭空制造一次脏读。

**判断协议要逐条查规则。** 两阶段锁先检查有没有在释放后再拿锁；严格版本再检查写锁是否保持到结束；强严格版本还要检查共享锁。共享锁、排他锁回答权限，行锁、表锁回答范围，二者可以组合，例如某行上的共享锁。

**看到等待，也不能立刻说死锁。** 只有等待关系成环，才是本章单实例锁模型下的死锁；单向等待可能随着持锁者提交而结束。等待图检查当前阻塞，优先图检查已执行操作的冲突次序，两者的箭头依据不可混用。

**看到旧版本，也不能立刻说可串行化。** MVCC 是版本组织与访问机制的统称；快照隔离、版本时间戳和课件的多版本两阶段锁各有额外规则。先说清采用哪种规则，再分析写偏差、提交条件与串行化保证。

## 29. 本章概念与方法速查

本表帮助回想用途与使用条件；完整例子和推导请回到正文。名称可能是对象、性质、运算或协议，不是全在同一层次。HTML 版在本节使用选择菜单，选中后显示对应解释，不再重复铺开长表。

| 名称 | 类别 | 解决什么问题 | 基本形式或读法 | 注意点与正文 |
| --- | --- | --- | --- | --- |
| S / X 锁 | 访问权限 | S 允许读取，X 允许读取和修改并排斥他人 | 同一对象上 S/S 兼容，其余含 X 的组合不兼容 | 锁申请不等于锁已授予 [回正文](#ch07-s003) |
| 基本两阶段锁 | 加锁协议 | 把持锁过程分成增长和收缩 | 释放或降级后，不得再拿新锁或升级 | 保证冲突可串行化，不自动保证无级联 [回正文](#ch07-s008) |
| 锁升级 / 降级 | 权限变化 | 根据后续访问改变同一对象的锁模式 | S→X 属增长；X→S 属收缩 | 降级后不能再升级或拿新锁，才符合两阶段 [回正文](#ch07-s012) |
| 严格两阶段锁 | 释放规则 | 未结束写入不被别人读取或覆盖 | 遵守两阶段，并把全部 X 锁保持到结束 | S 锁可提前释放，但随后不能再增长 [回正文](#ch07-s015) |
| 强严格两阶段锁 | 释放规则 | 把全部读写锁都保持到结束 | S、X 锁均保留到提交或中止 | 课件称 rigorous；不同资料命名可能不同 [回正文](#ch07-s017) |
| 锁管理与队列 | 系统执行 | 管理持有者、等待者与唤醒 | 申请 → 兼容和排队检查 → 授予 → 访问 | 兼容不承诺任何队列实现立即放行 [回正文](#ch07-s019) |
| 树形协议 | 访问顺序协议 | 利用树结构限制后续加锁 | 首次任意；后续先持父锁；可早释放；已释放不能重锁 | 死锁自由不代表自动提供恢复性质 [回正文](#ch07-s020) |
| 死锁 | 当前阻塞状态 | 互相等待导致都无法继续 | 确认请求尚未获准，再构造等待环 | 正常单向等待不是死锁 [回正文](#ch07-s023) |
| 保守两阶段锁 | 死锁预防 | 开工前拿齐所需锁 | 全部所需锁能获准才开始 | 需要提前知道所需对象，可能降低并发 [回正文](#ch07-s027) |
| 统一加锁顺序 | 死锁预防 | 让所有事务按同一对象顺序拿锁 | 如统一 A 在 B 前 | 排序规则必须被各事务一致遵守 [回正文](#ch07-s027) |
| wait-die | 时间戳预防 | 年老请求者可等，年轻请求者撤销 | 请求者比持锁者老则等，否则回滚 | 重启保留原时间戳，减少反复挨饿 [回正文](#ch07-s028) |
| wound-wait | 时间戳预防 | 年老请求者撤销年轻持锁者，年轻请求者可等 | 老请求年轻：使年轻回滚；年轻请求老：等待 | 释放前需完成必要撤销处理 [回正文](#ch07-s029) |
| 等待图 | 死锁检测 | 记录谁被谁阻塞 | 等待者 → 挡住它的持锁者 | 不能与优先图箭头依据混用 [回正文](#ch07-s031) |
| 死锁恢复 | 解除阻塞 | 选择牺牲者并撤销释放锁 | 选事务 → 回滚 → 释放 → 唤醒 → 合理重试 | 牺牲者选择要兼顾代价与公平 [回正文](#ch07-s035) |
| 锁粒度 | 保护范围 | 在并发程度与管理开销间取舍 | 行、页、表等对象范围 | 锁升级为表级锁不等于 S→X 模式升级 [回正文](#ch07-s038) |
| IS / IX / SIX | 祖先层提示 | 提示下层存在读写锁需求 | 读行：祖先 IS、行 S；写行：祖先 IX、行 X | 意向锁不代替叶子层实际权限 [回正文](#ch07-s039) |
| TS / RTS / WTS | 时间戳数据 | 分别记录事务顺序、最大读标记和最大写标记 | 读：TS≥WTS 才可；写：依次查 RTS、WTS | 这些数值是顺序标记，不是数据值 [回正文](#ch07-s044) |
| Thomas 写规则 | 过时写处理 | 在安全条件下忽略迟来的旧写 | 先查 TS<RTS：回滚；否则 TS<WTS：忽略本次写 | 忽略一条写不等于事务整体已提交 [回正文](#ch07-s048) |
| 验证协议 | 提交前检查 | 先尝试，再检查能否发布修改 | 读与计算 → 验证 → 写入 | 课件例采用串行验证与写阶段，条件不能随意推广 [回正文](#ch07-s049) |
| MVCC | 版本机制 | 按规则选择合适历史版本 | 先确定具体协议，再决定可见与写入规则 | 多版本不自动等于可串行化 [回正文](#ch07-s053) |
| 快照隔离与写偏差 | 并发异常 | 识别不同记录修改共同破坏规则 | 检查共同读取的条件与各自写入 | 稳定快照不等于串行化 [回正文](#ch07-s058) |
| 谓词锁 / 范围锁 | 条件范围保护 | 防止新行进入查询条件而形成幻读 | 保护符合条件的范围，而非仅当前已存在行 | 具体数据库使用机制和边界须另核实 [回正文](#ch07-s061) |
| 隔离级别 | 应用选择 | 指定可接受的并发影响范围 | 结合标准现象表与具体产品规则 | 不能仅凭名称推断产品全部行为 [回正文](#ch07-s065) |
| latch / 索引锁 | 结构与访问保护 | 区分短时页结构保护和事务访问限制 | 结构操作用短时保护；范围访问按事务规则保护 | next-key 示例依具体实现，不是所有 SQL 的统一规则 [回正文](#ch07-s066) |
