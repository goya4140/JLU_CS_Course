## 1. 【课程总结PPT重点知识点】从一笔转账理解事务与读写

> **本节为课程总结PPT明确列出的重点知识点：事务概念与模型。**

<a id="ch06-s003"></a>

### 1.1 先把业务与数据说清楚

银行甲账户 A 有 500 元，乙账户 B 有 300 元，甲向乙转账 200 元，不收手续费。教学表 `account(account_id,owner,balance)`每行一个账户；account_id 账户号，owner 所有者，balance 余额。

| account_id | owner | balance |
| --- | --- | --- |
| A | 甲 | 500 |
| B | 乙 | 300 |

这两个账户总额为 800，转账后应仍为 800。这里 A、B 是数据项代号，不是第 05 章属性集合。

**事务**是作为整体处理的一组操作。给这笔转账起名 T1，T 表示事务，1 是编号。为了理解，假设它按下列时间线执行：

| 步骤 | 做什么 | 程序暂存值 | 数据库中 A、B |
| --- | --- | --- | --- |
| 1 | read(A)，读甲余额 | a=500 | 500、300 |
| 2 | a=a−200 | a=300 | 500、300 |
| 3 | write(A)，写回甲余额 | a=300 | 300、300 |
| 4 | read(B)，读乙余额 | b=300 | 300、300 |
| 5 | b=b+200 | b=500 | 300、300 |
| 6 | write(B)，写回乙余额 | b=500 | 300、500 |
| 7 | commit，提交 | 事务成功结束 | 300、500 |

`read`读取数据项到程序，`write`把程序计算的新值写成数据库修改；a、b 是程序暂存变量，不是新增账户。纯计算暂存值并不直接改数据库。为手算，表中“数据库中”是逻辑上的写入状态，不表示该时刻所有数据已写到磁盘。

<a id="ch06-s004"></a>

### 1.2 提交和回滚的含义

**提交** `commit`表示事务成功结束，结果应持久保留。**回滚** `rollback`撤销事务修改，例如在步骤 3 后失败，应恢复甲余额为 500，乙仍 300，而不能把少了 200 的中间状态当成最终完成。

实际 DBMS 可能先保留旧版本、缓冲修改或记录日志；抽象 read/write 不承诺某个产品内部具体实现。应用仍需检查账户存在、余额规则、转账身份和修改行数。

<a id="ch06-s005"></a>

## 2. 【课程总结PPT重点知识点】ACID 四个要求逐一解释

> **本节为课程总结PPT明确列出的重点知识点：ACID。**

ACID 是 Atomicity、Consistency、Isolation、Durability 四个词的首字母，中文为原子性、一致性、隔离性、持久性。

<a id="ch06-s006"></a>

### 2.1 原子性：一件业务作为整体

扣 A 款与加 B 款应全做，或整体撤销。原子性不表示“只执行一条 SQL”，多条 SQL 也可组成一个事务；也不表示程序中途不会失败，而是失败后的已做修改得到正确处理。

<a id="ch06-s007"></a>

### 2.2 一致性：保持声明的规则和业务不变量

**业务不变量**是正确操作前后应保持的条件，例如本次转账 A+B=800；不变量不一定是某一格恒定不变。

转账后 300+500=800，保持规则；只扣款后 300+300=600，违背规则。数据库检查约束，应用提供正确操作，二者共同维护一致性。输入错误收款人也可能保持总额，但仍违反业务意图，不能说 DBMS 会自动识别。

<a id="ch06-s008"></a>

### 2.3 隔离性：控制别人看到什么与怎样交错

若另一事务 T2 查总额，它不应把 T1 半途的 600 当成合法完成结果。**隔离性**规定并发影响的可见范围与限制，理想的强隔离可使结果等价于某个逐件完成的次序。具体隔离级别可以较弱，详见第 07 章。

隔离不等于事务绝对不能同时推进；允许正确的交错可以提高吞吐量，即单位时间完成的事务数量。

<a id="ch06-s009"></a>

### 2.4 持久性：已经确认成功不能因普通故障丢失

若 T1 已提交并向甲返回成功，系统重启后还应保留 300、500。持久性不等于每次 write 都已经独立持久化，也不保证一份存储在所有物理灾难中永远存在；数据库依赖其配置的持久存储与恢复机制，备份等解决更广泛故障。

<a id="ch06-s010"></a>

## 3. 【课程PPT补充知识点】事务状态与失败

| 状态 | 白话解释 | 转账中的位置 |
| --- | --- | --- |
| 活动 active | 仍在执行 | 读取、计算、写入 |
| 部分提交 partially committed | 最后一条业务操作完成，提交保障尚未完成 | 已写 B，正处理提交 |
| 提交 committed | 成功提交已完成 | 可以确认业务成功 |
| 失败 failed | 出现错误，无法正常继续 | 断电、规则检查失败等 |
| 中止 aborted | 撤销结束 | 恢复原余额 |
| 结束 terminated | 清理后退出 | 无后续工作 |

通常活动→部分提交→提交→结束；活动或部分提交可失败，失败→中止，中止后可结束或重新开始事务。这里 `→`只表示状态转移，不是函数依赖。

“最后一条 UPDATE 成功”不能自动等同于“已提交”。重试也不能把原事务的一半简单补做，需要确认状态并防止重复业务。

<a id="ch06-s011"></a>

## 4. 【课程PPT补充知识点，但属于隔离性基础】为什么并发会出现异常

各小例独立从明确初值开始，不接续上一例。

<a id="ch06-s012"></a>

### 4.1 丢失更新：后来写入覆盖了别人的修改

A 初始 500；T1 存入 100，T2 取出 50，正确最终应为 550。

| 时刻 | 操作 | 暂存值或数据库结果 |
| --- | --- | --- |
| 1 | T1 读 A | T1 得 500 |
| 2 | T2 读 A | T2 也得 500 |
| 3 | T1 按旧值加 100 写 A | A=600 |
| 4 | T2 按自己的旧值减 50 写 A | A=450 |

最终 450，T1 的存款效果丢失，叫**丢失更新**。这不表示操作文本消失，而是结果被覆盖。锁、版本校验或适当的原子更新方式可防止这类错误，具体见第 07 章。

<a id="ch06-s013"></a>

### 4.2 脏读：读了可能被撤销的值

A 初始 500。T1 写 A=300，未提交；T2 读到 300；T1 回滚使 A 恢复 500。T2 使用的是一次失败业务的中间值，叫**脏读**。“脏”不表示数字格式坏了，而是来源未提交。

<a id="ch06-s014"></a>

### 4.3 不可重复读：同一事务两次看到不同已提交值

A 初始 500。T1 先读 500；T2 把 A 改为 400 并提交；T1 再读 A 得 400。两次读取同一数据项不同，叫**不可重复读**。这与脏读不同，第二个值已提交。

<a id="ch06-s015"></a>

### 4.4 幻读：相同条件的记录集合变了

独立选课表 `enrollment(SID,CID)`初始仅 S1 C1。T1 查“CID=C1 的所有选课”得到一人；T2 插入 S2 C1 并提交；T1 用同一条件再查，得到两人。

**幻读**关注满足条件的记录集合增加、减少或成员改变，不仅是已有某一行的值变化。第 07 章解释范围锁和快照。

<a id="ch06-s016"></a>

### 4.5 不一致分析：把不同时间的状态拼在一起

回到 A=500、B=300 的转账。T1 是统计者，T2 把 A 转 200 到 B。

| 顺序 | 动作 |
| --- | --- |
| 1 | T1 读 A=500 |
| 2 | T2 完成转账并提交，A=300、B=500 |
| 3 | T1 读 B=500 |
| 4 | T1 相加得 1000 |

1000 既不是转账前总額也不是转账后总额，两者都为 800。它来自不同时点拼接，叫不一致分析。保护单个写操作并不足以保证跨多行读取的一致观察。

<a id="ch06-s017"></a>

## 5. 【课程总结PPT重点基础】调度：把操作按实际次序排起来

<a id="ch06-s018"></a>

### 5.1 操作记号先读清楚

**调度**是多个事务操作的时间顺序表，每个事务内部仍按自身程序次序执行。

`r1(A)`表示 T1 读 A，r 为 read；`w1(A)`表示 T1 写 A，w 为 write；`c1`表示 T1 提交，c 为 commit；`a1`表示 T1 中止，a 为 abort。下标／编号识别事务，括号里的字母识别数据项。一行逗号分隔的操作串按从左到右的顺序执行，不表示同时发生。

<a id="ch06-s019"></a>

### 5.2 串行与非串行

**串行调度**让一个事务完全结束后下一个才执行，例如 `r1(A),w1(A),c1,r2(A),w2(A),c2`。

**非串行调度**把事务交错，例如 `r1(A),r2(B),w1(A),w2(B),c1,c2`。A、B 是独立数据项，T1 只改 A，T2 只改 B，这种交错可以正确。不能把“交错”直接等同于“错误”。

**可串行化**要求交错效果按规定的等价标准相当于某个串行次序，不要求现实执行已经串行。接下来区分冲突等价和视图等价。

<a id="ch06-s020"></a>

## 6. 【课程总结PPT重点中的重点】哪些操作冲突

<a id="ch06-s021"></a>

### 6.1 三个条件缺一不可

两操作**冲突**须满足：属于不同事务；访问同一数据项；至少一个是写。

| 操作对 | 是否冲突 | 原因 |
| --- | --- | --- |
| r1(A)、r2(A) | 否 | 都只读 |
| r1(A)、w2(A) | 是 | 同项，含写 |
| w1(A)、r2(A) | 是 | 同项，含写 |
| w1(A)、w2(A) | 是 | 同项，两写 |
| w1(A)、w2(B) | 否 | 数据项不同 |
| r1(A)、w1(A) | 不算事务间冲突对 | 同一个事务，内部顺序仍须保留 |

<a id="ch06-s022"></a>

### 6.2 为什么顺序会影响含义

A 初始 500，T2 写 A=300。先 r1(A) 再 w2(A)，T1 读 500；先写再读，T1 读 300。因此两操作不能随意交换。

两个写也不能随意换序：T1 写 600、T2 写 450，最后由谁写决定最终值。即使某个例子恰好两者写相同值，定义上仍是冲突；判定考虑操作结构，不能凭一次数值巧合忽略。

<a id="ch06-s023"></a>

## 7. 【课程总结PPT重点中的重点】冲突等价与交换操作

<a id="ch06-s024"></a>

### 7.1 等价检查的对象是什么

两个调度包含相同事务及操作，且所有冲突操作对的先后关系一致，叫**冲突等价**。可以通过不断交换相邻、不冲突的操作来理解这种等价；不得交换同事务必须保留的程序顺序。

<a id="ch06-s025"></a>

### 7.2 一个能一步步整理成串行的例子

独立事务 T1 先读写 A，再读写 B；T2 只读写 B。给定：
```text
r1(A), w1(A), r2(B), w2(B), r1(B), w1(B)
```
T2 的 B 操作与 T1 的 A 操作不冲突。把 r2(B) 向前移过 w1(A)、r1(A)，再把 w2(B) 移过这些 A 操作，得到：
```text
r2(B), w2(B), r1(A), w1(A), r1(B), w1(B)
```
这是 T2→T1 的串行次序。B 上 T2 原来就在 T1 之前，整理过程中未改变这一冲突顺序，所以原调度**冲突可串行化**。

提交操作在这节示例中省略，只研究读写次序；是否能安全恢复还需另看提交与依赖，不能混为一谈。

<a id="ch06-s026"></a>

## 8. 【课程总结PPT重点中的重点】优先图与冲突可串行化

<a id="ch06-s027"></a>

### 8.1 图里的点与箭头

**优先图**也称前驱图：每个事务一个**节点**；若 Ti 的操作先于 Tj 的冲突操作，画 `Ti→Tj`。箭头表示必须串行排在前面，不表示某事务现在正在等待。

**环**是沿箭头走最后回到起点，例如 T1→T2→T1；**无环**表示不存在这种循环。调度冲突可串行化当且仅当优先图无环。

**拓扑排序**是在无环图中把事务排成一个次序，使每条箭头的起点在终点之前；就是允许的串行次序。

<a id="ch06-s028"></a>

### 8.2 无环例：逐对找边

两个事务都读写 A，再读写 B。给定时间线：

| 顺序 | 操作 |
| --- | --- |
| 1 | r1(A) |
| 2 | w1(A) |
| 3 | r2(A) |
| 4 | w2(A) |
| 5 | r1(B) |
| 6 | w1(B) |
| 7 | r2(B) |
| 8 | w2(B) |

A 上 r1 在 w2 前、w1 在 r2 前、w1 在 w2 前，都产生 T1→T2；B 同样只产生 T1→T2。重复边只画一次。图是两个节点一条边，无环，所以可串行化为 T1 后 T2，尽管 T2 的 A 操作在 T1 的 B 操作之前执行。

<a id="ch06-s029"></a>

### 8.3 有环例：矛盾来自两个数据项

```text
r1(A),w1(A),r2(A),w2(A),r2(B),w2(B),r1(B),w1(B)
```

A 上 T1 的写在 T2 读写之前，给 T1→T2；B 上 T2 的写在 T1 读写之前，给 T2→T1。

| 边 | 对应证据 |
| --- | --- |
| T1→T2 | w1(A) 在 r2(A)／w2(A) 前 |
| T2→T1 | w2(B) 在 r1(B)／w1(B) 前 |

形成环，无法同时让 T1 在 T2 前、T2 又在 T1 前，因此不冲突可串行化。不能因为每个事务内部顺序正确就判断整体正确。

<a id="ch06-s030"></a>

## 9. 【课程总结PPT重点知识点】视图等价与盲写

> **本节为课程总结PPT明确列出的重点知识点：视图可串行化。**

<a id="ch06-s031"></a>

### 9.1 关注读取来源和最终写者

**视图等价**不是 SQL 视图可更新性。对同样事务的两个调度，要求：

1. 原来读初始值的读取，在另一个调度仍读初始值；
2. 原来从某事务某次写取得值的读取，仍从同一写取得值；
3. 每个数据项的最终写操作由同一事务执行。

**视图可串行化**是与某个串行调度视图等价。冲突可串行化一定视图可串行化，反过来可能不成立。

<a id="ch06-s032"></a>

### 9.2 盲写例子为什么冲突有环却视图可串行化

**盲写**是在未先读该数据项的情况下直接写值。独立场景中 T1 连续计划两次写 X，T2 写一次 X：
```text
w1(X),w2(X),w1(X)
```
第一个 w1 在 w2 前，产生 T1→T2；w2 在第二个 w1 前，产生 T2→T1，冲突有环。

这里没有任何读，前两项视图条件不用匹配读取；最终写者都是 T1。串行次序 T2 后 T1，也由 T1 最后写。因此原调度视图可串行化。

不能据此只用“最终值看起来一样”判断任意调度；存在读时必须核对读来源，最终写者只是三项之一。

<a id="ch06-s033"></a>

## 10. 【课程总结PPT重点知识点】可恢复调度：不要先提交依赖未确定的结果

> **本节为课程总结PPT明确列出的重点知识点：可恢复调度。**

<a id="ch06-s034"></a>

### 10.1 明确什么是读取依赖

若 T2 读到 T1 尚未提交的写入，就说 T2 对这次读取**依赖** T1。**可恢复调度**要求：只要 T2 读了 T1 写出的值，T2 提交前 T1 必须先提交。

下面是独立 A 场景，初始 X=500；T1 写 X=300，T2 读取它。w1(X)后最新写者是 T1，因此读取来源明确。

| 顺序 | 可恢复但有脏读 | 原因 |
| --- | --- | --- |
| 1 | w1(X) | T1 尚未提交 |
| 2 | r2(X) | T2 读自 T1 |
| 3 | c1 | 来源事务成功 |
| 4 | c2 | 依赖者后来提交 |

串行化检查与恢复检查不同；这个顺序允许脏读，只保证提交先后适当。

<a id="ch06-s035"></a>

### 10.2 不可恢复例：已经提交的结果依赖失败业务

```text
w1(X),r2(X),c2,a1
```
T2 先提交，T1 后中止。T2 依赖的值被撤销，但 T2 已对外确认成功，普通未提交事务回滚机制不能把已提交结果随意当作未提交撤掉。这是不可恢复调度。

“可恢复”是给定调度的依赖与提交关系性质，不等于系统具备备份或某个恢复软件就能把任意交错变合法。

<a id="ch06-s036"></a>

## 11. 【课程总结PPT重点知识点】无级联调度：读取前来源先提交

> **本节为课程总结PPT明确列出的重点知识点：无级联调度。**

<a id="ch06-s037"></a>

### 11.1 什么叫级联回滚

独立时间线 `w1(X),r2(X),w2(Y),r3(Y),a1`。Y 是另一个数据项，T2 用读到的 X 结果计算 Y，T3 又读取 Y。T1 失败时，T2 读了失效值，需回滚；T3 又依赖 T2，可能接着回滚，叫**级联回滚**。

<a id="ch06-s038"></a>

### 11.2 避免级联的条件

**无级联调度**要求读取一个由其他事务写的值之前，该写者已经提交。例如：
```text
w1(X),c1,r2(X),c2
```
T2 不读 T1 未提交值，因此不需要随 T1 的失败撤销。

与可恢复的差别：可恢复要求“依赖者提交前，来源已提交”；无级联更早要求“依赖者读取前，来源已提交”。因此无级联一定可恢复，但可恢复不一定无级联。

<a id="ch06-s039"></a>

## 12. 【课程PPT补充知识点，但有助于恢复理解】严格调度：未提交的写也不能被覆盖

<a id="ch06-s040"></a>

### 12.1 对读和写同时加限制

**严格调度**要求：某事务写了 X 后，在它提交或中止之前，其他事务既不能读 X，也不能写 X。读限制避免脏读，写限制避免**脏写**，即覆盖尚未提交的修改。

`w1(X),c1,w2(X),c2`可以严格；`w1(X),w2(X),c1,c2`不严格，因为 w2 覆盖未提交 w1。

后一例没有任何读，恢复与无级联的“读依赖”条件没有被违反，所以可以可恢复、无级联，却不严格。无级联只管未提交来源的读取，并不自动禁止覆盖。

<a id="ch06-s041"></a>

### 12.2 为什么严格性有利于撤销

X 初始 500，T1 写 300，T2 写 600；T1 后来中止。若简单把旧值 500 写回，会覆盖 T2 的 600。正确恢复必须避免这种冲突或复杂地处理它。严格调度让来源未结束前别人不能盖写，撤销更直接。

关系链：
```text
严格 ⇒ 无级联 ⇒ 可恢复
```
`⇒`表示左边保证右边。反向不保证。此链独立于冲突可串行化，一个性质不能代替另一个性质。

<a id="ch06-s042"></a>

## 13. 【课程总结PPT重点知识点】怎样实现隔离与可串行化

**并发控制协议**是各事务访问数据必须遵守的规则。课件介绍的方向包括：

- **锁**：先取得读／写许可，不兼容时等待；
- **时间戳排序**：为事务排逻辑先后，违反顺序时撤销；
- **验证**：先尝试执行，提交前检查是否冲突；
- **多版本**：保留多个历史值，让读取按规则选择版本。

这里只认清方法的目标；完整加锁、等待、回滚、版本例子在第 07 章。不是所有能可串行化的协议都自动保证严格或无级联，需要分别看规则。

<a id="ch06-s043"></a>

## 14. 【课程总结PPT重点知识点】日志怎样帮助原子性与持久性

<a id="ch06-s044"></a>

### 14.1 日志不是只有“转账成功”四个字

**日志**是恢复所需的持久记录，通常记录事务标识、修改对象和恢复信息。转账教学日志可解释为：

| 日志内容 | 用途 |
| --- | --- |
| T1 开始 | 知道事务已启动 |
| T1，A，旧值 500，新值 300 | 可撤销或重做甲的修改 |
| T1，B，旧值 300，新值 500 | 可撤销或重做乙的修改 |
| T1 提交 | 判断事务完成 |

这是一种便于理解的简化格式，真实系统不一定每条都直接存完整旧值新值。

<a id="ch06-s045"></a>

### 14.2 UNDO、REDO 与先写日志

**UNDO**是撤销未完成修改；**REDO**是重做已确认提交、但数据页可能还没保存完整的修改。

**WAL**是 Write-Ahead Logging，先写日志原则：相关恢复日志要在对应修改的数据页持久化前先持久化；提交成功所需的日志也要按协议可靠保存。这样故障后不至于只剩修改却找不到恢复依据。

例：T1 扣 A 后未提交就失败，按旧值撤回至 A=500；若提交已可靠记录但 B 数据页仍停留 300，重做使 B=500。读写入缓冲区不等于全部数据页已落盘，日志让这二者可以分工。

<a id="ch06-s046"></a>

### 14.3 检查点与恢复算法范围

**检查点**保存恢复进度信息，帮助系统减少故障后需要重新检查的范围；它不一定意味着所有活动事务已提交。ARIES 是一种经典日志恢复算法名称，涉及日志序号、分析、重做、撤销等步骤。完整恢复算法在课程第 16 章，本章只说明这些名称的作用，不用一句“利用日志”冒充完整算法证明。

<a id="ch06-s047"></a>

## 15. 【课程PPT补充知识点】SQL 事务怎样体现上述边界

```sql
START TRANSACTION;
UPDATE account SET balance=balance-200 WHERE account_id='A';
UPDATE account SET balance=balance+200 WHERE account_id='B';
COMMIT;
```
`START TRANSACTION`开始，`UPDATE`修改表，`SET`写新值，`WHERE`指定账户，`COMMIT`整体提交；出现错误时使用 `ROLLBACK`。单引号表示文字账户号，分号结束语句。

在本例成功完成后全表两行为 A 甲 300、B 乙 500；回滚后 A 甲 500、B 乙 300。实际代码还需处理扣款条件不满足、某条更新影响零行等情况，决定提交或回滚。自动提交设置与开始事务的具体语法按 DBMS 核实。

<a id="ch06-s048"></a>

## 16. 一份调度的判别顺序

1. 列出事务、数据项、每次操作和来源。
2. 只对“不同事务、同项、至少一写”画优先图边。
3. 查环，给冲突可串行化结论和串行次序。
4. 对每个读，找它读的是哪个写者的值。
5. 看来源提交是否早于依赖者提交，判断可恢复。
6. 看来源提交是否早于该读，判断无级联。
7. 看未结束的写是否被别人读或覆盖，判断严格。

不要把优先图当成等待图；优先图依据已经发生的冲突顺序，等待图依据被阻塞的锁请求，下一章会区分。

## 17. 本单元模拟题

<a id="ch06-s050"></a>

### 题目一：事务的四种特性

**原题**

> 事务的四种特性指的是什么？

**PPT 参考答案**

> 原子性，一致性，隔离性，持久性。

**规范答案与解析**

- 原子性：事务全部完成或全部撤销。
- 一致性：正确事务保持数据库约束和业务不变量。
- 隔离性：并发事务之间的影响受控，理想结果等价于允许的串行次序。
- 持久性：提交后的结果在故障后仍然保留。

只列四个名词适合简答题的最短答案；若题目分值较高，应补充定义和转账例子。

<a id="ch06-s051"></a>

### 题目二：转账中途故障

**原题**

> 张三通过汇款转给李四 200 元。张三的账户已经减掉 200 元后系统发生故障，并没有在李四账户中增加 200 元。数据库出现了什么状态？应怎样解决？数据库通过什么手段实现？

<a id="ch06-s052"></a>

### 17.1 原转账题的金额与恢复过程

源 PPT 在同一题里混用了“200元”和“200美元”，以下按同一币种的 200 处理，不引入汇率换算。原题没有给张三、李四的初始余额。为了看清“不一致”，另外设**教学初值**张三 500、李四 300，不收手续费，owner 列此时用张三、李四表示所有者。题中的 200 元来自原题，其他初值是为说明而补充。

| 时刻 | 张三 | 李四 | 总额 | 如何解释 |
| --- | --- | --- | --- | --- |
| 开始 | 500 | 300 | 800 | 正常 |
| 扣款后故障 | 300 | 300 | 600 | 未完成，减少 200 |
| 未提交事务撤销后 | 500 | 300 | 800 | 恢复原状态 |
| 若事务完整成功 | 300 | 500 | 800 | 正确转账结果 |

题面没有直接说明日志和提交时刻。采用参考答案的“未完成、应回滚”解释，属于未提交失败事务；此时日志中的旧值或撤销信息支持撤回扣款。

若实际情况是“提交记录已可靠保存，但数据页没写完整”，应走已提交事务恢复路径，而不是一概撤回。原题参考答案隐含前一种状态，不能从“系统故障”四字推断所有现实故障都用相同处理。


**PPT 参考答案**

> 数据库处于不一致状态。应该进行事务回滚，即将张三账户中减掉的 200 元再加回来。利用日志实现。

**规范答案与完整解析**

数据库处于违反转账业务不变量的**不一致状态**，因为总金额减少了 200 元。根本原因是转账的两个步骤没有作为一个原子事务完整完成。

若故障发生时事务尚未提交，恢复系统应撤销张三账户的扣款，使两个账户恢复到事务开始前的状态。数据库通常利用日志记录旧值或可撤销信息，并在重启恢复时对未提交事务执行 `UNDO`。

正确程序还应把扣款和入账放在同一事务中：

```sql
START TRANSACTION;
UPDATE account SET balance = balance - 200 WHERE owner = '张三';
UPDATE account SET balance = balance + 200 WHERE owner = '李四';
COMMIT;
```

发生错误时执行 `ROLLBACK`。若事务已经成功提交但数据页尚未全部落盘，恢复系统还可能利用日志 `REDO` 已提交修改，以满足持久性。

实际转账程序还应检查两个账户是否存在、扣款是否符合余额规则、两条 `UPDATE` 是否影响预期行数，并在同一事务中据此决定提交或回滚。DBMS 提供原子提交机制，却不能替应用判断“收款账户写错了”这类业务错误。

**易错点**

- 不能只补执行李四入账而不核对事务状态，否则重试可能重复入账。
- “日志”是恢复依据，不等于只保存一条普通业务文本。
- 完整日志恢复算法属于第 16 章，本题只需说明回滚和日志作用。

## 18. 自拟自测题与逐步答案

以下四题为自拟题。X、Y 是数据项代号；r、w、c、a 分别读、写、提交、中止。

<a id="ch06-s054"></a>

### 18.1 一个非串行调度能否冲突可串行化？

**给定**：`r1(X),w1(X),r2(X),w2(X),r1(Y),w1(Y),c1,c2`。T1 先改 X 再改 Y，T2 只改 X。

**步骤**：X 上所有跨事务冲突均由 T1 在前、T2 在后，得 T1→T2。Y 只有 T1，不产生跨事务边。无环。

**结论**：冲突可串行化，可等价为 T1 后 T2。T2 可能读 T1 未提交 X；因此 c1 在 c2 前时可恢复，但因 r2 早于 c1，不无级联、不严格。必须把串行化与恢复结论分开写。

<a id="ch06-s055"></a>

### 18.2 三种恢复性质逐一判断

**给定**：`w1(X),r2(X),c1,c2`，r2 读自 w1。

**步骤**：c1 在 c2 前，可恢复；r2 在 c1 前，读到未提交值，不无级联；严格性也因该读取失败。

**结论**：可恢复，但有脏读、非无级联、非严格。要无级联，可改为 w1(X),c1,r2(X),c2。

<a id="ch06-s056"></a>

### 18.3 不读脏数据就一定严格吗？

**给定**：`w1(X),w2(X),c1,c2`，两事务直接盲写。

**步骤**：没有读，因此没有违规的读取依赖，可恢复、无级联；但 w2 在 c1 前覆盖 T1 未提交写，违反严格。两个写只形成 T1→T2，没有环。

**结论**：本调度冲突可串行化且无级联，但不严格。严格性还禁止脏写。

<a id="ch06-s057"></a>

### 18.4 统计总额为什么会多出钱？

**背景**：A=500、B=300。T1 先读 A；T2 转 200 从 A 到 B 并提交；T1 再读 B。

**步骤**：T1 两读分别得到 500、500，合计 1000；转前、转后均为 800。多出的 200 是读了两种状态，不是银行真的生成了钱。

**结论**：不一致分析；需要合适隔离，使这项统计采用一致观察或受正确的串行化控制。只验证每条余额非负不够。
